讲一下分布式令牌桶限流。

讲一下分布式令牌桶限流。

讲一下分布式令牌桶限流。

🧠 联想记忆法

一句话记忆：令牌桶 = 水龙头匀速注水的桶。 桶有容量（突发上限），水龙头每秒匀速滴入 rate 个令牌（常态速率），请求来了从桶里拿令牌，桶满则多余的水溢出（多余令牌丢弃），桶空则拒绝。把"水"换成"令牌"，原理一字不差。

三个记忆钩子：
1. 公式钩子：tokens = min(capacity, tokens + (now - last_refill) × rate)——所有令牌桶实现（单机、Guava、Redis Lua）都是这一行数学公式的变体。面试时先背这行公式，代码就是它的翻译。
2. 对比钩子：漏桶（Leaky Bucket）像"漏斗"——进多出少、出水量恒定；令牌桶像"蓄水池"——允许你一次性舀走很多（突发 burst），但长期平均速率被 rate 锁死。一句话分胜负：漏桶恒定速率，令牌桶允许突发。
3. 分布式口诀："单机桶 → Redis 全局桶 → 分片桶 → 本地桶+Token Server"——这是一条演进链，每层解决上一层的问题。顺着背，答题不会乱。

数字记忆：Nginx 后面挂 5 台机器、每台单机限 100 QPS，全局最高能到 500——"5×100=500"这个翻车公式，是回答"为什么单机限流不够"的最好开场白。

📖 深度解答

1. 核心概念

限流（Rate Limiting）：控制单位时间内进入系统的请求量，防止流量尖峰打垮下游。

令牌桶（Token Bucket）：核心三个参数——
- 桶容量 burst：桶最多能存多少令牌，决定瞬时突发能力；
- 令牌生成速率 rate：每秒匀速向桶中补充多少令牌，决定长期平均速率；
- 请求到来时消耗一个令牌，有令牌放行、无令牌拒绝。

与漏桶（Leaky Bucket）的本质区别：漏桶把请求排进一个固定速率的队列，出口恒定速率，不关心入口尖峰——你的服务不支持突发；令牌桶是"匀速补充 + 任意消耗"，允许突发（burst），只要桶里有积攒的令牌，短时间可以打满 burst 个请求。一句话：漏桶平滑"出口"，令牌桶平滑"入口的平均速率但容忍突发"。这也是为什么网关选型时，Nginx 的 limit_req（漏桶模型）适合保护单一后端吞吐，而令牌桶适合"允许秒杀瞬间的流量但长期封顶"的业务。

分布式令牌桶（Distributed Token Bucket）：多实例部署下，把"一个桶"变成"全局共享的一个桶"（Redis 承载），或在"各实例本地桶 + 中心协调"之间做折中，保证全局视角的限流精度。

2. 底层原理

2.1 单机令牌桶：一行公式

public class TokenBucket {
    private final int capacity;    // 桶容量 burst
    private final double rate;     // 每秒生成令牌数
    private double tokens;
    private long lastRefill;

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 核心公式：按时间差补令牌，上限为桶容量
        tokens = Math.min(capacity, tokens + (now - lastRefill) * rate / 1000);
        lastRefill = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}

两个工程细节：一是懒更新（lazy refill）——不需要后台线程定时补令牌，只在请求来时按时间差补，性能最优；二是 Guava 的 RateLimiter 本质是同一思路，但引入了 storedPermits 与"预热（warmup）"平滑模型，面试可顺带提一句证明用过。

2.2 为什么单机令牌桶不够

第一，多实例流量不均。集群里 5 个实例各自持有一个独立的桶，每个限 100 QPS，负载均衡再均匀，用户视角的全局上限也只是"约 500"，不精确；更糟的是 hash 不均、新实例上线、机器权重不同时，某个实例可能先被打爆，而另一些实例的额度白白浪费。

第二，单机限流在 Nginx 后面的误区。Nginx 把请求分发到 5 个应用实例，如果只在应用里配了单机限流，每台限 100，全局峰值可能到 500——你以为保护了后端，实际只是把 500 拆成了 5 份"各自为政"。而且 Nginx 边缘层不限流的话，突发流量照样穿透到应用层。正确姿势是分层：网关（Nginx 集群）做边缘限流挡大流量，应用层再做全局精确限流兜底。我之前在项目里就是这套组合：Nginx 用 lua 脚本做边缘粗粒度限流，Sentinel 集群流控做应用层精确限流。

2.3 分布式实现：Redis Lua 原子实现

核心难点是原子性（atomicity）：读取令牌数、补令牌、扣减、写回，必须是不可分割的，否则并发下会超发。Redis 单线程模型 + Lua 脚本天然满足——Eval 执行的脚本不会被其他命令插入。

-- KEYS[1] : 桶 key，如 "rate_limit:user:1001"
-- ARGV[1] : 桶容量 capacity（突发上限）
-- ARGV[2] : 令牌生成速率 rate（每秒个数）
-- ARGV[3] : 当前时间戳（毫秒）
-- ARGV[4] : 本次消耗令牌数 cost，通常为 1

local key   = KEYS[1]
local cap   = tonumber(ARGV[1])
local rate  = tonumber(ARGV[2])
local now   = tonumber(ARGV[3])
local cost  = tonumber(ARGV[4])

local last    = tonumber(redis.call('HGET', key, 'last_refill') or now)
local tokens  = tonumber(redis.call('HGET', key, 'tokens') or cap)

-- 核心公式：按时间差匀速补令牌，最多补到桶容量
tokens = math.min(cap, tokens + (now - last) * rate / 1000)

if tokens >= cost then
    tokens = tokens - cost
    redis.call('HSET', key, 'tokens', tokens)
    redis.call('HSET', key, 'last_refill', now)
    -- 设置过期时间，空闲桶自动回收，避免 key 无限增长
    redis.call('PEXPIRE', key, math.ceil(cap * 1000 / rate) * 2)
    return 1                      -- 1 放行
end
redis.call('HSET', key, 'last_refill', now)
return 0                          -- 0 拒绝

Java 侧调用：

Long allow = (Long) jedis.eval(script, 1,
        "rate_limit:user:1001",
        "100",              // capacity
        "10",               // rate: 每秒 10 个
        String.valueOf(System.currentTimeMillis()),
        "1");

要点：桶的状态（last_refill 时间戳 + 剩余令牌数）持久化在 Redis Hash 里；时间戳建议用 redis.call('TIME') 取 Redis 服务器时间，而不是客户端时钟，规避多机时钟偏差；PEXPIRE 让不活跃的 key 自动过期，防止内存被限流 key 撑爆。

2.4 Redis 单 key 的性能与热点问题

这是必须主动讲出的缺点：单 key 限流是天然热点（hot key）。所有实例的请求都打到同一个 Redis key，而 Redis 单线程处理命令，百万级 QPS 下单个分片会成为瓶颈，甚至比被打爆的服务更早挂。解决方向有三层：
1. 分片桶：按用户 ID / 业务维度把 key 拆到多个分片——热点分散了，但"全局一个桶"的精度没了，只能做"每用户限流"这类天然可分维度的场景；
2. 本地桶 + 中心协调（见下文）；
3. 网关层前置限流，把打到 Redis 的流量先削掉一层。

3. 实践应用

3.1 Redis Lua 方案落地要点

  • 限流维度设计：按用户、按 IP、按接口分别建 key；
  • 超时与降级：Redis 不可用时不能把请求全部放行，要 fallback 到本地令牌桶兜底；
  • 性能：一次 eval 约亚毫秒级，单分片支撑数万 QPS 没问题，再高就要拆。

3.2 分片令牌桶 / 本地令牌桶 + 分布式协调（Token Server）

分片令牌桶：把全局配额按维度均分到 N 个桶，每个桶独立限流。优点是无中心、性能好；缺点是均分不代表真实流量分布，配额利用率低。

本地令牌桶 + Token Server（令牌服务器）——我推荐的重点方案，也是 Sentinel 集群流控的实现思路：

// 每 5 秒向 TokenServer 领取本实例配额（带租约 lease）
Quota q = tokenServer.allocate(instanceId, baseQuota);
localBucket.refresh(q.limit);   // 本地令牌桶按分配到的额度限流
  • 每实例分额度：实例从中心领取自己的配额，请求只打本地内存桶，零网络开销，性能接近单机限流；
  • 动态调整：TokenServer 依据各实例真实流量、权重、负载动态调额（流量大的实例多给，空闲的回收），配额带租约（lease）自动过期，实例宕机不续租即自动回收，防止额度泄漏；
  • 一致性取舍：领取周期内各实例"各管各的"，全局精度略降（瞬时可能超一点点），换来的是吞吐和可用性——限流本质是概率保护，不是精确记账。

3.3 网关级方案

  • Sentinel 集群流控（Cluster Flow Control）：应用层主流方案。启动 Token Server（内嵌模式：实例内选主；独立模式：单独部署），支持两种阈值模式——单机均摊阈值（全局值除以节点数）和集群总阈值（严格全局）；选主故障时可自动降级为单机限流。
  • Nginx 集群限流：OpenResty + lua-resty-limit-traffic 配合 lua_shared_dict 做单机，加 Redis 后端可做集群；注意 ngx_http_limit_req_module 本身是漏桶模型（恒定速率 + burst 排队），这是加分细节。
  • Kong：rate-limiting 插件支持本地内存与 Redis（cluster）两种模式，是现成的网关限流方案。

我之前的经历正好覆盖这条链路：Nginx（lua-resty + Redis）做边缘限流挡住大流量 → Sentinel 集群流控在应用层做精确兜底，上线后限流超发率从单机方案的"不可控"收敛到集群总阈值以内。

4. 深入思考

时钟问题（Clock Skew）：Lua 脚本里如果用客户端时间戳，各机器时钟漂移会让补令牌计算失真；应改用 redis.call('TIME') 取 Redis 服务器时间（同一节点内一致）。Token Server 租约续期依赖时钟，时钟回拨会导致租约失效/延长，需 NTP 同步 + 安全余量。

预热（Warmup）：令牌桶初始化即桶满，冷启动立刻满速放行——服务刚扩容的实例会瞬间被打满，违背扩容的"慢启动"意图。解法：初始令牌设为 0、预热期逐步抬升 rate（Guava SmoothWarmUp），或 Sentinel 的 warmup 流量控制做冷启动保护。

动态配额（Dynamic Quota）：大促时全局 rate 上调，各实例额度按权重比例同步刷新；配额中心可按实时负载与水位动态调额，避免"限流器先于服务被打爆"。

降级（Degradation）：限流组件必须自身可控故障——策略上分 fail-open（放行）与 fail-closed（拒绝）：Redis 挂掉时降级到本地桶兜底（额度按实例数均摊），TokenServer 挂掉时降级为单机限流；同时监控限流器自身的丢弃率、耗时、超时，让"限流器挂了"这件事可感知、可切换。原则：限流器不能成为比被保护服务更脆弱的故障点。

🗺️ 回答思路

答题逻辑框架（金字塔式）

一句话定义（令牌桶=匀速补令牌+允许突发，与漏桶的区别）
  ↓ 单机原理：一行公式 + 为什么不够（Nginx 后 5×100=500 的误区）
  ↓ 分布式三连：Redis Lua（原子）→ 热点问题（单 key 天然热点）
  ↓              → 分片/本地桶+Token Server（性能与精度的取舍）
  ↓              → 网关级（Sentinel 集群流控 / Nginx / Kong）+ 个人经历
  ↓ 收尾：时钟/预热/动态配额/降级（展示思考深度）

重点得分点（面试官想听到的关键词）

  1. 一句话分清令牌桶和漏桶：允许突发 vs 恒定速率；
  2. 公式：min(capacity, tokens + (now-last_refill)*rate)；
  3. Lua 原子性：单线程 + eval 无插队，"读-改-写"不可分割——这是分布式限流正确性的基石；
  4. 主动说出热点问题：单 key 是天然热点、千万 QPS 打爆单分片——主动暴露问题比被追问强十倍；
  5. 性能与精度取舍：本地桶+Token Server 是面试官最想听的"工程感"答案；
  6. 降级策略：fail-open / fail-closed 二选一的权衡；
  7. 结合经历：Nginx 边缘限流 + Sentinel 集群流控，一句带过即可加分。

常见误区（一定要避开）

  • ❌ 说"分布式令牌桶就是把 Redis 当桶"，漏掉热点问题——会被追问"百万 QPS 怎么办"；
  • ❌ 混淆漏桶与令牌桶，尤其说"Nginx limit_req 是令牌桶"（它是漏桶变体）；
  • ❌ 说"每台机器限 100 就等于全局限 100"——这是 Nginx 后的经典翻车点，主动纠正它；
  • ❌ 只背 Redis 方案不讲降级——"Redis 挂了怎么办"是必问 follow-up；
  • ❌ 把 Lua 脚本的时间戳用客户端时钟而不解释——时钟问题考察点。

时间分配建议（总长 2~3 分钟）

  • 0:30–1:00 单机公式 + Nginx 后误区（讲故事）；
  • 1:00–2:00 分布式方案主体：Lua 原子实现 → 热点 → Token Server → 网关；
  • 2:00–2:30 深入思考收尾（时钟/预热/降级各一句）+ 结合自己经历。
  • 时间紧就砍"分片桶"，但热点和降级必须讲。

过渡话术（可直接背）

  • 开场："我先从单机令牌桶讲起，因为分布式方案只是把它搬到共享存储上，公式不变。"
  • 引出误区："这里有个很常见的误区——很多人在 Nginx 后面的每台机器上各限 100，觉得全局就是 100，实际 5 台机器能冲到 500。"
  • 转分布式："把桶放进 Redis，用 Lua 保证原子性，是最直接的分布式方案，但它有一个绕不开的问题——热点。"
  • 讲方案取舍："所以工程上更常用的是本地桶 + Token Server：性能接近单机，精度通过动态调额找回，限流本来就是概率保护。"
  • 收尾："最后补一句降级——Redis 挂了不能 fail-open 全放行，我会降级到本地桶兜底并告警，限流器不能成为新的故障点。"
