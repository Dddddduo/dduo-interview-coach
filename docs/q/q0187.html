漏桶算法是什么？

漏桶算法是什么？

漏桶算法是什么？

🧠 联想记忆法

记忆口诀："一个桶、一个洞、匀速漏、溢出丢"——再配一句对比口诀："令牌管进口，漏桶管出口；令牌可突发，漏桶必匀速。"

记忆原理：漏桶（Leaky Bucket）是一个天然的视觉化场景，大脑对"具象画面"的记忆效率远高于抽象概念。面试时先在白板上画一个水桶——上面水龙头哗哗倒水（任意速率的输入），底部一个小洞匀速滴水（恒定速率 outflow），桶满后水溢出来被泼掉（溢出丢弃）。这一幅图就是全部考点：桶身=容量（Capacity），洞的大小=速率（Rate），滴水=输出恒定，溢出=拒绝语义。画面记住了，四个要素就齐了，回答时"先画图再讲理"还能显得思路特别清晰。

关联知识：把它挂在你已经熟悉的"限流四件套"上——固定窗口（Fixed Window）、滑动窗口（Sliding Window）、漏桶（Leaky Bucket）、令牌桶（Token Bucket）。其中漏桶和令牌桶是镜像关系：令牌桶是"入口发牌，攒牌可突发"，漏桶是"出口限速，出来必匀速"。此外可以联想消息队列的"削峰填谷"，本质就是漏桶思想的落地。

📖 深度解答

1. 核心概念（是什么）

一句话定义：漏桶算法（Leaky Bucket Algorithm）是一种限流（Rate Limiting）与流量整形（Traffic Shaping）算法——用一个容量固定的桶充当缓冲，请求以任意速率"倒入"桶中，桶底以恒定速率匀速"漏出"（即按固定速率处理请求）；当桶被灌满时，新到达的请求溢出桶沿，被直接丢弃（拒绝服务）。

它解决的核心问题是：把突发的、不均匀的输入流量，整形为平滑、恒定的输出流量。注意它的关注点不是"一段时间内最多放行多少个请求"，而是"任意时刻的输出速率都不能超过一个定值"。这决定了它在限流算法家族中的独特地位——它是四大经典算法中唯一一个"输出恒定、零突发"的算法，也因此成为与令牌桶（Token Bucket）对比的高频考题。

2. 底层原理（为什么）

漏桶有两种实现形态，面试中把两种都说清楚是拉开差距的关键：

形态一：队列式（FIFO 队列 + 匀速消费）——最直观的实现
- 一个容量为 capacity 的 FIFO（先进先出）队列作为桶；
- 请求到达时，队列未满则入队缓冲，已满则丢弃；
- 一个消费者线程（或定时器）以恒定速率 rate 从队头取出请求处理。
- 特点：它是真正的缓冲。突发的请求被按到达顺序排开，依次匀速放行；未满桶时请求不会丢，只是等待时间变长。代价是需要存储请求和常驻消费线程。

形态二：算法式（时间戳累加）——"令牌桶的反向"实现
- 不实际存储请求，只维护两个变量：当前水位 waterLevel 和上次漏水时间 lastLeakTime；
- 每个请求到来时，先按流逝的时间计算"漏掉了多少水"：leaked = (now - lastLeakTime) × rate，水位减去漏掉的量；
- 再尝试"加一滴水"（一个请求 = 一滴水），若加水后超过桶容量，则拒绝；否则放行并更新时间戳。
- 特点：零存储开销、无线程，纯 O(1) 计算。它与令牌桶（Token Bucket）恰好互为反向：令牌桶是"按恒定速率加令牌、请求来了拿走令牌、桶满则令牌浪费"，漏桶是"请求来就加水、按恒定速率漏掉水、桶满则请求被溢弃"。

两种形态的本质差异：队列式可以缓存并延后请求（延迟换吞吐），时间戳式是立即裁决（溢满即拒，快速失败）。

关键特性与代价：
- 输出速率恒定（强整形）：无论上游怎么突发，流出速率恒为 rate，输出流量曲线近似一条直线，平滑性在四大算法中最好；
- 无突发：绝对不允许瞬时流量穿透，任何超过漏速的流量都必须先在桶内缓冲或被丢弃；
- 代价是延迟：桶内积压的请求必须排队等前面的"漏"完，队列越长等待越久，延迟不可控。

设计哲学：漏桶的设计目标不是"最大化吞吐"，而是"保护下游"。它把"流量管理的确定性"放在第一位——下游永远看到的是一个匀速的输入流，这正是脆弱系统（数据库、第三方 API）最需要的东西。

3. 实践应用（怎么用）

代码示例一：时间戳累加式漏桶（Java）

public class LeakyBucketRateLimiter {
    private final long capacity;   // 桶容量：允许缓冲的最大请求数
    private final double leakRate; // 漏速：每秒漏出（处理）的请求数
    private double waterLevel;     // 当前水位
    private long lastLeakTime;     // 上次漏水时间戳（毫秒）

    public LeakyBucketRateLimiter(long capacity, double leakRate) {
        this.capacity = capacity;
        this.leakRate = leakRate;
        this.waterLevel = 0;
        this.lastLeakTime = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 1. 先按流逝时间"漏水"：漏掉 (now - lastLeakTime) 秒 × 漏速 的水
        double leaked = (now - lastLeakTime) / 1000.0 * leakRate;
        waterLevel = Math.max(0, waterLevel - leaked);
        lastLeakTime = now;

        // 2. 尝试加水（一个请求 = 一滴水）
        if (waterLevel + 1 > capacity) {
            return false;           // 桶已满 → 溢出丢弃（拒绝请求）
        }
        waterLevel += 1;
        return true;                // 放行，等待匀速"漏出"处理
    }
}

// 使用：桶容量 100，漏速 20 请求/秒 → 无论突发多大，输出恒定为 20 req/s
LeakyBucketRateLimiter limiter = new LeakyBucketRateLimiter(100, 20);
if (limiter.tryAcquire()) {
    process(handleRequest());      // 正常处理
} else {
    rejectWith429();               // 返回 429 Too Many Requests
}

代码示例二：队列式漏桶（Java 伪代码）

class LeakyBucketQueue {
    private final BlockingQueue<Runnable> bucket = new LinkedBlockingQueue<>(capacity);
    private final ScheduledExecutorService consumer =
            Executors.newSingleThreadScheduledExecutor();

    public void init(double rate) {
        // 匀速消费：每隔 1/rate 秒从桶里取一个任务执行
        consumer.scheduleAtFixedRate(() -> {
            Runnable task = bucket.poll();
            if (task != null) task.run();
        }, 0, (long) (1000 / rate), TimeUnit.MILLISECONDS);
    }

    public boolean submit(Runnable task) {
        return bucket.offer(task);  // 桶满则 offer 返回 false → 丢弃
    }
}

真实落地案例：
- Nginx limit_req：这是面试中最该说出的落地案例。Nginx 的 ngx_http_limit_req_module 就是漏桶算法实现：limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s; 中 rate 即恒定漏速，limit_req zone=one burst=5; 中 burst 即桶容量，超过 burst 的请求直接返回 503。加 nodelay 参数则让 burst 内请求不排队立即放行（牺牲平滑换取低延迟）。
- QoS 流量整形 / ATM 网络：漏桶最早出自电信网络领域。ATM（异步传输模式，Asynchronous Transfer Mode）网络用它做流量整形与流量合约（Traffic Contract），保证信元（cell）按恒定比特率（CBR，Constant Bit Rate）发送；QoS 中的承诺信息速率（CIR，Committed Information Rate）本质上就是"恒定漏速"。
- 秒杀/抢购排队：秒杀瞬间涌来百万请求，用漏桶把请求匀速灌入处理队列（如 1 万/秒），数据库和下游不被冲垮，用户侧表现为"排队中"。
- 保护下游脆弱系统：上游任意突发，经过漏桶后下游永远看到恒定速率，适合调用有 QPS 上限的第三方 API、写入连接池有限的数据库等场景。

4. 深入思考（注意事项）

队列容量与丢弃策略：桶容量 = 允许的缓冲深度，是"突发容忍度"与"延迟"的旋钮。容量越大，能吞下的突发越多，但排队延迟越久；容量设为 0 时退化为严格限速——凡是超过恒定速率的请求一律拒绝。溢出后的丢弃策略也可以扩展：直接拒绝（429）、静默丢弃、按优先级丢弃、降级返回兜底数据，甚至改为"排队 + 超时"而非丢弃。

满桶时的拒绝语义：漏桶是"被动拒绝"——满了就溢，没有让请求"等下一帧"的窗口概念（除非用阻塞式队列实现）。因此它的拒绝是立即且确定的，天然适配快速失败（Fail Fast）的场景；如果业务允许等待，应选用队列式实现并配合超时与重试。

与滑动窗口 / 令牌桶的组合使用：现实系统很少单用漏桶。常见组合：网关层用令牌桶放行（允许突发、响应快），服务层用漏桶整形（保护下游），两级配合兼顾"用户体验"与"下游安全"；滑动窗口负责总量控制（如每秒总配额），漏桶负责输出速率整形。Guava RateLimiter、Sentinel、Resilience4j 等主流限流组件多以令牌桶或滑动窗口为主，因为漏桶的恒定输出意味着请求延迟不可控，对 API 场景不友好——这个"为什么主流组件不用漏桶"的反问本身就是加分回答。

限流与削峰的区别：限流（Rate Limiting）的语义是"拒绝超出能力的请求"，总量被削减；削峰填谷（Peak Shaving）的语义是"把高峰流量存起来、到低谷再放"，总量不变只是平移。漏桶恰好横跨两者：溢出的部分做限流（丢弃），缓冲的部分做削峰（延后）。更精确地说——队列式漏桶更像削峰，时间戳式漏桶更像限流。能讲出这层区别，说明你真的吃透了它。

答题逻辑框架（按此顺序讲，逻辑闭环）：
1. 一句话定义 + 白板画桶（模型四要素：容量、漏速、恒定输出、溢出丢弃）；
2. 两种实现形态（队列式 vs 时间戳式，点明"令牌桶反向"）；
3. 关键特性与代价（恒定、无突发、延迟）；
4. 与令牌桶对比（这里主动引出对比，是面试官最想听的）；
5. 落地案例（Nginx limit_req、QoS/ATM、秒杀排队）；
6. 收尾升华（容量与延迟权衡、组合使用、限流 vs 削峰）。

重点得分点：
- 说出"流量整形（Traffic Shaping）"这个专业术语——直接拉开档次；
- 主动画出对比矩阵：漏桶=出口限速+无突发+以延迟为代价，令牌桶=入口发牌+可突发+以积压丢弃为代价；
- 明确指出漏桶的代价是延迟，体现你理解权衡而非背概念；
- 举 Nginx limit_req 实例并说出 burst 就是桶容量；
- 说出两种实现形态的差异（队列式可缓冲 vs 时间戳式即决即拒）。

常见误区：
- 把漏桶和令牌桶混为一谈——这是最致命的错误；
- 说"漏桶可以处理突发流量"——恰恰相反，漏桶禁止突发穿透输出；
- 把桶容量和漏速混淆——容量管"能积多少"，速率管"每秒出去多少"；
- 只背概念不画图——漏桶是最具象的算法，画图等于白送分；
- 忽略延迟代价，只说"平滑性好"——面试官一句"那延迟怎么办"就可能卡住。
