如果不同商家可以对同一个商品图进行请求，那么你如何保证不会有两个请求同时去实现缓存的重建？

如果不同商家可以对同一个商品图进行请求，那么你如何保证不会有两个请求同时去实现缓存的重建？

如果不同商家可以对同一个商品图进行请求，那么你如何保证不会有两个请求同时去实现缓存的重建？

🧠 联想记忆法

一句话本质：这道题 = 缓存击穿（Cache Breakdown）的"多人版"——多个商家、多台实例共享同一个商品图 Key，Key 过期瞬间，所有人同时冲去重建缓存。

口诀记忆："一锁、二查、三单飞，逻辑过期异步刷"
- 一锁：按 Key 粒度抢分布式锁（SET NX EX），保证同一时刻只有一个重建者；
- 二查：拿到锁后二次检查（Double Check）缓存，防止重复重建；
- 三单飞：SingleFlight 请求合并，把 N 个查询合并成 1 个；
- 逻辑过期异步刷：值里带过期时间戳，过期了返回旧值、后台异步重建。

场景类比：像只有一个坑位的公共厕所——第一个进去的人"冲水重建"（查 DB 写缓存），后面的人排队，进去前先看一眼坑干不干净（double check），等不了的人去隔壁商场解决（返回旧值/降级值）。

简历锚点：这道题我熟——之前做秒杀扣减时用过 Redisson 分布式锁和 Lua 原子脚本，扣库存的 compareAndSet 思路跟"比对 token 再释放锁"一模一样；多实例路由锁也让我养成了"凡是跨实例互斥，先想 Redis"的条件反射。这些经验直接可复用。

📖 深度解答

1. 核心概念

先定性：这不是普通的缓存击穿，而是它的升级版。缓存击穿指单个热点 Key 过期瞬间，大量并发请求同时穿透到数据库（Database）；而本题的关键在于多个商家共享同一个商品图 Key——也就是多个不同的调用方（可能来自不同服务、不同实例）同时未命中同一个 Key，每一个都认为自己应该去重建。

升级在哪？两点：
1. 并发来源不可控：单个商家的流量可能不大，但 N 个商家叠加、再加上平台本身的展示流量，同一毫秒内打到同一个 Key 的请求数可能非常大；
2. 没有任何协调机制：各商家请求之间天然无感知，谁都不会等谁，结果就是同一份商品图被重复查询数据库、重复写入缓存，数据库被打爆，这就是缓存击穿升级为缓存重建风暴的过程。

所以题目的目标非常明确：保证同一个 Key 在同一时刻只有一个重建者。更完整的诉求是：重建成本（查 DB）只付一次，其他请求要么等待、要么拿到旧值/降级值，且不能造成请求堆积。

2. 底层原理

2.1 为什么必须用分布式锁（Distributed Lock）

多商家请求落在不同实例上，JVM 内的 synchronized / ReentrantLock 只对单进程生效，无法跨进程互斥——这就是"本地锁解决不了分布式问题"。Redis 分布式锁是业界标准做法，因为它简单、高性能、可用性高。

2.2 SET NX EX 与锁的原子性

抢锁用一条原子命令：

SET lock:goods:img:1001 <token> NX EX 30
  • NX（Not eXists）：Key 不存在才设置成功，保证同一时刻只有一个请求拿到锁。关键是它把"判断存在 + 写入"合并成一步，避免了"先 GET 再 SET"两步操作之间的竞态（Race Condition）；
  • EX：设置过期时间（TTL），防止持锁进程宕机导致死锁；
  • value 必须是唯一标识（如 UUID 或机器+线程 ID），而不是固定值——这是后面安全释放锁的前提。

释放锁必须用 Lua 脚本保证"比对 + 删除"的原子性：

-- 只有 value 是自己持有的 token 时才删除，防止锁过期后误删别人新抢的锁
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

为什么需要它？如果业务执行时间超过了锁的 TTL，锁自动释放，另一个请求抢到锁开始重建；此时第一个请求执行完毕去 DEL，就会误删第二个请求的锁，导致锁完全失效。带 token 的 Lua 比对删除正是解决这个问题。

2.3 Redisson 看门狗（Watchdog）

上面的"业务超时导致锁过期"问题，Redisson 用看门狗机制解决：加锁时若不显式指定 leaseTime，默认 30 秒，后台一个定时任务每 10 秒（leaseTime 的 1/3） 自动续期一次，只要业务没执行完，锁就不会过期；业务执行完释放锁，看门狗随之取消。这就是"锁的有效期跟随业务执行时间"，从根上避免"锁过期但业务还在跑"造成的并发重建。

2.4 锁粒度（Lock Granularity）按 Key

锁的粒度要按业务 Key 划分：lock:goods:img:{goodsId}。不同商品图用不同的锁互不干扰；如果全局一把锁，一个慢重建会阻塞所有商品的请求，锁的粒度越细，并发能力越高。

2.5 加锁后二次检查（Double Check）

拿到锁后不能直接查库，要再读一次缓存：因为在你抢锁的间隙，可能已经有其他请求（比如没抢锁但恰好先重建完的实例，或抢锁失败但通过其他路径写入了缓存）把缓存重建好了。这就是单机懒加载中的 Double-Checked Locking 在分布式场景的翻版——锁只是"互斥保证"，缓存"是否为空"要以最新读取为准，避免重复查库。

3. 实践应用

3.1 标准互斥重建流程（伪代码）

String key = "goods:img:" + goodsId;
String value = redis.get(key);
if (value != null) return value;                       // ① 缓存命中直接返回

String lockKey = "lock:" + key;                        // ② 锁粒度 = 业务 Key
String token = UUID.randomUUID().toString();
boolean locked = redis.setIfAbsent(lockKey, token, 30, TimeUnit.SECONDS); // SET NX EX
if (locked) {
    try {
        value = redis.get(key);                        // ③ double check：二次检查
        if (value != null) return value;
        value = queryDB(goodsId);                      // ④ 只有这里会查库
        redis.set(key, value, randomTTL());            // 随机 TTL，防雪崩
        return value;
    } finally {
        releaseLock(lockKey, token);                   // ⑤ Lua 原子释放（比对 token）
    }
}
// ⑥ 拿不到锁：走等待 / 旧值 / 降级策略
return fallback(goodsId);

3.2 拿不到锁的请求怎么办——防止请求堆积

互斥只解决"不重复重建"，若所有失败请求都原地自旋等待，N 个请求会堆积成阻塞风暴，把击穿变成击垮。三种处理：

  1. 限次等待重试：短暂 sleep（或订阅 Redis 的 Key 失效通知/发布订阅）后重新读缓存，限制重试次数与总耗时；
  2. 返回旧值：容忍短暂不一致的场景，直接返回上次的过期数据（调用方自行容错），这是体验最优的方案；
  3. 降级值：返回统一占位图（如"图片加载中"），配合日志告警。

3.3 SingleFlight：从"互斥"到"合并"

互斥锁是"阻塞其他请求"，SingleFlight（请求合并）是"合并其他请求"：同一 Key 的并发请求只放行一个去查库，其余请求 await 同一个 Future（Java 里可用 ConcurrentHashMap<String, CompletableFuture> 存进行中的任务，或直接用 Guava 的 Striped 锁 + 共享 Future）。JVM 内版本能解决单实例内的重复查询；多实例下需要分布式版 SingleFlight——Redis 锁 + 等待机制（锁内请求完成后写入缓存并发布通知，其他实例的请求收到通知后直接读缓存，而不是各自自旋），本质是"分布式锁 + 通知合并"的组合。

3.4 其他方案：从"重建时机"上绕开问题

  • 逻辑过期 + 异步重建（Lazy Expire）：缓存不设物理 TTL，value 里带一个逻辑过期时间戳；请求发现逻辑过期时，先返回旧数据，同时投递一条消息到消息队列（Message Queue）触发异步重建（或直接由后台线程重建，DB 双写）。读写完全解耦，用户体验最好，适合"读多写少 + 容忍短暂旧数据"的场景（商品图完美匹配）；
  • 软过期（Soft Expiry）：值里带过期时间，过期后仍返回旧值、异步刷新，是逻辑过期的简化版；
  • 永不过期 + 后台刷新：缓存不设 TTL，由定时任务或后台线程周期性刷新热点数据，甚至"临近过期提前刷新"，把击穿消灭在发生之前；
  • 布隆过滤器 / 多级缓存兜底：布隆过滤器（Bloom Filter）主要防缓存穿透（不存在的 Key 全部放行到 DB），可与本地缓存（Caffeine）+ Redis 多级组合：每个实例先命中本地缓存，只有本地未命中才打到 Redis，进一步削峰，DB 流量大幅下降。

4. 深入思考

  • 锁过期了还是并发重建怎么办：加锁方有看门狗续期；更进一步的兜底思路是"重建允许幂等"——因为重建结果来自同一份 DB 数据，即使极端情况下两个请求并发重建，结果是一致的，最坏只是多查了一次库，不会产生脏数据，属于可接受的兜底；
  • 热点 Key 倾斜（Hot Key Skew）：商品图是超大热点，所有商家都抢同一把锁，锁本身会成为单点瓶颈。缓解手段：随机 TTL（重建时给过期时间加随机偏移，避免整点集体过期）、本地缓存限流（每个实例先查 Caffeine 本地缓存，把打向 Redis 的流量先削峰一层）；
  • 重建失败怎么办：try/finally 保证锁一定释放；重建失败不要写缓存，直接返回降级值，避免把坏值固化进缓存；重试要设上限与退避（Backoff）；
  • 与缓存一致性延伸：写 DB 与写缓存顺序、双写一致性问题（Cache-Aside 模式的失效策略）是这道题的常见延伸追问，答完主流程可以主动带出。

🗺️ 回答思路

答题逻辑框架（建议总时长 3~4 分钟）

  1. 定性（20~30 秒）：一句话点题——"这是多个调用方共享同一个 Key 的缓存击穿升级版，核心目标是同一 Key 同时只有一个重建者，其他请求等待或降级，且不能堆积"；
  2. 主方案（1.5 分钟）：分布式锁三步走——SET NX EX 抢锁（讲原子性）→ 锁粒度按 Key → 加锁后 double check → 重建 → Lua 比对 token 释放；顺带讲 Redisson 看门狗续期解决"锁过期"；
  3. 改进演进（1 分钟）：拿不到锁的请求怎么处理（限次等待/返回旧值/降级值防堆积）→ SingleFlight 请求合并，JVM 内 Future 合并 + 分布式版 Redis 锁 + 通知；
  4. 方案对比与兜底（1 分钟）：逻辑过期 + 异步重建（MQ + 返回旧值）、软过期、永不过期 + 后台刷新、布隆过滤 + 多级缓存；异常兜底：随机 TTL、本地缓存限流、重建失败不写缓存；
  5. 简历收尾（20 秒）："这套互斥思路和我用 Redisson 做分布式锁、Lua 脚本做秒杀扣减时的原子性设计是一脉相承的"。

重点得分点

  • 说出 NX 的原子性和为什么释放锁要用 Lua + token 比对（防误删）；
  • 说出加锁后 double check（很多人漏这一步）；
  • 说出锁粒度按业务 Key；
  • 说出看门狗机制（30s 默认、每 10s 续期），体现用过 Redisson；
  • 说出拿不到锁的降级策略，主动点出"防止请求堆积"这个隐藏考点；
  • 能对比 互斥重建 vs SingleFlight vs 逻辑过期 的适用场景（强一致 vs 短暂旧数据可容忍）；
  • 主动聊热点 Key 倾斜与随机 TTL，体现工程思维。

常见误区

  • ❌ 只说 JVM 锁（synchronized）：跨实例无效，必须点明"这是分布式问题"；
  • ❌ 加锁后直接查库、不做 double check：重复查库的风险场景没说清；
  • ❌ 释放锁直接 del 不比对 token：锁过期后误删他人锁，等于锁失效；
  • ❌ 所有抢锁失败请求原地自旋等待：造成请求堆积，把击穿打成击垮；
  • ❌ 只答"加锁"一个方案就结束：缺少改进（SingleFlight、逻辑过期）与兜底（随机 TTL、降级），显得没有架构纵深。
