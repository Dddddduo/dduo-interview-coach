like 查询会不会导致索引失效？

like 查询会不会导致索引失效？

like 查询会不会导致索引失效？

🧠 联想记忆法

一句话口诀：「百分号贴左边，索引能跑；百分号在开头，索引报废。」

联想场景一（排队点名）：想象全校学生按姓名字典序排成一列长队——这就是 B+ 树叶子节点的有序链表。
- LIKE '张%'（前缀匹配）：像教官喊"姓张的往前一步"。队伍有序，教官两步定位到第一个"张"，然后顺着队伍把姓张的一路带走——这就是范围扫描，走索引。
- LIKE '%张'（后缀匹配）：像教官喊"名字最后一个字是张的出来"。姓什么不知道，教官只能从队头到队尾挨个看名字——这就是全表扫描。

联想场景二（新华字典）：查"语"字直接翻到拼音 y 打头的页码（前缀匹配，可用）；只记得字里有个"吾"、不知道声母，只能整本字典从头翻（后缀匹配，失效）。

记忆公式与三招救场：
- % 在前 → 失效；% 在后 → 可用；% 在中 → 失效，上"歪招"。
- 三招打包记：反（REVERSE 反转，后缀变前缀）、倒（倒排索引/全文索引）、搬（搬到 ES）。

五字诀：前缀走范围，后缀扫全表，中缀上全文，特技是反转。

📖 深度解答

1. 核心概念

先纠正一个误区：索引失效（Index Invalidation）不是索引被"删除"或"损坏"，而是 MySQL 优化器（Optimizer） 在生成执行计划（Execution Plan）时，判断无法利用索引的有序性来缩小扫描范围，于是退而选择全表扫描（Full Table Scan）。所以"LIKE 会不会导致索引失效"的答案是：不能一概而论，关键看通配符 % 的位置。

分三种情况（这是本题的灵魂）：

LIKE 写法 匹配方向 索引使用 原因
LIKE 'abc%' 前缀匹配 ✅ 可用（range 范围扫描） B+ 树按字典序排列，可定位起点
LIKE '%abc' 后缀匹配 ❌ 失效（全表扫描 ALL） 首字符不定，无起点可定位
LIKE '%abc%' 中间匹配 ❌ 失效（全表扫描 ALL） 同后缀，需换全文索引/ES 等方案

补充细节：LIKE 'abc%def'（前缀固定）同样可用；单字符通配符 _ 出现在前缀之后不影响（如 'ab_c%' 前两位固定，可先按 'ab' 范围扫再过滤）；但 LIKE '_bc%' 第一个字符就不确定，无法用索引。另外要记住一条钥匙级的等价关系：LIKE 'abc%' 本质上等价于范围条件 col >= 'abc' AND col < 'abd'。

2. 底层原理

（1）B+ 树的"有序性"是索引可用的根基

InnoDB 的二级索引（Secondary Index）是一棵 B+ 树（B+ Tree）：叶子节点按索引列的值升序排列，且叶子节点之间通过双向链表（Doubly Linked List）串联，形成一条全局有序的链表。索引查找的本质就是"有序查找"：从根节点沿指针二分下钻（利用节点内部键值有序），O(log n) 定位到目标叶子，再在叶子内二分定位具体记录。

（2）前缀匹配的本质是范围查询（Range Query）

WHERE name LIKE 'abc%' 被优化器解析为半开区间 [abc, abd) 的范围条件，执行分两步：
- 定位起点：从 B+ 树根节点二分下钻，找到第一个以 'abc' 开头的记录；
- 顺序扫描：顺着叶子节点的有序链表逐条读取，只要仍以 'abc' 开头就命中，遇到第一个不匹配的记录（下一个键值已是 'abd...'）立即停止。

整个过程只扫描区间内的记录，天然剪枝掉大量无关数据，所以 EXPLAIN 中 type=range。为什么可行？因为字符按字典序连续排列，前缀相同的记录在物理上必然聚簇在一起——这是前缀匹配能走索引的根本原因。

（3）后缀匹配为什么等于全表扫描

WHERE name LIKE '%abc'：末尾是 'abc'，但第一个字符任意。以 'abc' 结尾的字符串在有序链表上是离散散布的（比如 "xabc"、"zzabc"、"A123abc" 彼此毫无相邻关系），B+ 树无法给出明确起点，二分定位无从谈起，更不可能利用有序性剪枝。优化器只能从第一条到最后一条逐行读取判断，即全表扫描（type=ALL）。%abc% 中间匹配同理，连"前缀区间"都不存在，是后缀问题的加强版。

（4）一个容易被误解的点：全表扫描不一定"慢"。优化器是基于代价的（Cost-Based Optimizer），当表很小或索引选择度极低时，走全表反而更快。所以更准确的说法是：不是优化器"故意不用"，而是后缀匹配客观上没有任何手段能利用索引的有序性。

3. 实践应用（正确写法与优化手段）

（1）前缀索引（Prefix Index）——减小索引体积，服务右模糊

列很长但只需前缀匹配时，可以只对前 n 个字符建索引：

ALTER TABLE user ADD INDEX idx_name (name(10));

n 取多长？用选择性（Selectivity）量化——不同值个数占总行数的比例，越接近 1 越好（经验值 ≥ 0.9）：

SELECT COUNT(DISTINCT LEFT(name, 5))  / COUNT(*) AS sel_5,
       COUNT(DISTINCT LEFT(name, 10)) / COUNT(*) AS sel_10
FROM user;

注意代价：前缀索引存的是截断值，不能用于 ORDER BY / GROUP BY，也无法构成覆盖索引（见下）。

（2）覆盖索引（Covering Index）——避免回表

ALTER TABLE user ADD INDEX idx_name_status (name, status);
SELECT id, name, status FROM user WHERE name LIKE 'abc%';

此时 EXPLAIN 的 Extra 为 Using index——查询所需列全在索引中，无需回表（Table Lookup），扫描成本进一步降低。

（3）生成列 + REVERSE 反转——把后缀匹配"变"成前缀匹配（5.7 起）

ALTER TABLE user
  ADD COLUMN name_rev VARCHAR(50)
  GENERATED ALWAYS AS (REVERSE(name)) STORED,
  ADD INDEX idx_name_rev (name_rev);

-- 原需求"查后缀为 abc 的记录"：LIKE '%abc' → 反转后变前缀 'cba%'
SELECT * FROM user WHERE name_rev LIKE CONCAT(REVERSE('abc'), '%');

写入时生成列（Generated Column）自动计算并同步进索引，查询走 idx_name_rev 的范围扫描，空间换时间，适合"后缀模糊"高频的存量表。MySQL 8.0 更进一步支持函数索引（Functional Index）：CREATE INDEX idx ON user ((REVERSE(name)))。

（4）全文索引（Fulltext Index）与倒排索引（Inverted Index）——应对 %xx% 中缀

%xx% 在 LIKE 语义下无解，但业务上的"包含关键词"通常是分词检索。MySQL 5.7.6+ 内置 ngram 分词器，中文可用：

ALTER TABLE article ADD FULLTEXT INDEX ft_title (title) WITH PARSER ngram;
SELECT * FROM article
WHERE MATCH(title) AGAINST('+MySQL +索引' IN BOOLEAN MODE);

全文索引底层是倒排索引（Inverted Index）——"单词 → 文档位置列表"的映射，与 B+ 树"有序键值 → 范围"的思路完全两回事，天然支持"包含/不包含"匹配。

（5）实际场景取舍：搜索功能该用 LIKE 还是 ES？

  • 简单右模糊、低频、数据量可控 → LIKE 'xx%' + 普通/前缀/覆盖索引即可，成本最低；
  • 中缀模糊、分词、相关性排序、高并发 → Elasticsearch（基于 Lucene 倒排索引）才是正解，MySQL 全文索引只适合中量级兜底；
  • 架构上的职责分离：DB 管精确匹配与范围过滤，ES 管模糊分词，不要互相绑架。

（6）EXPLAIN 实证：type 的差别

EXPLAIN SELECT * FROM user WHERE name LIKE '张%';

+----+-------------+-------+-------+---------------+----------+---------+------+------+--------------------------+
| id | select_type | table | type  | possible_keys | key      | key_len | ref  | rows | Extra                    |
+----+-------------+-------+-------+---------------+----------+---------+------+------+--------------------------+
|  1 | SIMPLE      | user  | range | idx_name      | idx_name | 153     | NULL | 120  | Using index condition    |
+----+-------------+-------+-------+---------------+----------+---------+------+------+--------------------------+

type=range：走索引的范围扫描；Using index condition 是 ICP（Index Condition Pushdown，索引条件下推，5.6+），把 LIKE 过滤下推到存储引擎层，减少回表——这是加分细节。

EXPLAIN SELECT * FROM user WHERE name LIKE '%张';

+----+-------------+-------+------+---------------+------+---------+------+--------+----------+
| id | select_type | table | type | possible_keys | key  | key_len | ref  | rows   | Extra    |
+----+-------------+-------+------+---------------+------+---------+------+--------+----------+
|  1 | SIMPLE      | user  | ALL  | NULL          | NULL | NULL    | NULL | 100000 | Using where |
+----+-------------+-------+------+---------------+------+---------+------+--------+----------+

type=ALL：全表扫描，possible_keys 为 NULL——优化器判定这些索引都无力参与。%张% 同理。

EXPLAIN SELECT id, name FROM user WHERE name LIKE '张%';

+----+-------------+-------+-------+---------------+-----------+---------+------+------+-------------+
| id | select_type | table | type  | possible_keys | key       | key_len | ref  | rows | Extra       |
+----+-------------+-------+-------+---------------+-----------+---------+------+------+-------------+
|  1 | SIMPLE      | user  | range | idx_name      | idx_name  | 153     | NULL | 120  | Using index |
+----+-------------+-------+-------+---------------+-----------+---------+------+------+-------------+

Using index：覆盖索引，免回表。补充一个小知识：%xx% 的查询若恰好只涉及索引列，优化器可能退而求其次走全索引扫描（type=index）——遍历整个索引而非整张表，比 ALL 略好，但本质仍是全扫。

简历可引用的实战案例：线上某搜索接口慢查询 3s+，EXPLAIN 定位到 type=ALL、rows 达 500 万 → 应用层把 LIKE '%关键词' 改写为生成列反转索引、高频字段加前缀索引 → 单次查询降到 200ms 以内。

4. 深入思考

（1）字符集与排序规则（Collation）对 LIKE 的影响

LIKE 的匹配语义由列的排序规则（Collation）决定：
- utf8mb4_general_ci / utf8mb4_0900_ai_ci（MySQL 8.0 默认）不区分大小写：LIKE 'a%' 会命中 'A' 开头的行，扫描区间天然更大；
- utf8mb4_bin / binary 区分大小写：LIKE 'a%' 只命中小写 'a'，区间更精确；
- 尾部空格（PAD SPACE / NO PAD）与重音（ai 不区分重音）的处理也随 collation 变化，'abc' 与 'abc ' 是否相等要看排序规则。

这带来一个工程启示：同一 SQL 在测试库（如 latin1）和生产库（utf8mb4）可能生成不同执行计划，环境对齐是慢查询排查的第一课。

（2）函数包裹必然失效，但有新解法

WHERE LEFT(name,3) = 'abc' 对列套了函数，无法利用普通索引（索引里存的是原值）。MySQL 8.0 函数索引可以解决：CREATE INDEX idx ON user ((LEFT(name, 3)))。

（3）慢查询排查的标准链路

开启慢查询日志（slow_query_log）→ 捞取超阈值 SQL → EXPLAIN 看 type / key / rows / Extra 四要素 → 按"右模糊优先、中缀后缀上反转/全文/ES"对症下药。这也是简历里"EXPLAIN 优化 3s+ → 200ms"的完整叙事。

（4）面试延伸弹药

  • 倒排索引 vs B+ 树索引：一个是"单词→位置"的映射，一个是"有序键值→范围"的排序结构；
  • ngram 分词与中文全文检索；
  • ES 的 match/term 与数据库 LIKE 的定位差异，为什么搜索引擎不放在数据库里。

🗺️ 回答思路

答题逻辑框架（总分总，3~5 分钟）

  1. 定调（30 秒）：一句话——"不能一概而论，关键看通配符位置"，立刻给出三行对照表；
  2. 分情况（核心，占一半时间）：'xx%' 可用 → 直接抛原理"它等价于范围查询"；'%xx' 与 '%xx%' 失效 → 讲清楚为什么（无起点、无法利用有序性）；
  3. 上证据：给两条 EXPLAIN 输出，对比 type 从 range 到 ALL，顺带解释 ICP 和 Using index；
  4. 给方案：前缀索引（含选择性公式）→ 覆盖索引 → 生成列 + REVERSE → 全文索引/ES → 场景取舍；
  5. 升华收尾：collation 影响 + 慢查询排查案例，暗示"我实际解决过线上问题"。

重点得分点（按分值排序）

  • 主动说出 LIKE 'abc%' ≡ col >= 'abc' AND col < 'abd'（最亮眼的洞察，直接体现深度）；
  • 用 B+ 树叶子有序链表解释"二分定位起点 + 链表顺序扫描"，并点明后缀匹配在链表上离散分布、无起点可言；
  • 说出前缀索引选择性公式 COUNT(DISTINCT LEFT(col,n)) / COUNT(*)，且知道前缀索引的代价（不能用于覆盖索引/ORDER BY）；
  • 提到 5.7 生成列 + REVERSE、8.0 函数索引、ngram 全文索引这些"超纲但真实"的方案；
  • 结尾给真实数据（3s+ → 200ms），增加可信度。

常见误区

  • 误区 1：答"LIKE 会让索引失效"——一棒子打死，右模糊明明可用，这是送分题变送命题；
  • 误区 2：只背结论不解释原理——面试官追问"为什么前缀行、后缀不行"就露馅；
  • 误区 3：以为"加了索引就不会失效"——%abc% 加再多普通索引也没用；
  • 误区 4：以为覆盖索引能救 %abc%——它只能免回表，救不了全扫；
  • 误区 5：一上来就甩 ES——要讲清 LIKE 与 ES 的适用边界和成本差异，体现工程判断力；
  • 误区 6：忽略 collation——"测试环境能用、生产走全表"这类环境差异是资深工程师才提的点。

时间分配建议（按 4 分钟回答计）

  • 0~30s：定调 + 三种情况对照表；
  • 30s~2min：原理深挖（B+ 树、范围查询本质、后缀为何全扫）——重头戏，宁可多花时间；
  • 2~3min：优化手段 + EXPLAIN 证据（挑 1~2 条输出讲透即可，不必全念）；
  • 3~4min：场景取舍 + 简历案例 + 预留追问防御。
