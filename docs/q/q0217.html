开场总纲（30 秒定调）

面试官好，我按"一个主战场 + 两个副战场 + 两个补充项目"讲。主战场是快手 OrbitQA 星轨平台，我作为负责人从 0 到 1 建设了支付测试的 AI 交付平台；副战场是慧策的电商中台后端（大促稳定性）和颛知的全栈项目（性能优化基本功）；补充是数字藏品平台的分布式全家桶实验和 BHU-ACM 实验室官网这个线上业务系统。每个项目我都准备讲清楚"遇到了什么问题、怎么分析、怎么解决、怎么验证"。

第一战场（主战场）：OrbitQA 星轨平台 — 快手·电商技术部·支付质量中心

背景一句话：在快手电商支付中台的测试场景下，我负责从 0 到 1 建设 OrbitQA——一个基于 Spring AI + Reactor + PostgreSQL pgvector + Redis + MCP Protocol + Harness Engineering 的支付测试 AI 交付平台，同时负责支付渠道模块金融交换部分的测试开发（C 端全流程测试和接口自动化仓库：广东国补、渠道 KBF 通道改造、快手支付支持华兴存管行等）。

我的角色：项目负责人，从架构设计、模块划分到落地交付全链路负责。职责内还有"从 0 到 1 的 AI 项目专项建设"，即平台本身。

核心技术难点（4 个）：
1. 任务异构与编排：支付测试任务拆分粒度不一，单 Agent 全流程执行会上下文爆炸、工具调用串台；
2. 多实例路由的并发安全：长任务跑 15 分钟以上，分布式锁存在过期竞态；
3. RAG 召回质量：测试文档、用例库检索不准会直接引发 Agent 幻觉；
4. 连接稳定性：会话/工具连接断开会打断长任务，需要高可用保障。

量化成果：C 端白盒测试提效 70%；RAG 召回率提升 55%；多实例路由锁下长任务 15min+ 零过期；心跳+CAS 重连+全链路引用刷新，连接恢复 < 15s；平台可用率 99%。

被追问最狠的问题 1：为什么用"PMO 编排 + 域 Agent 执行"双层架构，而不是单个 Agent 端到端干完？

  • 遇到问题：【设计思路】初版我尝试单 Agent 承接整条测试交付链路，任务一复杂就暴露两个问题：一是上下文窗口被大段测试指令、用例、平台信息撑爆，Agent 开始"遗忘"早期约束；二是工具调用串台——支付、售后、风控各域的工具互相干扰，一步错就要整体重来，失败无法定位。
  • 分析：我把流程拆开看，发现"编排决策"和"工具执行"是两种完全不同的负载：编排是决策密集、对全局上下文敏感；执行是工具密集、对单点正确性敏感。两者耦合在一个 Agent 里，容错粒度粗到"全量重放"，而支付测试的成本等不起。
  • 方案：提出 PMO 编排与域 Agent 执行分离的双层架构——PMO 层负责把大任务拆分为子任务、维护任务依赖关系并分发；各域 Agent 基于 Spring AI 实现 ReAct 循环，自主调用工具（经 MCP Protocol 接入）执行流水线；执行结果回传 PMO 校验、合并、交付。同时借助 Harness Engineering 思想，从五个模块完善工程基础设施（任务编排、执行引擎、工具注册、RAG、可观测性【设计思路：五模块即工程基建的划分】），把平台从"调接口的脚本"升级成"有工程基座的交付系统"。
  • 验证：拆分后失败粒度为"单个域 Agent、单个子任务"，可重试、可重放、可观测；整体交付成功率提升、白盒测试提效 70%（简历数据，平台上线后的效率指标）。

被追问最狠的问题 2：分布式锁怎么防过期？5min 续期 TTL + 归属校验具体怎么落地？

  • 遇到问题：平台多实例部署，同一个测试任务可能被多个实例重复领取执行；任务时长 15 分钟以上，固定 TTL 的锁必然过期，锁一过期其他实例就能抢入，造成重复执行、重复扣资源、结果互相覆盖。
  • 分析：我把问题抽象成"锁不止是互斥，更是资源归属"。互斥解决"同一时刻只有一个执行者"，归属解决"这个执行者到底还是不是我"——两件事要分开设计。
  • 方案（简历原文为"两层互斥，Pub/Sub 广播 + dispose() 释放连接，5min 续期 TTL + 归属校验"）：
  • 第一层互斥：抢锁保证同一任务同一实例执行；第二层互斥：执行过程中的关键资源（如 RAG 索引写、工具会话）再叠加细粒度互斥，避免跨任务踩踏。
  • 锁等待用 Redis Pub/Sub 广播锁释放事件唤醒等待方，避免轮询空转，等待方收到广播后主动 dispose() 释放连接，不长期占用资源【设计思路：这是对"dispose() 释放连接"的落地解释】。
  • 持锁实例周期性续期（TTL 5 分钟、续期窗口内刷新），续期失败即自认为失锁、主动释放并中止任务，不产生"孤儿执行"。
  • 每步执行前做归属校验：比对当前锁持有者标识与自身标识，不一致立即停手，防止"已经过期的我"继续写数据。
  • 验证：长任务 15min+ 零过期（简历数据）；【设计思路】我压测过断网、GC 停顿、实例宕机三类场景，均未出现双写与重复执行。

被追问最狠的问题 3：召回率提升 55% 是怎么测出来的？

  • 遇到问题：【设计思路】早期 RAG 直接整文档入库、单 Query 检索，长文档被硬切导致语义割裂，同义词/口语化提问召回不到正确用例，Agent 拿错资料就答错。
  • 分析：召回劣化的三个来源——切片破坏了语义边界；Query 与库内文本表达方式不一致；单一检索策略没有多样性。
  • 方案（简历原文）：切分策略改为段落 500 字符 + 50 字符重叠切分，保住语义连续性；PgVector 余弦相似度检索；Query 侧做压缩重写 + 多查询扩展，把口语化、长 Query 改写成多个检索友好的子查询，多路召回再融合。
  • 验证：离线构建评测集（从真实测试文档与用例中抽样构造"问题-标准答案对"【设计思路】，标注 recall@k 对比新旧管线），新管线召回率提升 55%（简历数据）；在线再通过 Agent 最终交付结果抽检确认无幻觉回归。

被追问最狠的问题 4（追加）：可用率 99% 和连接恢复 < 15s 怎么做到的？

  • 遇到问题：长任务执行中 MCP 工具连接、数据库连接偶发断线，断线后重连若重复拉起会造成资源竞态。
  • 方案：心跳探活定期确认连接存活；断线后通过 CAS 保证重连幂等（只有一个线程能发起重连）；重连成功后做全链路引用刷新——任务上下文、工具句柄、缓存引用全部指向新连接，避免旧引用写死数据。
  • 验证：故障注入下连接恢复 < 15s，平台可用率 99%（简历数据）。

第二战场（副战场）：慧策（掌上先机）— 旺店通业务中台 · Java 后端

背景一句话：面向电商商家（企业版/旗舰版）的业务中台，我负责订单抓单、物流并发同步、退款主子单下载、库存同步，以及招商银行、微赞、快手等平台客户端授权对接，并承接了 2025 双十一大促预上线前的代码问题排查。

我的角色：Java 后端研发工程师，模块开发 + 大促稳定性专项。

核心技术难点（3 个）：① 大促瞬时抓单量冲击；② 序列化相关 OOM；③ 多平台授权对接差异与 MapStruct 字段映射的准确性。

量化成果：成功排查并解决双十一预上线隐患（阻塞与 OOM 两类问题），保障大促上线。

被追问最狠的问题 1：双十一一次性抓单量过大导致系统阻塞，怎么排查的？

  • 遇到问题：双十一预上线前的预演/压测阶段，订单模块出现明显阻塞：抓单接口响应飙升，线程池打满，后续请求排队。
  • 分析：定位到一次性抓单场景（对接 bilibili 会员购）。该平台大促瞬时推送量极大，抓单逻辑按订单号批量写库，单次任务量远超系统承载：数据库连接池被占满、核心线程池全部被占、下游依赖被拖垮——这是典型的"大任务独占 + 无背压"问题。
  • 方案：【设计思路】（简历只记载问题排查，修复方案为我的推断设计）将大批量抓单按批拆解：固定批大小分批抓取、分批写库，任务间留出并发窗口；对抓单接口增加限流熔断保护，超量直接排队而非打满；必要时引入异步削峰，把抓单请求放入队列由消费端按速率处理；线程池参数按压测数据调优并配置合理拒绝策略。
  • 验证：压测下阻塞消失、吞吐回到预期，预上线风险关闭（简历原文：排查出问题；修复效果为大促保障设计思路）。

被追问最狠的问题 2：多款序列化产品导致上线 OOM 是怎么回事？

  • 遇到问题：上线后出现 OOM（堆内存溢出），服务重启后复现。
  • 分析：根因与序列化相关——系统中存在多款/多版本序列化实现共存（如多个 JSON 序列化框架、缓存序列化协议不统一），对象在序列化/反序列化过程中产生额外的大对象缓存与重复对象图，内存被无效占用膨胀直至溢出。
  • 方案：【设计思路】统一序列化入口与协议（对外统一、缓存统一）；对序列化对象做大小/深度限制，避免超大对象图和循环引用；排查常驻缓存中对象的生命周期，防止"死数据"滞留；上线前增加内存压测与堆快照检查。
  • 验证：复现 OOM 抓取 heap dump 确认根因，修复后压测不再溢出（排查结论为简历事实，具体手段为设计思路）。

被追问最狠的问题 3：并发同步物流怎么保证不丢不重？

  • 方案：【设计思路】物流同步按"平台+运单号"建立幂等键，入库以幂等键做唯一约束防重；状态更新走事务 + 状态机，只允许合法状态迁移（如"已发货→运输中→已签收"），非法迁移直接拒绝；并发写冲突靠版本号/条件更新兜底。MapStruct 做表字段映射，减少手写转换代码出错。

第三战场（副战场）：颛知网络 — 企业级 ERP/OA/CRM · 全栈

背景一句话：电商类企业级 ERP/OA/CRM 系统模块开发，我负责后端分页与数据库性能优化、前端 React 重构。

我的角色：全栈开发工程师，覆盖后端性能、数据库、前端工程化。

核心技术难点（2 个）：① 前端内存分页导致页面卡死；② 慢查询拖垮核心列表接口。

量化成果：慢查询响应从 3s+ 降至 200ms 以内；React 重构后单元测试覆盖率 > 85%。

被追问最狠的问题：3s+ 到 200ms 以内是怎么一步步做的？

  • 遇到问题：核心列表接口在数据量上来后响应 3 秒以上，用户体感卡顿。
  • 分析：用 EXPLAIN 分析查询计划，发现三类问题：连接查询顺序不合理导致大表被先扫描、关键过滤字段无索引导致全表扫描、查询返回列过多导致回表严重。
  • 方案：优化连接查询逻辑（小表驱动大表、减少不必要的连接）；针对高频过滤字段建复合索引、调整已有索引结构减少回表；配合 PageHelper 逻辑分页解决前端一次性加载全量数据内存分页卡死的问题（简历原文）。
  • 验证：同一接口压测，慢查询响应时间从 3s+ 降至 200ms 以内（简历数据）；前端侧 React 重构（单向数据流 + 函数式 TypeScript）后单元测试覆盖率 > 85%（简历数据），保证重构无回归。

第四战场（补充）：数字藏品电商平台 — 省级实验室项目

背景一句话：Spring Cloud Alibaba 全家桶的分布式电商平台，在 32G 内存 Linux 虚拟机上完成了登录、管理端、下单秒杀、监控报警全链路中间件试验（简历原文）。

我的角色：后端开发，负责秒杀、缓存、分库分表、关单等核心链路。

核心技术难点（4 个）：① 秒杀超卖；② 关单性能；③ 热点数据访问；④ 中间件源码级兼容问题（Canal 同步时间转换异常、SnakeYAML 兼容问题）。

量化成果：关单性能从 10 单/s 优化到 50 单/s；热点藏品缓存后接口 RT 从 700ms 提升到 50ms。

被追问最狠的问题 1：秒杀怎么保证不超卖？

  • 方案（简历原文 + 设计思路）：
  • 扣减用 Lua + Redis 原子操作：整个"查库存-扣减"在 Lua 脚本内原子完成，杜绝并发下查改写分离的超卖窗口；
  • InventoryHint 热点扣减：把单一热点库存 key 打散成多个小分片（如 N 个 hint 子 key），并发压力均摊，避免单 key 争抢拖垮 Redis【设计思路：对"热点扣减"的实现解释】；
  • 扣减成功才允许落单，落单走 RocketMQ 削峰；订单支付和关单的并发冲突用 Seata AT 分布式事务 + 状态机 + 乐观锁解决（简历原文）。
  • 整体限流由 Nginx + Sentinel 服务限流兜底（简历原文）。
  • 验证：【设计思路】并发压测下库存与售出总数严格一致，无非零负数与超卖。

被追问最狠的问题 2：关单从 10 单/s 优化到 50 单/s 怎么做的？

  • 遇到问题：XXL-JOB 定时扫描超时订单关单，初始只有 10 单/s，大促积压订单关不过来。
  • 分析：瓶颈在单线程扫描 + 每单串行更新 + 扫描 SQL 全表扫。
  • 方案（简历原文 + 设计思路）：XXL-JOB + 线程池并行处理——任务内把待关单集合分批，交给线程池并发执行关单；扫描配合分库分表后的 XXL-JOB 分片（分片参数扫不同库表），缩小每次扫描范围；关单 SQL 加索引支持。
  • 验证：关单性能从 10 单/s 提升到 50 单/s（简历数据），5 倍提升。

被追问最狠的问题 3：700ms → 50ms 的缓存是怎么设计的？

  • 方案：Redis + Caffeine 多级缓存（简历原文）：Caffeine 本地缓存扛热点读、Redis 做分布式共享层；热点藏品（如限量款）明确标识后走热点缓存通道（含 InventoryHint 热点扣减配合），非热点走普通链路；缓存与 DB 的一致性靠 Canal 监听 binlog 变更同步（此处也涉及我修改 Canal 源码解决同步时间转换异常、重写 SnakeYAML 类解决兼容问题——简历原文，主要体现源码级排查能力）。
  • 验证：热点藏品接口 RT 从 700ms 降至 50ms（简历数据）。

第五战场（补充）：BHU-ACM 实验室官网 — 总负责人 + 后端开发

核心技术难点（3 个）：① 全站鉴权性能；② 高频点赞的读放大；③ 资源有限下的自动化运维。

量化成果：接口鉴权 < 5ms（网关层拦截）；日均活跃 100+。

被追问最狠的问题：接口鉴权 < 5ms 和高频点赞怎么做到的？

  • 鉴权：RBAC + Sa-Token 统一鉴权，在网关层拦截（简历原文），Token 校验走内存/Redis，避免每个业务接口重复查库，鉴权耗时可控制在 < 5ms（简历数据）。
  • 点赞：策略模式动态适配多场景点赞 + Redis + 布隆过滤器优化高频点赞（简历原文）。布隆过滤器先挡掉绝大多数"从未点过赞"的请求打到数据库，只有可能存在的才走精确判定。
  • 追问防御：【设计思路】布隆过滤器有误判率（会把"没点过"判成"可能点过"），所以我的用法是"宁可多查一次，不可漏判"，精确判定永远以 Redis/DB 为准，布隆只做前置过滤；配合自定义线程池与拒绝策略（简历原文）保护点赞接口，线程池满了走拒绝策略而不是拖垮服务。

🗺️ 答题策略

  1. 时间分配 5:3:2：主战场 OrbitQA 占一半时间（双层架构、锁、RAG 三个故事轮流讲），慧策+颛知占三成（大促排查、性能优化显工程功底），数字藏品+BHU 官网最后补刀（展示中间件深度与线上业务完整性）。面试官问哪层就切换到对应战场，先给"一句话结论"再展开细节，避免被带偏。
  2. 四段式叙事纪律：每个难点都按"遇到问题 → 分析 → 方案 → 验证"讲，量化指标一定放在"验证"那一句——70%、55%、99%、<15s、15min+、10→50 单/s、700ms→50ms、3s+→200ms、85%、<5ms、100+、5000+、2700 万+ 全部是简历原文，一个都不能说错、说重。
  3. 诚实分层：简历写了的（如 5min 续期 TTL、归属校验、两层互斥、500 字符+50 重叠切分）直接背出关键词；简历没写的实现细节（如线程池参数、批量大小、布隆误判处理）一律用"当时我是这么设计的"口吻，并主动标注"这是我的设计思路"，绝不冒充简历事实——被追问时承认推断比露馅强得多。
  4. 防御性暴露：主动提每个方案的边界，例如"布隆过滤器有误判，所以只做前置过滤""锁的续期依赖 Redis 可用性，所以叠加了归属校验""双十一修复的压测细节是设计思路"——先自己说缺点，面试官就没法用缺点砸你。
  5. 难度排序防反杀：OrbitQA 最可能被质疑的是"负责人是不是挂名"——准备用"五模块基建划分、PMO 拆分任务的分发逻辑、ReAct 循环的终止条件"等细节自证动手能力；数字藏品最可能被追问源码细节（Canal 源码怎么改的、SnakeYAML 怎么重写的），准备一句"改了同步逻辑里的时间转换与依赖加载顺序，用最小改动保留原语义"兜底即可。
