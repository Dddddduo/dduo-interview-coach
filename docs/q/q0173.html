写一段死锁的代码，然后想尽可能多的方法解决死锁

🧠 联想记忆法

一句话记死锁定义：两个线程互相握着对方要的那把钥匙，谁也不先松手，于是一起卡死。

四必要条件口诀——「互、持、不、环」→ 谐音"虎持不还"：一只老虎（互→互斥）手里握着骨头（持→持有并等待）就是不还（不→不可剥夺、还→环→循环等待）给别人，别人也拿不到骨头，就形成了死锁。破解之道就一句话：四条件缺一不可，打破任意一条，死锁立刻瓦解。

代码记忆——"ABBA 锁"：线程 1 拿 A 锁再要 B 锁，线程 2 拿 B 锁再要 A 锁，方向交叉成环，就是最经典的死锁演示（英文字母 A→B、B→A 本身就是"循环等待"的图形化记忆）。

方法记忆——预防四连：打破循环等待 → 锁排序（按 id 全局顺序加锁）；打破持有并等待 → 一次性申请所有资源；打破不可剥夺 → tryLock 可剥夺锁；打破互斥 → 无锁化 CAS。预防是静态设计，避免是运行时判断（银行家算法），检测恢复是事后兜底（jstack / ThreadMXBean）。

📖 深度解答

1. 核心概念

1.1 什么是死锁（Deadlock）

死锁（Deadlock）指两个或两个以上的线程在执行过程中，因竞争资源而互相等待对方释放资源，导致所有相关线程永久阻塞、无法继续推进的现象。典型场景：转账时两个账户互相扣款、数据库事务交叉更新两张表、分布式系统两个服务互相持有对方需要的分布式锁。

1.2 死锁四必要条件（Coffman Conditions）逐一分析

1971 年 Coffman 等提出死锁必须同时满足的四个条件，缺一不可：

  1. 互斥（Mutual Exclusion）：资源同一时刻只能被一个线程独占使用。比如一把锁只能被一个线程持有。这是锁机制的本质属性，几乎无法打破（只能绕过——用 CAS 乐观锁或读写分离）。
  2. 持有并等待（Hold and Wait）：线程已持有至少一个资源，在等待获取另一个资源的同时，不释放手中已有的资源。这是死锁的"温床"。
  3. 不可剥夺（No Preemption）：资源只能由持有者主动释放，其他线程不能强行抢占。synchronized 就属于典型的不可剥夺锁。
  4. 循环等待（Circular Wait）：存在一条线程等待环：T1 等 T2、T2 等 T3……Tn 等 T1。比如 T1 持有 lock1 等 lock2，T2 持有 lock2 等 lock1。

逐一分析的意义：解决死锁不需要同时破坏四个条件，只要打破其中任何一个即可，这直接推导出四大类预防策略（见 3.1）。

1.3 死锁代码示例：经典 ABBA 交叉加锁（必现，含 main 演示）

下面用 CountDownLatch 门闩保证两个线程同时起跑，且各自第一把锁互不冲突，因此死锁 100% 必现，而不是"碰运气"：

import java.util.concurrent.CountDownLatch;

public class DeadlockDemo {

    private static final Object lock1 = new Object(); // 账户 A 的锁
    private static final Object lock2 = new Object(); // 账户 B 的锁

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch ready = new CountDownLatch(2); // 两个线程都"就绪"
        CountDownLatch go = new CountDownLatch(1);    // 同时放行的"发令枪"

        Thread t1 = new Thread(() -> {
            try {
                ready.countDown();
                go.await();                        // 等待发令
                synchronized (lock1) {             // 先拿 A
                    System.out.println("T1 持有 lock1，等待 lock2...");
                    Thread.sleep(100);             // 确保 T2 已拿到 lock2
                    synchronized (lock2) {         // 再要 B → 死锁
                        System.out.println("T1 转账成功");
                    }
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "T1");

        Thread t2 = new Thread(() -> {
            try {
                ready.countDown();
                go.await();
                synchronized (lock2) {             // T2 先拿 B（顺序反了）
                    System.out.println("T2 持有 lock2，等待 lock1...");
                    Thread.sleep(100);             // 确保 T1 已拿到 lock1
                    synchronized (lock1) {         // 再要 A → 形成环
                        System.out.println("T2 转账成功");
                    }
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "T2");

        t1.start();
        t2.start();
        ready.await();    // 主线程等两人就绪
        go.countDown();   // 放行：T1 拿 lock1、T2 拿 lock2，互不竞争第一把锁
        t1.join();
        t2.join();
        System.out.println("程序结束");  // 永远不会打印到这一行
    }
}

运行后程序永久卡住。此时另开终端执行 jstack <pid>（pid 用 jps 查），就能看到 JVM 检测到的 Found one Java-level deadlock 以及 waiting to lock / locked 明细——这就是第 3.3 节的检测手段。

2. 底层原理

synchronized 的底层：JVM 中每个对象头部有 Mark Word，记录锁状态；加锁本质是进入对象的 monitor（监视器），编译成 monitorenter/monitorexit 指令。为性能经历了锁升级（Lock Escalation）：偏向锁 → 轻量级锁 → 重量级锁。重量级锁由操作系统互斥量（mutex）实现，阻塞时线程从用户态陷入内核态，通过 park/unpark 挂起唤醒。关键点：阻塞在 synchronized 上的线程状态是 BLOCKED，且不响应中断——这正是它"不可剥夺、无法超时"的根源。

ReentrantLock 的底层：基于 AQS（AbstractQueuedSynchronizer，抽象队列同步器）的 CLH（Craig-Landin-Hagersten）变体队列实现，线程通过 LockSupport.parkNanos 休眠。因为等待状态完全由 JVM/Java 层控制，所以它额外提供了 tryLock(timeout)（带超时的可剥夺尝试）、lockInterruptibly()（可中断获取）——这些是 synchronized 做不到的，也是解决死锁的利器。

死锁在底层如何形成：T1 持有 lock1 的 monitor，其线程控制块记录"等待 lock2 的 monitor"；T2 正好反向。两个 monitor 的等待队列互相指向对方的持有者，构成一个有向环，任何一方都不会主动放弃 → 系统资源被永久占用。

检测的底层原理：jstack 靠线程 Dump 做图分析——把"持有"与"等待"关系画成资源分配图，检测到环就输出 Found one Java-level deadlock。程序化检测用 ThreadMXBean.findDeadlockedThreads()（Java 6 引入），它通过 JVMTI 遍历所有线程的锁等待关系，比只查 monitor 锁的 findMonitorDeadlockedThreads 更强，能覆盖 java.util.concurrent 包的锁。

银行家算法（Banker's Algorithm）底层思想：Dijkstra 提出的资源分配策略——分配前先"预演"：假设分配后检查系统是否仍处于安全状态（存在安全序列 Safe Sequence，即存在某种顺序让所有线程依次完成），若不安全则拒绝本次分配，让线程等待。

3. 实践应用

3.1 预防（Prevention）——静态设计，打破四条件之一

打破的条件 手段 代价
循环等待 锁排序/全局顺序加锁（最常用） 需要全局一致的顺序约定
持有并等待 一次性申请所有资源 资源利用率低、临界区变大
不可剥夺 tryLock 超时 + 释放重试 可能引入活锁（需随机退避）
互斥 无锁化：CAS / 乐观锁 只能用于简单读改写场景

① 锁排序（全局顺序加锁）通用实现——所有线程必须遵守同一个加锁顺序，环就永远构造不出来：

/** 锁排序：所有线程统一"先锁 id 小的，再锁 id 大的" */
public class LockOrdering {

    static class Account {
        final int id;             // 全局唯一账户 id（用数据库主键，勿用 identityHashCode，可能碰撞）
        int balance = 1000;
        Account(int id) { this.id = id; }
    }

    public static void transfer(Account from, Account to, int amount) {
        // 关键：比较 id 决定顺序，而不是简单按参数顺序加锁
        Account first  = from.id < to.id ? from : to;   // 先锁 id 小的
        Account second = from.id < to.id ? to   : from; // 再锁 id 大的
        synchronized (first) {
            synchronized (second) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }
}

② 一次性申请所有资源：把"先拿 A 再拿 B"变成"一口气拿到 A、B 两把锁才干活"。现实中可用 Semaphore（信号量）一次 acquire(n) 拿齐 n 个许可，或用数据库的两阶段锁（Two-Phase Locking，2PL：增长阶段只加锁、收缩阶段只解锁）。

③ 可剥夺锁 tryLock 带超时——拿不到第二把锁就释放第一把（打破"持有并等待"），退避后重试：

import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.LockSupport;
import java.util.concurrent.locks.ReentrantLock;

public class TryLockTransfer {

    private final ReentrantLock lock = new ReentrantLock();

    /** 拿不到对方的锁就释放自己的锁，随机退避重试；超时返回 false 交给上层回滚 */
    public boolean transferTo(TryLockTransfer target, int amount) {
        final long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(1);
        while (System.nanoTime() < deadline) {
            if (lock.tryLock()) {                          // 第一把：可尝试获取
                try {
                    if (target.lock.tryLock()) {           // 第二把：拿不到就退出
                        try {
                            System.out.println(Thread.currentThread().getName() + " 转账成功");
                            return true;
                        } finally {
                            target.lock.unlock();
                        }
                    }
                } finally {
                    lock.unlock();                         // 关键：立刻释放已持有的锁
                }
            }
            // 随机退避：避免两个线程"同时释放、同时重试"互相谦让成活锁
            LockSupport.parkNanos(ThreadLocalRandom.current().nextLong(1, 50) * 1_000_000L);
        }
        return false;   // 超时失败，上层执行补偿/回滚
    }
}

④ Lock 接口家族：ReentrantLock 比 synchronized 多了超时、可中断、公平性、多条件队列（Condition），是工程上替代 synchronized 的首选。

3.2 避免（Avoidance）——运行时动态判断

  • 银行家算法：为每个线程记录"最大资源需求"，每次分配前检查是否存在安全序列，不存在就不分配。优点是理论完备，缺点是必须提前知道每个线程的最大需求，现实中很难满足，所以工程上极少完整实现，但思路常考。
  • 加锁前预检测（资源分配图判环）：维护"已持有锁集合"，申请新锁前在图里做一次可达性检查，发现会成环就拒绝或等待。和银行家算法本质同源，都是"先判断、后分配"。

3.3 检测与恢复（Detection & Recovery）——事后兜底

  • jstack 检测：jstack -l <pid>（JDK 9+ 也可 jcmd <pid> Thread.print -l）。输出中若出现 Found one Java-level deadlock 并列出循环等待的线程栈，即确认死锁。
  • ThreadMXBean 程序化检测（可内置成监控任务，周期性上报）：
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();          // null 表示无死锁
if (ids != null) {
    for (ThreadInfo info : bean.getThreadInfo(ids)) {
        System.out.println("死锁线程: " + info.getThreadName()
                + " 状态: " + info.getThreadState());
    }
}
  • 恢复手段：锁超时 + 回滚（即 3.1 的 tryLock 方案，失败返回后做补偿逻辑，如数据库事务回滚）；极端情况下重启进程。数据库（如 MySQL InnoDB）内置死锁检测，检测到环会自动回滚代价较小的事务并报错 1213，这与 JVM 完全不同——JVM 不会自动恢复死锁。

3.4 工程手段：用并发工具"化死锁于无形"

  • ConcurrentHashMap：JDK 8 改为"桶级细粒度锁 + CAS"，不再整表加锁，锁竞争面大幅缩小；
  • 读写锁（ReentrantReadWriteLock）：读读共享、写互斥，把"互斥"条件放宽为"写互斥"，减少冲突窗口；
  • Semaphore：限制同时访问资源的线程数，或一次性领取全部许可；
  • 单线程化 Actor 模型：如 Akka、Disruptor 无锁环形队列——共享状态封装在单个线程/事件循环内，根本不共享内存，自然无锁无死锁；
  • 无锁编程：AtomicInteger 等 CAS 原子类，从源头消灭锁。

4. 深入思考

死锁 vs 活锁 vs 饥饿——面试高频辨析：
- 死锁：线程永久阻塞（BLOCKED/WAITING），不消耗 CPU；
- 活锁（Livelock）：线程不阻塞但永远做无用功——比如两个线程 tryLock 失败后同时释放、同时重试，互相谦让成"空转"。解决靠随机退避（random backoff）；
- 饥饿（Starvation）：线程始终得不到锁/CPU但其他线程一直有进展，如非公平锁（Nonfair Lock）下低优先级线程可能长期等不到锁。解决靠公平锁（Fair Lock）或提高优先级。

为什么 synchronized 无解而 Lock 有解：synchronized 阻塞时不响应中断、无超时，是"不可剥夺"的具象化；只有换成 Lock 家族的 tryLock/lockInterruptibly 才能人为干预。

两点补充认知：其一，锁排序虽好用，但要求所有线程自觉遵守同一全局顺序，一处例外（如代码里的 T2）就前功尽弃，所以团队规范往往比技术方案更关键；其二，银行家算法"最大需求已知"的假设在真实系统里几乎不成立，这也是它停留在教科书的原因——面试能说出这一点，说明你真懂。

🗺️ 回答思路

答题逻辑框架（四层递进）

  1. 定义 + 四必要条件：先背口诀「互持不环」，给面试官一个清晰的坐标系；
  2. 手写死锁代码：现场敲 ABBA 示例，强调用 CountDownLatch 保证必现（体现你会"控制实验变量"）；
  3. 四大类解法：预防（锁排序/tryLock/一次性申请/无锁）→ 避免（银行家算法）→ 检测恢复（jstack、ThreadMXBean）→ 工程替代（并发容器、读写锁、Actor）；
  4. 辨析收尾：活锁、饥饿对比，把深度拉满。

重点得分点

  • 四条件逐一对应破解方案（预防 = 打破条件），而不是零散罗列方法；
  • 锁排序代码写对：先比较 id 再决定加锁顺序，而不是按参数顺序锁；
  • 会写 jstack 命令 + ThreadMXBean.findDeadlockedThreads()；
  • 说出 synchronized 与 ReentrantLock 的底层差异（monitor vs AQS + LockSupport）；
  • 主动提到 tryLock 的副作用是活锁，以及随机退避方案——这是加分细节。

常见误区

  1. 以为 synchronized 可被 interrupt 打断：错，阻塞在 synchronized 上的线程不响应中断；InterruptedException 只在 wait/join/sleep 时抛出；
  2. jstack 用法错误：jstack 是事后检测工具不是预防工具，要加 -l 看完整锁信息；
  3. 混淆死锁/活锁/饥饿：死锁"卡死不动"、活锁"空转不休"、饥饿"永远轮不到"；
  4. 以为锁排序 = "先锁 A 再锁 B"：关键是所有线程必须统一顺序，T2 反着来立刻死锁；
  5. 以为 tryLock 万能：会引入活锁和忙等 CPU 空转；
  6. 以为死锁只存在于 synchronized：任何锁机制（分布式锁、数据库锁）都可能死锁。

过渡话术

  • 代码 → 解法："刚才这段代码形成了经典的循环等待，怎么解？核心思想只有一句：四条件缺一不可，打破任意一个即可，这对应着四类预防手段。"
