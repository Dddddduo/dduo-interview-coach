数据库索引失效的情况有哪些？

数据库索引失效的情况有哪些？

数据库索引失效的情况有哪些？（MySQL 方向）

🧠 联想记忆法

口诀：「左模函隐，或范非空，统计排序」——十个场景压成 12 个字，讲完正好一个不落：

字 场景 类别
左 违反最左前缀（Leftmost Prefix） 结构性失效
模 前导模糊 LIKE '%xx' 结构性失效
函 函数/计算作用于索引列（LEFT、num+1=5） 结构性失效
隐 隐式类型转换（Implicit Type Conversion） 结构性失效
或 OR 连接非索引列 优化器/语义层面
范 范围条件（Range）右侧的列 优化器/语义层面
非 NOT IN / NOT EXISTS / != 优化器/语义层面
空 IS NULL / IS NOT NULL 三值逻辑（Three-Valued Logic） 优化器/语义层面
统 统计信息（Statistics）失真 成本层面
排 排序/分组与索引顺序不符 成本层面

记忆故事：想象你拿着 EXPLAIN 报告像拿着一张路况图——「左模」最爱走最左边的路（最左前缀），可「函隐」这两个路标一出现（函数、隐式转换），导航立刻失灵；「或范」大路一堵车（OR、范围），右侧车道全部作废；「非空」小巷信号差（NOT 系列、IS NULL）；最后还得靠「统计」路况图和「排序」车道线来判断走不走索引。口诀本身就带了两层分类：前四个是 B+ 树结构上用不了，中间四个是优化器/语义层面用不了，最后两个是成本层面不想用——这个分类意识就是面试时的最大加分点。

📖 深度解答

1. 核心概念

索引失效（Index Invalidation）的准确含义是：不是索引"坏了"，而是这一次 SQL 执行没有使用索引。它分两大类：

  1. 结构性失效：条件在 B+ 树（B+ Tree）上根本无法做键值定位/范围定位——想用也用不了；
  2. 成本性失效：索引明明可用，但优化器（Optimizer）用成本模型（Cost Model）估算后认为全表扫描（Full Table Scan）更便宜——能用但不想用。

判断标准是 EXPLAIN 输出：type 字段从优到劣依次是 system > const > eq_ref > ref > range > index > ALL，当表有索引但 type=ALL 或 key 为 NULL 时，就是"失效"；另外 Extra 列出现 Using filesort（文件排序）、Using temporary（临时表）也提示索引没被有效利用。

相关术语：回表（二级索引查到主键后再回主键树取整行）、覆盖索引（Covering Index，索引已含所需列，免回表）、索引下推（Index Condition Pushdown，ICP）、选择性（Selectivity，列去重值与总行数之比）。

2. 底层原理

B+ 树叶子节点是有序链表，定位方式只有两种：等值二分定位 + 范围扫描。因此必须"按照索引定义时的列顺序、从最左列开始、连续地"给出条件，树的键序（key order）才能被利用。这统一解释了所有"结构性失效"：

  • 条件作用在变换后的值上（函数、计算、隐式转换），而树里存的是原始值，键序被打乱，无法二分定位；
  • LIKE 前导 %：无法确定起点，只能从第一个叶子扫到最后；
  • 跳过中间列：键序断档，后续列无法继续参与定位。

而"成本性失效"的解释在存储引擎层：InnoDB 的二级索引（Secondary Index）叶子节点存的是主键值，走索引 = 索引扫描 + 逐行回表（每次回表都可能是一次随机磁盘 IO）。优化器依据统计信息估算扫描行数，行数占比过大时，全表扫描的顺序读反而更快——注意这里没有硬性阈值，是纯成本估算。

还有一个必须掌握的底层概念：三值逻辑。SQL 中 NULL 参与比较的结果是 UNKNOWN 而不是 TRUE/FALSE，这是 = NULL、NOT IN 含 NULL 这类"语义失效"的根源。

3. 实践应用

以下 10 个场景，每个都给出反例 SQL、失效原理（B+ 树层面）、正确写法。

场景一：违反最左前缀（设联合索引 idx(a,b,c)）

-- 反例：从非最左列开始，或跳过中间列
SELECT * FROM t WHERE b = 2;             -- 全表扫
SELECT * FROM t WHERE a = 1 AND c = 3;   -- 只用到 a，c 断档

原理：树按 (a,b,c) 整体字典序排列。没有 a 的约束时，b 的取值散布在整棵树中，无从定位；a 等值后树内 b 有序，但 c 要依赖 b 才能继续，中间断档后 c 只能靠 ICP 过滤。正确写法：条件必须含最左列，或为新的查询模式单独建 (b,c) 索引。

场景二：函数 / 计算作用于索引列

SELECT * FROM t WHERE LEFT(name, 3) = '张';  -- 反例
SELECT * FROM t WHERE num + 1 = 5;           -- 反例

原理：树里存的是 name 的原始值，LEFT(name,3) 是变换后的值，键序被打乱无法二分；优化器不会对列做逆运算反解（列上的表达式不可反转定位）。正确写法：

SELECT * FROM t WHERE name LIKE '张%';        -- 改写为可定位的形态
SELECT * FROM t WHERE num = 4;                -- 把计算移到常量侧

-- MySQL 8.0.13+：函数索引（Functional Index）
CREATE INDEX idx_name3 ON t ((LEFT(name, 3)));

-- MySQL 5.7：生成列（Generated Column），VIRTUAL 列即可加索引
ALTER TABLE t ADD COLUMN name3 VARCHAR(3)
  GENERATED ALWAYS AS (LEFT(name, 3)) VIRTUAL,
  ADD INDEX idx_name3 (name3);

场景三：隐式类型转换

-- 反例：phone 是 VARCHAR 列，却用数字比较
SELECT * FROM t WHERE phone = 13800138000;

原理：MySQL 的转换规则是数字优先级高于字符串，比较时把字符串列转成数字（等价于对列做了一次 CAST，即"函数作用于列"），索引失效。同理，两表 join 时字符集/排序规则（collation）不一致（如 utf8 vs utf8mb4），也会在列上发生隐式转换。正确写法：WHERE phone = '13800138000';——原则是列上零转换。

场景四：前导模糊 LIKE '%xx'

SELECT * FROM t WHERE name LIKE '%张%';   -- 反例

原理：树按 name 前缀有序，前导 % 无法确定起点，只能从头扫到尾。缓解方案（MySQL 5.7 起）：

-- ① 后缀匹配改写：生成列存 REVERSE(name) 并加索引
ALTER TABLE t ADD COLUMN name_rev VARCHAR(20)
  GENERATED ALWAYS AS (REVERSE(name)) VIRTUAL,
  ADD INDEX idx_name_rev (name_rev);
SELECT * FROM t WHERE name_rev LIKE '张%';     -- 反查后缀，走索引

-- ② 真正的内容检索：FULLTEXT 全文索引（5.6+ InnoDB 支持，5.7 引入 ngram 解析器支持中文分词）
SELECT * FROM t WHERE MATCH(name) AGAINST('张' IN NATURAL LANGUAGE MODE);

注意 LIKE 'xx%'（尾部通配）是可以走索引范围扫描的——只有前导通配才会失效。

场景五：OR 连接非索引列（设仅有 idx(name)）

SELECT * FROM t WHERE name = '张三' OR age = 20;   -- 反例

原理：OR 需要合并两边的结果集，age 上没有索引，无法参与索引合并（index_merge），优化器只能全表扫后逐行过滤。正确写法：

SELECT * FROM t WHERE name = '张三'
UNION ALL
SELECT * FROM t WHERE age = 20;   -- 两侧各自走索引；需要去重时改 UNION

或者给 age 也建索引，让 MySQL 自动走 index_merge。

场景六：范围条件右侧的列失效（设联合索引 idx(a,b)）

SELECT * FROM t WHERE a > 1 AND b = 2;   -- 反例：b 无法参与定位

原理：a 走范围后命中一段连续区间，但区间内 b 的取值是乱序的（树按 (a,b) 排序，a 每次变化 b 从头开始），b 无法缩小范围，只能靠 ICP 在叶子节点过滤。正确写法：

-- ① 等值列放前面，调整索引为 (b,a)
-- ② 把范围改写为等值边界（a >= 2 单边条件无法让 b 参与定位，
--    必须给出上界 a <= 2 构成等值点，优化器才能按 a = 2 处理，b 才可继续参与）
SELECT * FROM t WHERE a >= 2 AND a <= 2 AND b = 2;

BETWEEN 同理；而 a >= 1 AND a <= 1 这种"等值边界"组合，右侧列仍然可用。

场景七：NOT IN / NOT EXISTS / !=

SELECT * FROM t WHERE status != 1;                     -- 反例：常被选为全表扫
SELECT * FROM t WHERE id NOT IN (SELECT uid FROM u);   -- 反例：子查询含 NULL 时恒空

原理：这一组不是"铁定失效"，而是优化器选择 + 三值逻辑的坑：

  • != 等价于 col < 1 OR col > 1 两个范围，MySQL 技术上可以走范围扫描，但通常覆盖行数过多、回表成本高，优化器选全表扫；
  • NOT IN (子查询)：若子查询结果含 NULL，x NOT IN (...) 三值运算结果为 NULL 而非 TRUE，整条语句返回空结果——这是语义错误，不只是性能问题；MySQL 会把 NOT IN 子查询改写为 NOT EXISTS（反连接 antijoin）或物化（Materialization），依赖内表索引；
  • NOT EXISTS 相关子查询：内表关联列必须有索引，否则退化为嵌套循环（Nested Loop）逐行扫描。

正确写法：!= 场景改用覆盖索引降低回表成本；子查询场景给内表列建索引；NULL 陷阱优先用 NOT EXISTS 或先 WHERE col IS NOT NULL 排除。

场景八：IS NULL / IS NOT NULL

SELECT * FROM t WHERE name = NULL;   -- 反例（伪失效）：永远查不到

原理：三值逻辑——NULL 与任何值比较结果为 UNKNOWN，WHERE 只接受 TRUE，所以 = NULL 恒空。真正的加分点：name IS NULL 本身是范围条件，可以走索引（InnoDB 中 NULL 记录在 B+ 树最左侧）；name IS NOT NULL 也可以走范围，只是当绝大多数行都不为 NULL 时，优化器因成本选全表扫。正确写法：判空一律用 IS NULL / IS NOT NULL，禁止 = NULL；在 NOT IN 场景先加 IS NOT NULL 排除 NULL 行。

场景九：统计信息与优化器选择

-- 反例：索引存在，但 EXPLAIN 显示 type=ALL，rows 估算巨大
SELECT * FROM t WHERE gender = 'M';   -- 选择性约 50% 的列

原理：成本性失效——非覆盖索引 = 索引扫描 + 大量随机回表；选择性低时估算行数巨大，全表扫描顺序读反而便宜。统计信息过期（大量增删改后未 ANALYZE）也会导致估算偏差。正确写法：

ANALYZE TABLE t;                        -- 更新统计信息（8.0 还支持直方图 Histogram）
EXPLAIN FORMAT=TREE SELECT ...;         -- 8.0.16+ 看执行树与成本细节
-- 或用 optimizer_trace：SET optimizer_trace='enabled=on' 后查 information_schema.optimizer_trace
-- 治本：把 SELECT 列并入索引构成覆盖索引，消除回表

这正对应我简历里的案例：线上一个 3 秒多的慢查询，EXPLAIN 显示 type=ALL、rows 几十万，加覆盖索引后变成 index 扫描 + Using index，耗时降到 200ms 左右。注意 force index 只是治标，索引结构变化后可能失效。

场景十：排序/分组与索引顺序不符（设联合索引 idx(a,b)）

SELECT * FROM t ORDER BY b;              -- 反例：filesort
SELECT * FROM t WHERE a > 1 ORDER BY b;  -- 反例：a 范围后 b 无序，filesort
SELECT * FROM t GROUP BY b;              -- 反例：需要临时表

原理：索引天然有序，可以代替排序（避免 filesort）；但 ORDER BY 同样要求满足最左前缀且方向一致（MySQL 8.0 之前不支持混合方向扫描，8.0 起支持 DESC 索引与反向扫描）。正确写法：WHERE a = 1 ORDER BY b（a 等值后 b 有序）可以走索引排序；否则为排序查询单独建 (b) 或 (b,a) 索引，或接受 filesort 并调大 sort_buffer_size。

4. 深入思考

(1) 真实世界的"元凶"排序：线上最常见的是隐式类型转换和函数/计算（常被传参类型不对带出来），其次是违反最左前缀；LIKE 前导 %、NOT 系列这类"教科书案例"反而少见。面试时说出这个排序，会显得有实战感。

(2) 失效是动态的：同一个 SQL 今天走索引、明天全表扫——统计信息、数据分布、optimizer_switch 参数都在变。所以调优要"以 EXPLAIN 为准，而不是背结论"。

(3) 版本演进视角：5.7 生成列 → 8.0.13 函数索引 → 8.0 直方图、反连接、反向索引扫描，很多"失效"在新版本有了官方解法。这背后本质是"B+ 树键序 vs 查询形态"的匹配问题，版本只是工具。

(4) 方法论沉淀（EXPLAIN 三板斧）：看 type（访问方式）、看 key（用了哪个索引）、看 Extra（filesort/temporary/Using index condition/Using index），再结合 rows 估算。我简历里 3s+→200ms 的优化就是按这个流程：先定位 ALL，再判断是结构性还是成本性，最后用覆盖索引收尾。

🗺️ 回答思路

答题逻辑框架（总分总）

  1. 开场定义（15~20 秒）：一句话点题——"索引失效不是索引坏了，我分两类答：结构性用不了和成本性不想用"，并带出 EXPLAIN type 的判断标准，展示方法论意识；
  2. 主体按口诀展开（2.5~3 分钟）：「左模函隐，或范非空，统计排序」。前四个讲 B+ 树结构原理（原理分），中间四个讲优化器与三值逻辑（深度分），最后两个讲成本与排序。每个场景 15~20 秒，重点讲 3 个：最左前缀、隐式类型转换、范围右侧列；
  3. 收尾（30 秒~1 分钟）：用简历案例佐证 + 方法论总结——"判断失效，永远以 EXPLAIN 为准"。

重点得分点

  • 分类意识（结构失效 vs 成本失效）：大多数候选人不会分，这是最大的差异化；
  • 每个失效都讲得出 B+ 树层面的原因（键序、二分定位、回表）；
  • 敢于纠错："IS NULL 其实可以走索引"、"!= 不一定失效"——体现知其然更知其所以然；
  • 自然带出"解法词"：覆盖索引、ICP、生成列、函数索引、直方图；
  • 有真实案例（3s+→200ms），哪怕一句话带过，可信度直接拉满。

常见误区

  • 只背场景不会归类，面试官追问"为什么"就卡壳；
  • 把"优化器选择"说成"一定失效"：!=、NOT IN、IS NOT NULL 都是"看情况"，话说太死会被追问反驳；
  • 说"IS NULL 完全失效"：这是错误结论，能主动纠正反而是加分；
  • 建议函数索引不提版本：函数索引是 8.0.13+，5.7 要用生成列，版本意识是亮点；
  • 全程不讲 EXPLAIN 判断方法：等于只会背题、不会诊断。

时间分配建议

  • 0~30s：定义 + 分类 + EXPLAIN 判断标准；
  • 30s~3.5min：十个场景（3.5 分钟内讲完，重点三个，其余快速带过）；
  • 3.5~4.5min：案例 + 方法论收尾；
  • 全程控制在 4~5 分钟，留 1 分钟给面试官追问（追问大概率是"怎么判断/怎么排查"，正好接住）。

过渡话术

  • 开场："这个问题我分两类来答：一类是结构上就用不了索引，另一类是优化器认为用索引不划算。我先说前者……"
  • 场景切换："以上四个是 B+ 树结构层面的；下面这几个更隐蔽，是优化器选择和 SQL 语义层面的……"
  • 收尾："最后说一个判断方法。我之前在项目里用 EXPLAIN 排查过一个 3 秒多的慢查询，定位到 type=ALL 后加覆盖索引，优化到 200ms 左右。所以我的结论是：索引失效没有固定清单，判断标准永远是 EXPLAIN 的成本估算，口诀只是帮我们快速定位嫌疑。"
