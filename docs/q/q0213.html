什么情况下应该坚持固定 RAG，而不是升级成 Agentic RAG？

什么情况下应该坚持固定 RAG，而不是升级成 Agentic RAG？

什么情况下应该坚持固定 RAG，而不是升级成 Agentic RAG？

🧠 联想记忆法

一句话锚点：升不升级，就看一架天平——"确定性收益 > 不确定性成本"才升级，否则坚持固定 RAG。

数字记忆法（"六个不升，一才升"）：六个"不升级"场景 = 单跳、延迟、成本、审计、已稳、难评；一个"才升级"信号 = 低置信、多跳、追问。把"六个不升"串成口诀："一跳就够、等不起、花不起、说不清、改不了、评不了"——单跳问答一次检索就够（一跳就够）；在线客服延迟敏感（等不起）；调用量大成本敏感（花不起）；金融合规要审计（说不清）；检索质量已稳定（改不了）；评测体系不健全（评不了）。

场景代入法：把自己想象成电商客服机器人。用户问"运费多少"——查一次文档就回答，这就是固定 RAG；如果它先"思考"要不要再搜、要不要拆成三个子问题、要不要调 API，用户早就挂断电话了。只有用户追问"那退货怎么算？"（追问）或"保价和运费险有什么区别？"（多跳）时，才值得启动"搜索小分队"（Agentic 补检）。

📖 深度解答

1. 核心概念

固定 RAG（Fixed RAG）：一条确定性的流水线（Pipeline）——用户问题 → 检索器（Retriever）一次检索 top-k → 拼接上下文 → LLM 生成答案。所有环节固定、可预期，执行路径不随问题内容改变。

Agentic RAG（智能体化 RAG）：把"决策权"交给大模型，由它自主决定：要不要检索、检索什么、要不要改写查询（Query Rewriting）、要不要拆分子问题（Sub-question Decomposition）、要不要多轮检索甚至调用外部工具。执行路径是非确定性的，因问题而异。

本质区别：流程决策从构建期（build time）移到了运行期（run time）。固定 RAG 的策略在构建时定死，Agentic RAG 的策略在每次运行时由模型现做。

判断框架：确定性收益是否大于不确定性成本（Certain gain vs. uncertain cost）。Agent 化带来的收益是"多轮检索换来的准确率提升"，这部分收益可以在评测集上确定性地测出来；但它引入的成本是"不确定性"的——多一轮调用就是多一份延迟与 token 消耗，多一个决策点就是多一份出错和不可复现的风险。当确定性收益不足以覆盖不确定性成本时，坚持固定 RAG。

2. 底层原理

为什么 Agent 化不是免费的？因为它重构了成本结构：

  • 多轮 LLM 调用成本：固定 RAG 只有 1 次检索 + 1 次生成；Agentic 每多一轮规划/决策就是一次额外的 LLM 调用，推理（Inference）的 token 消耗和延迟随轮数线性甚至超线性增长。在日均百万级请求的规模下，这是真金白银。
  • 决策错误风险（Decision error risk）：模型做"要不要检索/检索什么"的决策本身会出错——过度检索（Over-retrieval）引入噪声上下文污染答案，检索不足（Under-retrieval）漏掉关键证据，规划错误把简单问题拆碎导致错误逐级放大。固定 RAG 的检索策略是工程师调优过的确定性方案，不存在这层风险。
  • 不可复现性（Non-reproducibility）：Agent 的路径依赖模型输出，受 temperature 与上下文影响，同样的输入可能走不同路径。审计（Audit）、问题排查（Debugging）、回归测试（Regression testing）全部变难。
  • 对应地，收益只体现在特定 badcase 上：固定 RAG 一次检索解决不了的问题，主要是多跳问题（Multi-hop）、需要工具调用的问题、用户意图模糊需要澄清的问题——这些在真实流量中的占比往往不足 10%。这意味着 Agent 化是"用 100% 的额外成本去覆盖 10% 的场景"。

3. 实践应用（坚持固定 RAG 的六个场景）

a) 简单单跳问答（Single-hop QA）：FAQ、产品文档问答、知识库问答——一个问题一次检索 top-k 就够了。Agent 化纯属浪费：没有多轮检索的空间，只有多一轮调用的延迟。

b) 延迟敏感（Latency-sensitive）：在线客服、实时风控、对话式助手。固定 RAG 端到端约 300–500ms；Agentic 每多一轮检索加 200ms 到 1s+，且多轮补检会显著放大 P95（95th percentile，第 95 百分位延迟）——最慢的请求从"一次检索慢"变成"多轮串行都慢"。对 SLA（Service Level Agreement，服务等级协议）有硬约束的场景，这是不可接受的。

c) 成本敏感（Cost-sensitive）：日调用量大的场景，每多一轮检索 + 一次 LLM 调用都是钱。多一轮可能就是 2–3 倍 token，在 CPM（Cost Per Million tokens，百万 token 计费）模式下，日均千万 token 的规模差异就是每月几十万级的账单差，还没算检索基础设施（向量库 QPS、embedding 调用）的成本。

d) 审计与可复现要求（Auditability & Reproducibility）：金融、医疗、合规场景。固定 RAG 的执行轨迹固定：输入相同、检索相同、生成相同，流程可预测、可审查，能回答"为什么是这个结果"。Agent 化的随机路径在监管审查面前是劣势——你说不清"这次为什么多搜了一轮"。

e) 检索质量已经很稳定：当 embedding 模型、重排（Reranker）、召回率（Recall）都已充分调优，badcase 率很低时，Agent 的收益空间很小——收益只来自 badcase，badcase 都快清零了。用"增量收益 ≈ 0"换"增量成本 > 0"，不划算。

f) 评估体系不健全（Immature evaluation）：Agent 化后行为不可预测，如果离线评测集（Eval set）和线上监控不完善，你无法回答"升级后到底变好还是变坏"，回归风险不可度量。没有评测的升级就是盲飞——这时应坚持固定 RAG，先把评测体系建起来。

工程实践：混合策略（Hybrid / Router-based strategy）——多数团队的最终答案。默认走固定 RAG 快路径，只有特定信号触发时才升级到 Agentic 补检：
- 低置信度（Low confidence）：检索相似度分数低于阈值，或生成模型的 self-consistency（自洽性）低；
- 多跳检测（Multi-hop detection）：用轻量分类器判断问题是否含多个实体、多个限定条件，需要多轮检索；
- 用户追问（Follow-up）：首答后用户不满意继续追问，说明首次检索信息不足。

这样把 Agent 的能力限制在真正需要的流量子集上，用 5–10% 的请求承担 100% 的 Agent 成本，性价比最优。（可联动第 61 题：Agentic RAG 的触发与路由设计。）

4. 深入思考：如何量化判断

回答"该不该升级"，不要拍脑袋，要建算式：

  • 离线评测对比：构造覆盖两类场景（单跳与多跳）的评测集，对两种模式分别跑，得到"质量—成本"两个维度：质量侧看答案准确率（Accuracy）、引用正确率（Citation accuracy）；成本侧看 P95 延迟、单次平均 token 数、失败率。
  • 性价比指标：计算增量收益与增量成本之比：(Agentic 准确率 − Fixed 准确率) ÷ (Agentic 平均成本 − Fixed 平均成本)。只有当增量收益被业务量化（如减少一次人工转接、多一笔成交）后能覆盖增量成本，才值得升级。
  • 细分的视角：升级决策本质是"按请求类型条件化的路由"——高收益子流量（多跳、追问）分给 Agent，低收益子流量留在 Fixed，这正是混合策略的理论基础。
  • 反模式提醒：最常踩的坑是"简单任务复杂化"（Over-engineering / Premature abstraction）——把 Agent 当万能钥匙，为 10% 的 badcase 引入 100% 的复杂度。面试官想听的是"知道何时不做"的工程判断力：确定性、可预测、便宜的方案，永远优于聪明、随机、昂贵的方案；复杂度应只加在收益确认过的位置。

🗺️ 回答思路

答题逻辑框架（总分总）：
1. 亮观点：升级与否是成本收益判断题，不是技术先进度判断题——"确定性收益 > 不确定性成本"就升级，否则坚持固定 RAG；
2. 给框架：一句话说清两种模式的本质区别（决策在构建期还是运行期）；
3. 展开场景：挑 2–3 个最有说服力的场景讲透（建议延迟 b + 成本 c + 审计 d），其余点一下；
4. 讲原理：Agent 的三重成本结构（多轮调用、决策错误、不可复现）+ 收益集中在小比例 badcase；
5. 收尾升华：给出混合策略体现落地能力，联动第 61 题体现知识体系。

重点得分点：
- 先给"确定性收益 vs 不确定性成本"框架——这是本题的灵魂；
- 讲清成本结构三要素（多轮 LLM 调用 / 决策错误 / 不可复现），说明你理解 Agent 不免费；
- 主动给出混合策略而非二选一，体现工程判断而非二极管思维；
- 提到量化评测（离线评测集 + 性价比指标），体现数据决策习惯；
- 点出"简单任务复杂化"反模式，体现架构品味。

常见误区：
- 只答"简单场景不需要 Agent"，没有框架、没有成本结构分析——浮于表面；
- 把"成本高"当唯一理由，忽略延迟、审计、可复现这些更硬的理由；
- 全程吹 Agentic RAG 是趋势，暗示"迟早要升"——会被认为缺乏判断力；
- 不提混合策略——答案停在"什么时候用哪个"，没到"怎么组合"；
- 背场景清单像背菜单，每个场景只给标签不给解释。

时间分配建议（按面试 3–5 分钟作答）：
- 0–30 秒：亮观点 + 判断框架；
- 30 秒–2 分钟：场景清单，详讲 2–3 个（延迟/成本/审计），带数据（P95、token、占比）；
- 2–3.5 分钟：底层原理（成本结构与收益分布）；
- 3.5–4.5 分钟：混合策略 + 量化方法 + 反模式，收尾。
若被追问，优先展开混合策略的触发信号设计与离线评测方法。

过渡话术：
- 开场："我认为这不是一个技术选型问题，而是一个成本收益判断题——核心是确定性收益是否大于不确定性成本。"
- 场景转原理："这些场景的共性在于，Agent 化的成本结构发生了本质变化……"
- 场景转策略："当然，现实里我们不会二选一，更常见的工程答案是混合策略……"
- 收尾："最后我想强调，Agent 化真正值钱的地方是路由和触发设计，而不是把简单问题复杂化——复杂度要花在收益确认过的位置。"
