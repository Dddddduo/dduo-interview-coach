电商图生视频缓存实现

电商图生视频缓存实现

电商图生视频缓存实现

🧠 联想记忆法

把「图生视频缓存」拆成三个记忆锚点，面试前 30 秒快速过一遍：

锚点一：公式记忆。 图生视频缓存 = 多级缓存（简历已有）+ 文件型结果（新增）+ 生成式状态机（State Machine）（新增）。简历上「Redis + Caffeine 多级缓存」管的是读得快的 JSON 数据；图生视频的结果是一段视频文件，所以核心差别一句话：Redis 存元数据（Metadata）和任务状态，OSS + CDN 存视频文件本身。记住这个「文件不进 Redis」的差别，就不会答成普通数据缓存。

锚点二：口诀记忆。 「穿透布隆、击穿互斥、雪崩抖动」——三大经典问题的三板斧；再补两句：「重建一把锁」（对应第 12 题互斥重建）、「Key 里加校验」（对应第 11 题 MD5 冲突）。五句话把防护体系和两个关联题全串起来。

锚点三：类比记忆。 把图生视频比作简历里的「热点藏品」：热点藏品是"读接口贵"（RT 700ms），用缓存降到 50ms；图生视频是"算接口贵"（GPU 生成要几秒到几分钟），用缓存把"已经生成过的结果"直接复用。本质都是把贵的读/算，变成便宜的缓存命中。面试时先讲简历的多级缓存故事，再向图生视频平移扩展，逻辑最顺。

📖 个人化回答

第一步：先如实说简历里实际做了什么

我在数字藏品电商平台（省级实验室项目，2025.03-2026.03）后端，真实落地的缓存相关经历有：

  • 多级缓存机制：使用 Redis 和 Caffeine 构建两级缓存，Caffeine 作本地 L1、Redis 作 L2，优化数据读取速度、减少数据库压力；
  • 热点缓存：针对热点藏品引入缓存机制，接口 RT 从 700ms 提升到 50ms（简历真实量化数据，未命中走 DB、命中走缓存的收益对比）；
  • 配套能力：AOP + 自定义注解 + Redisson 实现分布式锁注解；Lua + Redis 实现库存秒杀扣减；XXL-JOB（含分片）做定时扫表；RocketMQ 做异步消息；Seata AT 模式分布式事务。

这里必须先坦白：「图生视频」模块在简历中没有明确记载，我项目的缓存对象是藏品数据（JSON 读缓存），不是视频文件。所以下面分两部分：以上是简历真实经历；接下来是基于这段经历、对「电商图生视频缓存」做的合理设计推演——推演是我的方案设计，不是简历经历，请以此区分。

第二步：基于经历的「电商图生视频缓存」设计推演

1. 缓存什么、存在哪（层次设计）

图生视频结果和藏品数据本质不同：结果是文件而非行数据。我的推演是三层：

  • 视频二进制文件存 OSS + CDN，文件级缓存由 CDN 承载（大文件进 Redis 是错误方案，浪费内存且吞吐差）；
  • Redis 存元数据（Metadata）+ 任务状态机（State Machine）：pending / running / done / failed，以及结果 OSS 地址、时长、封面、校验信息；
  • 沿用简历思路，Caffeine 做 L1：对热门模板、高频结果元信息做本地缓存，Redis 做 L2 兜底——与简历「Redis + Caffeine 两级缓存」完全同构，只是缓存对象从藏品行数据换成了结果元信息。

2. Key 设计

  • 请求特征 Key：img2video:req:{md5(userId|imageMd5|prompt|model|params)} → 存「该请求是否生成过、对应哪个 taskId」；
  • 结果 Key：img2video:result:{taskId} → 存 OSS 地址、元数据、TTL、校验字段；
  • 图片内容 Key：img:md5:{imageMd5} → 识别相同输入图，支撑「同图同 prompt 复用结果」，这是图生视频缓存收益最大的场景。

3. TTL 与一致性

生成式结果不可变、生成成本极高，TTL 应设长（推演：7 天），由 XXL-JOB 定时扫描清理过期结果——直接平移简历「XXL-JOB 分片扫表」经验；用户主动删除时用 RocketMQ 异步删 OSS 文件 + Redis 元数据。因为视频生成后基本不再修改，用最终一致性即可，一致性压力远小于订单/库存这类强一致场景（那里我用了 Seata + 乐观锁，这里不需要）。

4. 穿透（Cache Penetration）/ 击穿（Cache Breakdown）/ 雪崩（Cache Avalanche）防护

  • 穿透：布隆过滤器（Bloom Filter）拦截不存在的请求特征，再兜底空值缓存（null cache）短 TTL（如 30s），避免恶意请求打到生成服务；
  • 击穿：热点 Key 过期瞬间大量请求同时重建，用互斥（Mutex）重建控制（见第 5 点）；
  • 雪崩：TTL 加随机抖动（基础 TTL ±10%），L1/L2 TTL 错峰（Caffeine 短、Redis 长），避免同时大面积失效。

5. 重建并发控制（关联第 12 题）

推演场景：两个用户同一秒提交「相同图片 + 相同 prompt」，绝不能生成两次浪费 GPU。方案直接复用简历能力：在生成入口用自定义注解 + Redisson tryLock 做互斥，拿到锁的线程幂等（Idempotent）创建任务并写 Redis 状态，未拿到锁的线程轮询已有 taskId；用 Lua 脚本原子完成「检查 → 上锁 → 写状态」，保证不并发重建。关键差异点：图生视频的生成是异步的，所以互斥点从「同步重建缓存」变成了「幂等创建任务」——命中就返回结果，未命中就任务化，前端轮询/SSE 拿状态，这比普通缓存重建多一层任务化设计。

6. MD5 哈希冲突（关联第 11 题）

请求特征 Key 用 MD5 拼出，理论上存在冲突；一旦冲突会把别人的结果错误复用给当前用户，而一次生成耗几秒到几分钟的 GPU 时间，错误成本极高。推演方案：Key 中拼入 userId 等业务维度降低冲突面；命中时二次校验（比对 imageMd5、图片大小、prompt 长度等字段），必要时追加 SHA-256 做精确匹配，宁可 miss 重新生成，也不错误复用。

第三步：量化口径说明

简历真实量化仅有两组：热点藏品接口 RT 700ms→50ms；关单性能 10 单/s→50 单/s。图生视频的命中率目标、耗时预期（如「命中毫秒级返回、未命中异步生成」）属于推演设计目标，面试时我会明确标注为「设计预期」，不会伪装成简历数据。

🗺️ 答题策略

  1. 先立边界再展示能力：开场主动说明「简历没有图生视频模块」，用诚实建立信任，再用「多级缓存、Redisson 锁、Lua、XXL-JOB、RocketMQ」五段真实经历锚定能力——面试官不会因模块缺失扣分，反而认可严谨性。
  2. 每提一个推演，挂一段简历证据：互斥重建挂 Redisson 注解，清理挂 XXL-JOB，异步回填挂 RocketMQ，原子操作挂 Lua。让推演「有根」，是个人化回答的灵魂。
  3. 主动串联第 11、12 题：讲到 Key 设计时主动抛出「MD5 冲突二次校验」，讲到重建时主动抛出「互斥 + 幂等任务化」，展示知识体系是串起来的，而不是背题库。
  4. 反问收尾：追问「结果文件平均大小、单次生成成本、目标命中率」，展示你是带着工程指标思考的，而非背方案。
  5. 三个避坑点：700ms→50ms 只能说成热点藏品数据；所有图生视频方案都要带「推演」标记；绝不提「Redis 直接存视频」这种错误方案。
  6. 时间分配建议（总计约 4.5 分钟）：开场 30s 先坦白简历无图生视频模块、立边界 → 1min 讲简历多级缓存与 RT 700ms→50ms 量化 → 3min 推演设计（层次/Key 设计 60s、TTL 与一致性 30s、防护 45s、重建并发 45s、MD5 校验 30s）→ 30s 反问收尾。若被追问，优先展开「互斥重建」与「MD5 二次校验」这两个与第 11、12 题联动的深水区。
