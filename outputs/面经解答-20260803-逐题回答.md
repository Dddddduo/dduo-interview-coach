## 1. Agent 项目怎么开发的？ {#q1}

### 🧠 联想记忆法

**口诀**：「前端 EventSource 单向收，后端 Emitter 事件推，Agent 流水线三节点，六脚本十阶段跑全流程。」

**记忆原理**：把整个架构抽象成一条 SSE 长连接管道——前端只负责"听"，后端负责"说"，中间是确定性的 10 阶段流水线。

### 📖 深度解答

#### 1. 核心概念

我说两个项目，它们在架构思路上是统一的：

**Interview Coach（个人项目）**：基于 Harness Engineering 思想，用 Claude Code 的 Skill + Agent + Workflow 体系构建。用户输入面试题 → 3 个 Agent 协作（Answerer → Reviewer → Assembler）→ 自动归档题库 → Git 推送。

**OrbitQA 星轨平台（快手实习）**：同样贯彻 Harness Engineering——PMO 编排层拆分任务并分发，各域 Agent 基于 Spring AI 的 ReAct 循环自主调用工具执行流水线。两者的核心差异在于 Interview Coach 跑在 Claude Code 的托管环境里，OrbitQA 是纯自建的后端服务。

#### 2. 底层原理：SSE 单向长连接

前端用浏览器原生的 **EventSource API** 建立连接：

```java
// 后端 — Spring Boot SSE Emitter 实现
@GetMapping(value = "/api/agent/stream/{sessionId}", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> agentStream(@PathVariable String sessionId) {
    return Flux.create(sink -> {
        SseEmitters.add(sessionId, sink);  // 注册到 Emitter 池
        agentOrchestrator.execute(sessionId, sink);  // 启动 Agent 流水线
    });
}
```

前端 `new EventSource('/api/agent/stream/' + sessionId)` 建立连接，后端通过 `SseEmitter` 分阶段推送事件——每个阶段完成就 `send()` 一条带 `event:` 类型标记的 SSE 消息。前端根据 event 类型渲染不同 UI 组件（思考过程、工具调用、最终回答）。

**为什么不选 WebSocket？** 因为这个场景是单向的——Agent 执行过程中前端不需要发消息打断，SSE 比 WebSocket 更轻量，天然支持自动重连，不需要额外的 ping/pong 心跳。

#### 3. 实践应用

Interview Coach 的完整链路：

```
POST /api/questions → API Server(Python http.server)
  → interview_agent.py 主流程:
     阶段1: 题目解析 (classify_question → auto_tag → estimate_difficulty)
     阶段2: Answerer Agent 答题 (Anthropic API)
     阶段3: Reviewer Agent 审查 (JSON 解析 → PASS/FAIL)
     阶段4: 不合格返工 (最多2次)
     阶段5: Assembler 组装文档
     阶段6: QuestionManager 归档到题库 (questions/database/)
     阶段7: GenerateSite 生成静态页面 (docs/q/)
     阶段8: Git push 到 GitHub Pages
     阶段9: 返回统计结果
```

在 Claude Code 托管环境下，这个流程被抽象为 **10 阶段 Workflow**——每个阶段是确定性的，不依赖模型的自主决策。阶段 2 的 Answerer 调用是并行的（`parallel()`），阶段 3 的 Reviewer 也是并行的，质量门控是硬性的——FAIL 自动返工。

#### 4. 深入思考

**面试官可能的追问**：
- **SSE 连接断了怎么办？** EventSource 浏览器原生支持自动重连，后端通过 `Last-Event-ID` 头判断从哪里补推。OrbitQA 还做了心跳保活 + CAS 重连，连接恢复 < 15s。
- **多实例部署 SSE 怎么办？** OrbitQA 用了 Redis Pub/Sub 做跨节点广播——任意节点收到前端请求都能找到 Emitter 所在的节点。

## 2. RAG 是怎么存储和召回的？ {#q2}

### 🧠 联想记忆法

**口诀**：「段落切分五百字，五十重叠保语义；PgVector 存向量，余弦相似找 Top-K；查询先压缩重写，多查询扩展提召回。」

### 📖 深度解答

#### 1. 核心概念

RAG（Retrieval-Augmented Generation）= 检索增强生成，在 LLM 回答之前先从知识库中检索相关文档片段注入 Prompt，让模型基于"参考资料"回答而非凭空生成。

我在两个项目里做过 RAG：

| 项目 | 向量数据库 | 场景 |
|------|----------|------|
| OrbitQA（快手） | PostgreSQL pgvector | 支付域测试知识库，白盒测试代码上下文 |
| Interview Coach | 关键词 + 全文匹配（非向量） | 面经题库搜索，题目去重 |

#### 2. 底层原理：OrbitQA 的 RAG 管线

**（1）文档切分（Chunking）**

```python
# 段落 500 字符 + 50 字符重叠的滑动窗口
def chunk_document(text: str, chunk_size=500, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunk = text[start:end]
        chunks.append({"content": chunk, "start": start, "end": end})
        start += (chunk_size - overlap)  # 每次滑动 450 字符
    return chunks
```

为什么 500 字符？太大则检索粒度粗、噪声多；太小则语义碎片化。50 字符重叠保证跨 chunk 边界的知识点不被切断。

**（2）向量化 & 存储**

用 Spring AI 集成的 Embedding 模型（text-embedding-3-small）将每个 chunk 转为 1536 维向量，存入 PostgreSQL pgvector：

```sql
-- pgvector 扩展
CREATE EXTENSION vector;
CREATE TABLE knowledge_chunks (
    id SERIAL PRIMARY KEY,
    content TEXT,
    embedding vector(1536),     -- OpenAI 1536 维
    metadata JSONB
);
-- IVF-Flat 索引，加速近似检索
CREATE INDEX ON knowledge_chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
```

**（3）检索链路 — 两级优化**

第一级：**Query 压缩重写**。用户输入通常是自然语言，先让一个小模型把 Query 压缩为核心检索词（去掉口语化、提取关键词）。

第二级：**多查询扩展**。对原始 Query 生成 3-5 个语义变体，分别检索后合并去重。这一步是召回率 +55% 的关键——同一个知识点可能因表述不同而漏检。

```
用户问题: "支付的分布式锁怎么实现"
  → 压缩: "支付 分布式锁 实现方案"
  → 多查询扩展:
      1. "分布式锁 Redis 支付场景"
      2. "支付幂等性 并发控制 锁机制"
      3. "交易系统 分布式锁 Redisson"
  → 每条查询独立向量检索 Top-10
  → 合并去重 → 重排序 → 取 Top-5 注入 LLM Prompt
```

**（4）相似度计算**

pgvector 的余弦相似度：`cosine_similarity = (A·B) / (|A| × |B|)`。值越接近 1 越相似。`<=>` 运算符直接返回余弦距离（1 - 相似度）。

#### 3. 实践应用

Interview Coach 项目中没有用向量 RAG，因为题库检索用关键词匹配就够了。但 `search_index.py` 实现了题目去重的 MD5 hash 机制，`question_manager.py` 的全文搜索用关键词权重打分（题目命中 +3，标签命中 +2，分类命中 +1）。

#### 4. 深入思考

**面试官追问**：
- **pgvector vs 专用向量库（Milvus/Qdrant）？** pgvector 的优势是和业务数据库同库，减少运维复杂度；对于百万级以下向量够用。亿级以上才需要专用向量库。
- **召回率不够怎么优化？** ① 调整 chunk 大小 ② 混合检索（BM25 关键词 + 向量语义）③ 重排序模型（Reranker）

## 3. OCR 是怎么实现的（多模态输入）？ {#q3}

### 🧠 联想记忆法

**口诀**：「图片转文字靠多模态 API，语音转文字靠 ASR 模型，本质都是大模型的黑盒服务。」

### 📖 深度解答

#### 1. 核心概念

坦白说，我没有自己训练 OCR 模型。OrbitQA 和 Interview Coach 的"多模态输入"是指：
- **图片**：调用多模态大模型 API（GPT-4V / Claude Vision），让模型直接"看懂"截图中的代码、UI、错误日志
- **语音**：ASR（自动语音识别）接入，语音 → 文字 → 作为 Agent 的文本输入

核心思路是**不做底层模型训练，而是做模型服务的编排层**——这正是 Harness Engineering 的理念：不造轮子，驾驭轮子。

#### 2. 底层原理

**图片输入链路**：
```
用户截图(测试用例/报错/UI) → 前端 Base64 编码
  → POST /api/multimodal → 后端调用 Claude API (vision)
  → system prompt: "你是测试专家，分析这张截图中的问题"
  → 返回: 结构化的文字分析 → 注入后续 Agent 流程
```

**语音输入链路**：
```
用户语音 → 前端 MediaRecorder 录制 → Whisper API 语音转文字
  → 得到的文本 → 作为普通文本输入 Agent 流水线
```

#### 3. 实践应用

在这个架构里，多模态本质上是**输入适配层**——无论原始输入是什么格式，都在进入 Agent 流水线之前统一转成文本。流水线本身不感知输入的原始模态。

```java
// OrbitQA 中的多模态输入适配
public interface InputAdapter {
    String adapt(MultimodalInput input);  // 统一转文本
}

// 图片适配器
public class ImageAdapter implements InputAdapter {
    public String adapt(MultimodalInput input) {
        return visionModel.analyze(input.getImage(), """
            你是支付测试专家，分析图片中的：
            1. 是否为异常截图？2. 涉及哪个支付渠道？3. 可能的根因？
        """);
    }
}

// 语音适配器
public class VoiceAdapter implements InputAdapter {
    public String adapt(MultimodalInput input) {
        String text = whisperApi.transcribe(input.getAudio());
        return text;  // ASR 转换后直接当文本用
    }
}
```

#### 4. 深入思考

**为什么不自研 OCR/ASR？** ROI 太低。大厂（OpenAI/Google/阿里）的 OCR 和 ASR API 准确率已经很高，自研模型需要标注数据 + 训练算力 + 持续迭代，对于测试提效这个业务目标来说，投入产出不成正比。我们的核心壁垒在编排层——怎么把多模态输入和 RAG 知识库、Agent 工具链串起来——而不是模型本身。

## 4. UUID 的实现和维度是什么？ {#q4}

### 🧠 联想记忆法

**口诀**：「sessionId 标记一次对话，messageId 标记每条消息，前端生成 UUID v4 传过来，后端不重复生成。」

### 📖 深度解答

#### 1. 核心概念

UUID 在我的项目里有两个维度：

| 维度 | ID | 生成方 | 作用 | 生命周期 |
|------|-----|--------|------|---------|
| **会话维度** | sessionId | 前端生成（UUID v4） | 标识一次完整的 Agent 对话 | 从用户打开对话到关闭/超时 |
| **消息维度** | messageId | 前端生成（UUID v4） | 标识会话中的每条消息 | 单次请求-响应 |

#### 2. 底层原理

**为什么用前端生成而不是后端生成？**

前端生成 sessionId 的核心原因是：SSE 连接建立时需要 sessionId 作为路由 Key。如果后端生成，前端需要先发一个 POST 请求建 session，拿到 sessionId 后再建 SSE 连接——多一次往返。前端直接 `crypto.randomUUID()` 生成，SSE 连接请求带上即可。

```javascript
// 前端
const sessionId = crypto.randomUUID();  // 例如 "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
const eventSource = new EventSource(`/api/agent/stream/${sessionId}`);
```

```java
// 后端 — sessionId 作为 Emitter 池的 Key
ConcurrentHashMap<String, SseEmitter> emitters = new ConcurrentHashMap<>();

@GetMapping("/api/agent/stream/{sessionId}")
public SseEmitter stream(@PathVariable String sessionId) {
    SseEmitter emitter = new SseEmitter(300_000L);  // 5 分钟超时
    emitters.put(sessionId, emitter);
    emitter.onCompletion(() -> emitters.remove(sessionId));
    emitter.onTimeout(() -> emitters.remove(sessionId));
    return emitter;
}
```

#### 3. 实践应用

在 OrbitQA 中，sessionId 不仅在 SSE 层做路由，还在 Redis 中作为上下文状态 Key：

```
redis key: "agent:session:{sessionId}"  → 存储对话历史、中间状态
redis key: "agent:session:{sessionId}:lock"  → 分布式锁，防并发写入
```

在 Interview Coach 中，题目归档时用 `q{序号:04d}` 作为题目 ID（如 q0001），这是业务维度的 ID，区别于 sessionId 的技术维度。

#### 4. 深入思考

**面试官追问：UUID v4 vs 雪花算法？** UUID v4 是随机生成的 128 位值，优势是前端可独立生成、无碰撞风险。雪花算法是趋势递增的 64 位 Long，优势是数据库索引友好（B+Tree 有序插入 vs UUID 的随机插入导致页分裂）。对于会话 ID 这种不需要持久化索引的场景，UUID v4 最合适。

## 5. 为什么用多模块 Agent 而不是多 Agent？ {#q5}

### 🧠 联想记忆法

**口诀**：「Multi-Agent 协商开销大、耗时长，多模块 Agent 确定性强、流水线效率高——用编排代替协商。」

### 📖 深度解答

#### 1. 核心概念

**多 Agent（Multi-Agent）**：每个 Agent 是独立 LLM 实例，Agent 之间通过对话/协商来协作——比如 Agent A 说"我需要查数据库"，Agent B 说"我帮你查"，Agent C 提出不同意见。

**多模块 Agent（Single Agent + Multi-Module）**：一个核心 Agent 引擎，内部按职责拆分模块（Answerer / Reviewer / Assembler），模块间通过确定性流程串联，不协商。

#### 2. 底层原理：为什么不用 Multi-Agent？

我在 OrbitQA 早期尝试过 Multi-Agent 模式——让不同的域 Agent 互相协商。结果很现实：

| 指标 | Multi-Agent | 多模块 Agent |
|------|------------|-------------|
| 单次任务耗时 | 30-60s（协商轮次不可控） | 8-15s（确定性流水分发） |
| Token 消耗 | 3-5x（Agent 间对话也消耗） | 1x（模块间用结构化数据传递） |
| 结果确定性 | 低（协商路径不同导致结果差异） | 高（同一流水线的输出一致） |
| 并发可行性 | 难（协商需要同步等待） | 易（PMO 分发后各模块独立执行） |

**协商开销不可接受**是最核心的原因。Agent A 提问 → Agent B 回答 → Agent A 追问 → Agent C 插话……这个过程对用户是不可见的黑盒，但耗时是实打实的。对于支付测试场景，用户等 60 秒和等 10 秒是天壤之别。

**本质上的设计选择**：我把智能放在模块内部（Answerer 怎么组织答案的智能），把控制流放在模块之间（什么时候调 Reviewer、什么时候返工），用 Harness Engineering 的编排替代 Agent 之间的协商——编排是确定性的，协商是概率性的。

#### 3. 实践应用

OrbitQA 的 PMO（Project Management Office）模式：
```
PMO 编排层（不参与推理，只做路由和分发）
  ├── 支付域 Agent（分析支付相关问题，调用支付工具）
  ├── 订单域 Agent（分析订单相关问题，调用订单工具）
  ├── 物流域 Agent（分析物流相关问题，调用物流工具）
  └── 通用 Agent（兜底，处理跨域问题）
```

PMO 本身不做 LLM 推理（规则匹配 + 简单的意图分类），只有域 Agent 才是 LLM 实例。PMO 把任务拆分后分发给对应的域 Agent——各 Agent 之间不通信不协商，各做各的，结果汇总回 PMO。

#### 4. 深入思考

**面试官追问：什么场景适合 Multi-Agent？** 开放性探索任务，比如"设计一个系统架构"——需要多个视角互相碰撞。或者需要多角色对抗的场景，比如"Agent A 写代码，Agent B Review"，但这个也可以用流水线模式替代（写完 → 审）。

## 6. 没有用 Spring AI 等 Agent 框架，Agent 之间怎么传递数据？ {#q6}

### 🧠 联想记忆法

**口诀**：「向量机做中间层，sessionId 串上下文，结构化 JSON 传结果——不靠框架靠约定。」

### 📖 深度解答

#### 1. 核心概念

先澄清：OrbitQA 项目**确实用了 Spring AI**，简历里写了。技术栈是 `Spring AI + Reactor + PostgreSQL pgvector + Redis + MCP Protocol`。

Interview Coach 项目没有用 Spring AI 等框架，因为它是跑在 Claude Code 托管环境里的——Agent 的调度由 Claude Code 的 Workflow 引擎完成。

两个项目的数据传递思路是一致的：

#### 2. 底层原理：向量机 + sessionId 模式

**核心思路：用 sessionId 做上下文 Key，用 Redis 做中间缓存**

```
                ┌─────────────┐
                │   Redis     │
                │ session:{id}│  ← 所有模块共享的上下文
                └──────┬──────┘
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    ┌──────────┐ ┌──────────┐ ┌──────────┐
    │ Answerer │ │ Reviewer │ │Assembler │
    └──────────┘ └──────────┘ └──────────┘
```

**具体实现（Interview Coach 的 Python 版）**：

```python
class InterviewCoach:
    def process_single(self, question, index):
        # 阶段1：答题 → 输出结构化 answer
        answer = self.answerer.call(...)
        
        # 阶段2：审查 → input = answer (上一个模块的输出)
        review_raw = self.reviewer.call(..., answer)
        parsed = self._parse_review(review_raw)  # JSON 解析
        
        if parsed["result"] == "PASS":
            return {"index": index, "question": question,
                    "answer": answer, "review": "PASS"}
        else:
            # 不合格 → answer 附上审查反馈 → 重答
            answer = self.answerer.call(..., f"{question}\n\n[修正]: {parsed}")
```

关键设计：
1. **模块间传递的是结构化 JSON，不是自然语言**：`{"result": "PASS", "failed_items": [...], "specific_issues": "..."}`，解析确定性高、不会歧义。
2. **下游模块通过参数接收上游输出**：不依赖全局状态，也不依赖框架的上下文管理。
3. **在 OrbitQA 中加了一层 Redis**：因为多实例部署需要跨节点共享上下文，`Redis session:{sessionId}` 存对话历史和中间状态。

#### 3. 为什么没用更多 Agent 框架？

**Spring AI**：OrbitQA 用了，但只用了它的 Tool Calling 和 Embedding 能力。它的 Agent 编排比较"重"——需要定义 State、定义 Transition，对于我这种流水线型任务来说，过度抽象了。

**LangChain**：太"魔法"了，Chain 套 Chain 调试困难。而且 LangChain 的 Python 生态和我的 Java 后端不好集成。

**自己写 vs 用框架的权衡**：当你的流程是**确定性**的（解析 → 答题 → 审查 → 组装），自己写就是几十行的 if-else + 函数调用，引入框架反而增加了学习曲线和调试复杂度。但当流程变得动态（Agent 自主决定调用哪些工具、以什么顺序），框架的 ReAct 循环就有价值了——这也是为什么 OrbitQA 用了 Spring AI 的 Tool Calling。

#### 4. 深入思考

**面试官追问：不用框架的代码可维护性怎么保证？** 三个原则：① 每个模块只做一件事（Answerer 不管审查，Reviewer 不管组装）② 模块间接口用 dataclass/JSON 而非自由文本 ③ 管线编排独立于模块实现——换掉 Answerer 的实现不影响 Reviewer。

## 7. 项目里哪些是 AI 完成，哪些是自己实现的？ {#q7}

### 🧠 联想记忆法

**口诀**：「AI 负责内容生成（不可预测），人负责流程编排（确定性工程）——这就是工作流模式 vs Agent 模式的核心区别。」

### 📖 深度解答

#### 1. 核心概念

这是一个很好的架构问题。我用一个比喻：**AI 是"车间里的工人"，我是"流水线的设计师"**。AI 不决定做什么、按什么顺序做——那些是我定义的工作流。

#### 2. 底层原理：工作流模式 vs Agent 模式

| | Agent 模式 | 工作流模式（我的选择） |
|---|---|---|
| 控制权 | LLM 自主决定下一步 | 开发者预先定义流程 |
| 适用场景 | 开放性任务 | 结构化任务（如面试答题） |
| 可靠性 | 概率性 | 确定性 |
| 调试难度 | 高（LLM 黑盒决策） | 低（每步可单独测试） |

我在 Interview Coach 中选择**工作流模式**——或者叫"工作树"（因为阶段 2 有并行分支）：

```
阶段1: 题目解析（确定性规则：关键词分类 + 正则标签 + 难度估算）
  ↓
阶段2: 并行答题（AI 完成 — 每道题一个 Agent，LLM 按规则生成答案）
  ↓   ↓   ↓
  ↓   ↓   ↓  ← 树状：N 道题 → N 个并行 Agent
  ↓   ↓   ↓
阶段3: 逐个审查（AI 完成 — Reviewer Agent 按检查清单审核）
  ↓
阶段4: 不合格返工（确定性规则：最多 2 次重试）
  ↓
阶段5: 文档组装（AI 完成 — Assembler 排版）
  ↓
阶段6-10: 归档/生成站点/推送（我自己写的 Python 脚本 — 确定性文件操作 + git 命令）
```

#### 3. 自己实现的部分（非 AI）

**全部自己写的内容**：

| 模块 | 文件 | 实现方式 |
|------|------|---------|
| 题目分类器 | `question_manager.py` 中的 `classify_question()` | 13 个分类 × 大量关键词 → 打分匹配 |
| 自动标签 | `auto_tag()` | 正则表达式规则库 |
| 难度估算 | `estimate_difficulty()` | 关键词权重计分 |
| 题库索引管理 | `QuestionManager` 类 | JSON 读写 + MD5 去重 + 文件落盘 |
| API 服务器 | `api_server.py` | Python `http.server`，10+ REST 端点 |
| 站点生成器 | `generate_site.py` | Markdown → HTML，180+ 行 CSS |
| SSE Emitter 池 | OrbitQA | Java ConcurrentHashMap + SseEmitter 管理 |
| 分布式锁 | OrbitQA | Redis Pub/Sub + Redisson + CAS 重连 |
| 前端页面 | HTML/CSS/JS | 题库搜索、知识图谱、复习打卡 |

**AI 完成的部分**：答案内容生成、质量审查、文档排版。这些都是"内容生成"任务——不可预测、需要语言理解能力，适合 AI。

#### 4. 深入思考

**为什么要做这种划分？** 因为 LLM 擅长"生成"，不擅长"精确"。让 LLM 去做文件去重（MD5 精确匹配），可能它编了一个不存在的文件路径。各司其职——LLM 做创造性的内容工作，确定性逻辑留给代码。

## 8. 回复是整体返回前端还是分阶段流式？ {#q8}

### 🧠 联想记忆法

**口诀**：「分阶段 SSE 推送，每个事件带类型标记；前端按类型分段渲染，不用等全部完成。」

### 📖 深度解答

#### 1. 核心概念

**分阶段流式推送**——不是等全部答案完成才返回，而是每完成一个阶段就推送一个 SSE 事件。

#### 2. 底层原理

```java
// 后端 — 分阶段推送
sink.next(ServerSentEvent.builder()
    .id("1")
    .event("phase")              // 阶段事件
    .data("{\"phase\": \"thinking\", \"message\": \"正在分析题目...\"}")
    .build());

sink.next(ServerSentEvent.builder()
    .id("2")
    .event("tool_call")          // 工具调用事件
    .data("{\"tool\": \"search_knowledge\", \"args\": {...}}")
    .build());

sink.next(ServerSentEvent.builder()
    .id("3")
    .event("answer_chunk")       // 答案流式片段
    .data("{\"delta\": \"分布式锁的核心是...\"}")
    .build());

sink.next(ServerSentEvent.builder()
    .id("4")
    .event("done")               // 完成事件
    .data("{\"total_tokens\": 3500, \"duration_ms\": 8200}")
    .build());
```

前端按 event 类型做不同渲染：
- `phase` → 更新进度条、显示当前阶段名称
- `tool_call` → 显示"正在查询知识库..."
- `answer_chunk` → 打字机效果追加文本
- `done` → 显示统计信息、停止加载动画

**为什么不整体返回？** 用户体验——Agent 执行可能需要 8-15 秒，如果等全部完成再显示，用户看着空白页面以为卡死了。分阶段推送让用户感知到"系统在工作"。

#### 3. 实践应用

`api_server.py` 虽然是同步的（先 run Agent 再返回），但在 OrbitQA 的 Java 版本中是完全异步的——Spring WebFlux + Reactor，`Flux<ServerSentEvent>` 实现背压。并发用户数可以到数百。

```java
// OrbitQA — WebFlux 异步 SSE
@GetMapping(value = "/stream/{sessionId}", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> stream(@PathVariable String sessionId) {
    return Flux.create(emitter -> {
        agentService.execute(sessionId, new SseEmitterAdapter(emitter));
    }, FluxSink.OverflowStrategy.LATEST);  // 背压策略：丢弃旧事件，保留最新
}
```

#### 4. 深入思考

**面试官追问：SSE 和 WebSocket 怎么选？** SSE 单向（服务端 → 客户端）、HTTP 协议、自动重连、更轻量。WebSocket 双向、独立协议、需要心跳保活。如果只需要服务端推送（不需要客户端中途打断 Agent），SSE 完全够用。

## 11. 使用 AI 时怎么排查错误？AI 开发出错了怎么办？ {#q11}

### 🧠 联想记忆法

**口诀**：「埋点打日志覆盖全链路，单元测试保关键逻辑，Postman 手动验接口。」

### 📖 深度解答

#### 1. 核心概念

AI 开发的代码有两个特征：① 开发速度快（几分钟出几百行），② 但正确性不确定。所以我的策略是**信任但验证（Trust but Verify）**。

#### 2. 底层原理：三层保障体系

**第一层：埋点 + 日志（可观测性）**

以 OrbitQA 的管理端为例，我在 Agent 流水线的每个关键节点都做了埋点：

```
[埋点] Agent 启动 → sessionId, userId, timestamp
[埋点] PMO 任务分发 → taskId, domain, 分发耗时
[埋点] RAG 检索 → query, 召回 chunk 数, 相似度 top-5
[埋点] Tool 调用 → toolName, 参数摘要, 调用耗时
[埋点] Agent 完成 → sessionId, 总耗时, token 消耗, 审查结果
```

这些埋点的数据通过 Grafana 大盘展示，出问题的时候能快速定位是哪个节点耗时异常、哪个工具调用失败。

**第二层：单元测试**

AI 写的代码必须带单元测试，而且我会要求覆盖率 > 80%。比如 `question_manager.py` 中的去重、分类、标签方法，每一个都有对应的测试场景：

```python
# AI 生成的代码
def classify_question(question: str) -> str:
    scores = {}
    for cat, keywords in CATEGORY_KEYWORDS.items():
        scores[cat] = sum(1 for kw in keywords if kw.lower() in question.lower())
    return max(scores, key=scores.get) if scores else "java"

# 我要求 AI 同时生成的测试
def test_classify_redis_question():
    assert classify_question("Redis 分布式锁怎么实现") == "redis"

def test_classify_empty_question():
    assert classify_question("") == "java"  # 兜底分类

def test_classify_mixed_keywords():
    result = classify_question("Spring Boot 和 MySQL 的事务管理")
    # spring 和 mysql 关键词都命中，看哪个匹配更多
    assert result in ["spring", "mysql"]
```

**第三层：手动接口验证**

单元测试通过 ≠ 接口真的能用。对于前后端对接的关键接口（SSE 流式推送、题库 API 的搜索/筛选），我会用 Postman 或 Curl 逐一手动测试：

```bash
# 验证题库搜索 API
curl "http://localhost:8765/api/search?q=分布式锁" | jq '.results | length'

# 验证 SSE 推送格式
curl -N "http://localhost:8765/api/agent/stream/test-session-001"
```

#### 3. 实践应用：AI 代码出错的真实案例

在 Interview Coach 开发中，AI 生成的 `_parse_review` 方法最初是这样的：

```python
# AI 原始输出（有 bug）
def _parse_review(text):
    json_str = text[text.find('{'):text.rfind('}')+1]  # Bug: 如果 json 中有嵌套 {} 会截断
    return json.loads(json_str)
```

这个在解析带嵌套 JSON 的 Reviewer 输出时会失败。我发现后加了 try-catch + fallback 逻辑：

```python
def _parse_review(text):
    try:
        start, end = text.find('{'), text.rfind('}') + 1  # rfind 找最后一个 }
        if start >= 0 and end > start:
            return json.loads(text[start:end])
    except (json.JSONDecodeError, ValueError):
        pass  # 不抛异常，走 fallback
    # 回退：从文本推断
    if "PASS" in text.upper():
        return {"result": "PASS", ...}
    return {"result": "FAIL", ...}
```

#### 4. 深入思考

**面试官追问：AI 生成代码的 bug 特征？** ① 边界条件处理不够（空输入、超长输入）② 类型转换逻辑不严谨（以为返回的是 String，实际是 dict）③ 异常处理过于宽松（`except Exception: pass` 吞掉关键错误）。这些我通过 code review + 测试 + 埋点三层兜底。

## 12. Vue 的响应式数据可以响应成员变化吗？ {#q12}

### 🧠 联想记忆法

**口诀**：「`ref` 包简单值，`.value` 触发响应；`reactive` 包对象，直接 `.属性` 就能响应；新增/删除属性要用 `reactive` 而不是 `ref` 的普通对象。」

### 📖 深度解答

#### 1. 核心概念

Vue 3 的两大响应式 API：

**`ref`**：包装基本类型（string、number、boolean），通过 `.value` 访问和修改，模板中自动解包。

**`reactive`**：包装对象类型，直接访问和修改属性即可触发响应。基于 ES6 的 `Proxy` 实现。

#### 2. 底层原理

`ref` 的内部本质也是 `reactive`——`ref(5)` 等价于 `reactive({value: 5})`。模板中 `<div>{{count}}</div>` 不需要 `.value` 是因为 Vue 编译器自动处理了。

`reactive` 用 `Proxy` 拦截对象的所有 get/set/deleteProperty 操作，所以**新增和删除属性也能响应**（这是 Vue 3 相比 Vue 2 的最大改进——Vue 2 的 `Object.defineProperty` 做不到这一点）。

```javascript
// Vue 3 reactive — 新增属性可以响应
const state = reactive({name: "zhangsan"});
state.age = 25;  // ✅ 可以响应（Proxy 的 set 拦截到了新增属性）
state.name = "lisi";  // ✅ 可以响应（普通修改）

// Vue 2 data — 新增属性不能响应
// this.newProp = 'xxx';  // ❌ 不响应，需要用 Vue.set()
```

#### 3. 实践应用

在我项目中（虽然是后端为主，但 Interview Coach 的前端页面都是 Vue 写的）：

```javascript
// questions.js — 题库搜索页
const state = reactive({
    questions: [],       // 题目列表
    loading: false,      // 加载状态
    selectedCategory: '',// 选中的分类
    searchKeyword: ''    // 搜索关键词
});

// 直接修改属性就能触发视图更新
state.questions = await fetchQuestions();
state.selectedCategory = 'java';  // 触发列表重新筛选
state.loading = false;            // 触发加载动画关闭
```

`ref` vs `reactive` 的选择：单个值用 `ref`，一组相关状态（对象）用 `reactive`。其实在 Vue 3 Composition API 里，用 `ref` 更多——因为 `.value` 解包规则在解构时不会丢失响应性，而 `reactive` 解构需要用 `toRefs`。

#### 4. 深入思考

**Vue 3 响应式的局限性**：`reactive` 不能用于基本类型、不能整体替换对象（`state = newObj` 会丢失响应性）、`Map/Set` 等集合类型要用独立的 API。这也是为什么面试中会问这个问题——考察对 Proxy 机制的理解程度。

## 13. 二叉树遍历（算法题） {#q13}

### 🧠 联想记忆法

**口诀**：「前序根左右，中序左根右，后序左右根，层序队列走。递归三行代码，迭代记住栈。」

### 📖 深度解答

#### 1. 核心概念

二叉树遍历的四种方式都是 **O(n)** 时间（每个节点访问一次）和 **O(h)** 空间（递归栈深度，h 是树高，最坏 O(n)）。

#### 2. ACM 模式完整代码（Java）

```java
import java.util.*;

// 先手动组装树，再遍历
public class Main {
    // 树节点定义
    static class TreeNode {
        int val;
        TreeNode left;
        TreeNode right;
        TreeNode(int val) { this.val = val; }
    }

    public static void main(String[] args) {
        // === 第一步：手动组装二叉树 ===
        // 构造这棵树:
        //       1
        //      / \
        //     2   3
        //    / \   \
        //   4   5   6
        TreeNode root = new TreeNode(1);
        root.left = new TreeNode(2);
        root.right = new TreeNode(3);
        root.left.left = new TreeNode(4);
        root.left.right = new TreeNode(5);
        root.right.right = new TreeNode(6);

        System.out.println("前序: " + preorder(root));
        System.out.println("中序: " + inorder(root));
        System.out.println("后序: " + postorder(root));
        System.out.println("层序: " + levelOrder(root));
    }

    // === 前序遍历：根 → 左 → 右 ===
    static List<Integer> preorder(TreeNode root) {
        List<Integer> res = new ArrayList<>();
        if (root == null) return res;
        Deque<TreeNode> stack = new ArrayDeque<>();
        stack.push(root);
        while (!stack.isEmpty()) {
            TreeNode node = stack.pop();
            res.add(node.val);
            // 先压右再压左（栈是 LIFO，取出来时先左后右）
            if (node.right != null) stack.push(node.right);
            if (node.left != null) stack.push(node.left);
        }
        return res;
    }

    // === 中序遍历：左 → 根 → 右 ===
    static List<Integer> inorder(TreeNode root) {
        List<Integer> res = new ArrayList<>();
        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode curr = root;
        while (curr != null || !stack.isEmpty()) {
            // 一路向左走到底
            while (curr != null) {
                stack.push(curr);
                curr = curr.left;
            }
            curr = stack.pop();
            res.add(curr.val);
            curr = curr.right;
        }
        return res;
    }

    // === 后序遍历：左 → 右 → 根 ===
    static List<Integer> postorder(TreeNode root) {
        List<Integer> res = new ArrayList<>();
        if (root == null) return res;
        Deque<TreeNode> stack = new ArrayDeque<>();
        TreeNode curr = root, prev = null;
        while (curr != null || !stack.isEmpty()) {
            while (curr != null) {
                stack.push(curr);
                curr = curr.left;
            }
            curr = stack.peek();
            // 如果右子树为空或已访问过，才能访问当前节点
            if (curr.right == null || curr.right == prev) {
                res.add(curr.val);
                stack.pop();
                prev = curr;
                curr = null;
            } else {
                curr = curr.right;
            }
        }
        return res;
    }

    // === 层序遍历：BFS ===
    static List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> res = new ArrayList<>();
        if (root == null) return res;
        Queue<TreeNode> q = new LinkedList<>();
        q.offer(root);
        while (!q.isEmpty()) {
            int size = q.size();
            List<Integer> level = new ArrayList<>();
            for (int i = 0; i < size; i++) {
                TreeNode node = q.poll();
                level.add(node.val);
                if (node.left != null) q.offer(node.left);
                if (node.right != null) q.offer(node.right);
            }
            res.add(level);
        }
        return res;
    }
}
```

#### 3. 回答思路

面试时按这个结构讲：
1. **先组装树**：手动 new 节点 + 连指针（5-6 行代码）
2. **选遍历方式**：递归简单（3 行），面试官可能让写迭代版
3. **前序 = 栈 + 先压右再压左**：一句话说清楚为什么
4. **中序 = 一路向左 + 弹栈访问**：关键点
5. **层序 = BFS + for(size) 分层**：用于按层输出

**ACM 模式下特别注意**：手写 import（`java.util.*`），`TreeNode` 要自己定义，类名是 `Main`。

#### 4. 时空复杂度

| 遍历 | 时间 | 空间（递归） | 空间（迭代） |
|------|------|------------|------------|
| 前序 | O(n) | O(h) → O(n) | O(h) → O(n) |
| 中序 | O(n) | O(h) → O(n) | O(h) → O(n) |
| 后序 | O(n) | O(h) → O(n) | O(h) → O(n) |
| 层序 | O(n) | — | O(w) ≤ O(n) |

最坏空间 O(n) 出现在斜树（链表），平均 O(log n)。

## 15. 爬楼梯方法数（算法题） {#q15}

### 🧠 联想记忆法

**口诀**：「爬楼梯就是斐波那契——`dp[i] = dp[i-1] + dp[i-2]`，滚动变量三个数 O(n) 时间 O(1) 空间。」

### 📖 深度解答

#### 1. 核心概念

**题目**：爬 n 阶楼梯，每次爬 1 或 2 阶，有多少种方法？

**本质**：斐波那契数列。到第 n 阶 = 到第 n-1 阶（再爬 1 阶）+ 到第 n-2 阶（再爬 2 阶）。

#### 2. 答案

```java
public int climbStairs(int n) {
    if (n <= 2) return n;  // 1阶→1种, 2阶→2种
    
    int prev2 = 1;  // dp[1]
    int prev1 = 2;  // dp[2]
    for (int i = 3; i <= n; i++) {
        int curr = prev1 + prev2;
        prev2 = prev1;
        prev1 = curr;
    }
    return prev1;
}
```

#### 3. 时空复杂度分析

| 方案 | 时间 | 空间 | 说明 |
|------|------|------|------|
| 递归（不剪枝） | O(2^n) | O(n) | 大量重复计算，不可用 |
| 递归 + 记忆化 | O(n) | O(n) | 用 HashMap 存中间结果 |
| DP 数组 | O(n) | O(n) | `dp[i] = dp[i-1] + dp[i-2]` |
| **滚动变量** ✅ | **O(n)** | **O(1)** | 只保留前两个状态 |

**能不能优化到 O(log n)？** 可以！用**矩阵快速幂**：

```
[F(n)  ]   [1 1]^(n-1)   [F(1)]
[F(n-1)] = [1 0]       × [F(0)]
```

矩阵的 n 次幂可以用快速幂 O(log n) 算。但在 n ≤ 45（不会溢出 int）的面试场景下，O(n) 滚动变量足够了。n 很大时（> 10^9）才需要矩阵快速幂 + 取模。

#### 4. 回答思路

面试时的完整表达：

「这是一道经典的 DP 题，本质是斐波那契。我先说状态定义：`dp[i]` 表示爬到第 i 阶的方法数。转移方程：`dp[i] = dp[i-1] + dp[i-2]`，因为最后一步可以跨 1 阶或 2 阶。初始值：`dp[1] = 1, dp[2] = 2`。

**时间复杂度 O(n)**，因为遍历一次。
**空间复杂度可以优化到 O(1)**：因为每个状态只依赖前两个，用两个变量滚动就行，不需要 dp 数组。

如果面试官继续问：可以用**矩阵快速幂 O(log n)** 进一步优化，但这道题的 n 规模通常不大，O(n) 足够了。

如果变体是"每次可以爬 1/2/3 阶"：`dp[i] = dp[i-1] + dp[i-2] + dp[i-3]`，三个变量滚动。

如果变体是"不能连续跨 2 阶两次"：需要多一维状态表示'上一步是否跨了 2 阶'。」
