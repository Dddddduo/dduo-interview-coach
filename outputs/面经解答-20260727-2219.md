### Q2: 你为什么会想到做这个Coding Agent项目？

**联想记忆法**: 痛点驱动 = 重复劳动 + 协同低效 + 知识流失 → 用AI Agent自动化

**深度解答**:

**核心概念**: Coding Agent项目的出发点源于快手实习期间的实际痛点——测试团队每天面临大量重复性测试任务，知识分散在多个团队成员的大脑中，缺乏系统化的沉淀和复用机制。

**底层原理**:
- **重复劳动问题**：白盒测试中有大量回归性、模式化的测试用例需要编写和执行，人工完成效率低且容易遗漏

- **知识流失问题**：资深测试人员的经验和业务知识难以有效传承，人员流动导致知识断层

**实践应用**：OrbitQA星轨平台应运而生——通过AI Agent来自动化测试任务的分发、执行和结果汇总，将测试人员的精力从重复劳动中解放出来，专注于更有价值的测试设计和问题分析。

**回答思路**：从实际痛点出发，说明项目动机不是为了"追AI潮流"，而是切实解决团队面临的问题。

### Q5-Q7: Agent系统架构、执行流程、核心能力

**深度解答**:

**系统架构（Q5）**：OrbitQA采用**PMO编排与域Agent执行分离的双层架构**。

- **PMO层**（编排层）：负责任务接收、拆分、分发和结果聚合。PMO Agent理解测试需求的语义，将其拆解为可执行的子任务。
- **域Agent层**（执行层）：每个域Agent专注于特定领域（如支付渠道测试、接口测试、白盒测试），基于Spring AI实现ReAct循环，自主调用工具执行测试流水线。

**执行流程（Q6）**：
1. 用户输入测试需求 → PMO Agent解析需求
2. PMO拆解为子任务 → 分配给对应域Agent
3. 域Agent执行ReAct循环：思考→调用工具→观察结果→再思考
4. 域Agent返回执行结果 → PMO聚合 → 生成测试报告

**核心能力（Q7）**：Agent的真正核心能力不是"智能"，而是**自主决策与工具调用的闭环**——能够在不确定的环境中，通过感知-思考-行动的循环，自主完成目标任务。

### Q8: Agent为什么需要调用工具？

**联想记忆法**: 工具 = LLM的双手——语言模型只能"说"，工具让它能"做"

**深度解答**:

**核心概念**: LLM本身只是一个文本生成模型，它无法与外部世界交互。工具调用（Tool Use / Function Calling）让LLM突破了纯文本生成的限制，获得执行实际动作的能力。

**底层原理**:
1. **LLM的能力边界**：LLM只能生成token，无法查询数据库、发送请求、操作文件、执行代码
2. **MCP协议**：通过标准化协议，LLM发现可用工具并调用，工具返回结果后继续推理
3. **ReAct循环**：思考→调用工具→观察结果→再思考，形成完整的Agent闭环

**实践应用**：在OrbitQA中，Agent调用测试执行工具、RAG检索工具、报告生成工具等，完成从测试到报告的完整流程。

### Q10: 如何避免上下文污染？

**深度解答**:

**核心概念**: 上下文污染指无关或过期的上下文内容影响LLM的推理质量。

**解决方案**：
1. **上下文窗口管理**：控制每次输入的信息量，避免填充过多无用信息
2. **记忆分层**：工作记忆（当前会话）、情景记忆（历史交互摘要）、语义记忆（长期知识）
3. **定期清理**：会话达到一定长度后，主动进行摘要和裁剪
4. **隔离设计**：不同Agent使用独立上下文，避免交叉污染
5. **锚定迭代摘要**：保留核心任务和关键约束，丢弃历史细节

## 第二部分：RAG 与 AI 基础设施

### Q11: Embedding为什么能够实现语义搜索？

**深度解答**:

**核心概念**: Embedding（嵌入）将文本转换为高维向量空间中的点，语义相近的文本在向量空间中的距离也相近。余弦相似度衡量两个向量的夹角，角度越小表示语义越相似。

**底层原理**：
1. **向量空间模型**：每个文本片段被映射为一个固定维度的向量（如768维或1536维）
2. **语义映射**：训练过程中，模型学习到"上下文相近的词语在向量空间中的距离更近"
3. **余弦相似度**：cos(A,B) = A·B / |A||B|，值越接近1表示语义越相似

**实践应用**：在OrbitQA中，使用PgVector作为向量数据库，embedding模型将测试文档转化为向量，用户查询也转化为向量，通过余弦检索找到最相关的测试文档片段，召回率提升55%。

### Q12: Chunk一般如何切分？

**深度解答**:

**核心概念**: Chunking（文本分块）是RAG系统的关键预处理步骤，将长文本切割为可检索的片段。

**常见切分策略**：
1. **固定大小切分**：按token数或字符数固定切分（如500字符/块）
2. **语义切分**：按段落、句子边界切分，保持语义完整性
3. **递归切分**：先按段落切，过长的再递归切分
4. **重叠切分**：相邻chunk之间有重叠（如50字符），避免切断裂关键信息

**实践应用**：在OrbitQA中采用段落500字符 + 50重叠切分策略，兼顾检索精度和语义完整性。

## 第五部分：数据结构与算法

### Q28: 哈希表为什么查找速度快？

**深度解答**:

**核心概念**: 哈希表通过哈希函数将key直接映射为数组下标，实现O(1)的平均查找时间复杂度。

**底层原理**:
- 哈希函数计算key的哈希值，通过取模运算映射到数组位置
- 理想情况下，每个key映射到不同位置，查找时直接定位到目标
- 哈希冲突时，通过链地址法或开放地址法解决

**回答思路**：从哈希函数的映射机制和数组随机访问两个角度说明O(1)时间复杂度的来源。

---

### Q29: 哈希冲突解决

**深度解答**:

1. **链地址法**（Seperate Chaining）：同一槽位的元素用链表存储，Java HashMap使用
2. **开放地址法**：冲突时寻找下一个空位，包括线性探测、二次探测、双重哈希
3. **再哈希法**：使用多个哈希函数，冲突时切换
4. **公共溢出区**：冲突元素放入公共区域

---

### Q30: 堆是什么数据结构？

**深度解答**:

**核心概念**: 堆是一种完全二叉树，分为大顶堆（父节点≥子节点）和小顶堆（父节点≤子节点）。用数组存储，父子节点通过下标计算（i的左子=2i+1，右子=2i+2，父=(i-1)/2）。

**用途**：优先级队列、堆排序、Top K问题、中位数维护、Dijkstra最短路径

### Q55-Q57: 去重有序集合

**核心概念**: 题目描述的是LinkedHashSet（Java）或OrderedSet——底层使用哈希表+双向链表，实现O(1)的插入、删除、查找。

**删除复杂度**: 哈希表O(1)找到节点 + 双向链表O(1)删除 = O(1)整体

**优化方案**: 使用跳表（Skip List）、一致性哈希改进版、B+树变体

### Q62: 算法 LC33 搜索旋转排序数组

**联想记忆法**: 旋转数组二分搜，半边有序不用愁

**深度解答**:

**核心思路**: 旋转数组从中点一分为二，至少有一半是严格升序的。先判断哪一半有序，再检查target是否在该有序区间内。

**Java实现**:
```java
public int search(int[] nums, int target) {
    int left = 0, right = nums.length - 1;
    while (left <= right) {
        int mid = left + (right - left) / 2;
        if (nums[mid] == target) return mid;
        
        if (nums[left] <= nums[mid]) {  // 左半有序
            if (nums[left] <= target && target < nums[mid]) {
                right = mid - 1;
            } else {
                left = mid + 1;
            }
        } else {  // 右半有序
            if (nums[mid] < target && target <= nums[right]) {
                left = mid + 1;
            } else {
                right = mid - 1;
            }
        }
    }
    return -1;
}
```

**复杂度**: O(log n) 时间，O(1) 空间

## 第六部分：MySQL 与数据库

### Q31: MySQL InnoDB 索引数据结构

**深度解答**:

**核心概念**: InnoDB使用B+树作为索引数据结构。B+树是多路平衡搜索树，所有数据存储在叶子节点，非叶子节点只存储键值用于路由。

**底层原理**：
- 每个节点对应一个磁盘页（16KB），一次I/O可读取大量键值
- 叶子节点通过指针相连形成有序链表，支持高效范围查询
- 扇出高（通常1000+），三层B+树即可存储数亿条记录

---

### Q32: 为什么使用 B+ 树？

**深度解答**:

**核心优势对比**：
- **vs B树**：B+树非叶子节点不存数据，扇出更高，I/O更少；叶子节点链表支持范围查询
- **vs 红黑树**：红黑树深度大，磁盘I/O次数多；B+树多路分支，深度小
- **vs 哈希表**：哈希表不支持范围查询和排序，B+树支持

---

### Q33: 主键索引 vs 普通索引

**深度解答**:

- **主键索引（聚簇索引）**：叶子节点存储完整行数据，一张表只有一个
- **普通索引（二级索引）**：叶子节点存储主键值，查询时需要**回表**到主键索引取完整数据
- **覆盖索引**：如果查询字段都在普通索引中，则无需回表

## 第九部分：线程池与并发设计

### Q58: 线程池提交任务参数变化

**深度解答**: ThreadPoolExecutor.execute()的四级流水线：
1. **核心线程闸门**：workerCount < corePoolSize → 创建核心线程
2. **任务队列闸门**：workerCount >= corePoolSize → 任务入队
3. **非核心线程闸门**：队列满 → 创建非核心线程（上限maximumPoolSize）
4. **拒绝策略闸门**：超过maximumPoolSize → 执行RejectedExecutionHandler

---

### Q59: 核心线程与非核心线程转化

**深度解答**: 线程池不区分核心和非核心线程——Worker类没有isCore字段。所谓的"转化"是**行为策略的动态变化**：getTask()中`timed = allowCoreThreadTimeOut || wc > corePoolSize`。当workerCount降到corePoolSize以下，非核心线程在行为上自动变为"永久阻塞等待"，实现了"行为转化"而非"身份转化"。

---

### Q60: 主线程与子线程交互

**深度解答**: 三种方案对比：
1. **CountDownLatch**：底层AQS实现，需要额外容器存结果。必须在finally中countDown
2. **Future + ExecutorService**：submit提交任务，get阻塞获取结果
3. **CompletableFuture（推荐）**：事件驱动，allOf + thenJoin，无需手动管理计数和结果收集
