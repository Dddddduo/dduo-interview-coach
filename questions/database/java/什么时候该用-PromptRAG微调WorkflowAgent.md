# 什么时候该用 Prompt、RAG、微调、Workflow、Agent？

# 什么时候该用 Prompt、RAG、微调、Workflow、Agent？

## 🧠 联想记忆法

**一句话记忆**：选工具就像"给员工派活"——先问这个模型（这个人）能不能直接干，干不了再分清楚：是**缺知识**、**缺能力**，还是**不知道怎么干**。

**口诀："先问缺什么，再选补什么"**
- 缺**知识**（事实/实时/私有数据）→ **RAG**（外挂资料库）
- 缺**能力/风格**（格式、语气、领域术语）→ **微调**（给模型特训）
- 缺**流程控制** → 流程确定用 **Workflow**（写死的流水线），流程不确定用 **Agent**（自己拍板的智能体）
- 什么都不缺、任务很简单 → **直接 Prompt**（最便宜，永远先试）

**爬楼记忆法**：把五个词按复杂度排成一排，像爬楼梯：**Prompt（动嘴）→ RAG（带书）→ 微调（特训）→ Workflow（流水线）→ Agent（把流水线交给员工自己管）**。面试现场还能顺手把它画成一张决策树——树的三个节点就是三个问题：① 要不要事实/私有数据？② 模型能力够不够？③ 流程确定吗？

## 📖 深度解答

### 1. 核心概念（五者分别是什么）

这五个工具解决的**不是同一个维度的问题**，这是全题的钥匙：

| 手段 | 本质 | 解决什么问题 |
|------|------|-------------|
| **Prompt**（提示工程，Prompt Engineering） | **表达能力挖掘**（capability elicitation） | 模型本来就会，用提示词把它"唤醒" |
| **RAG**（检索增强生成，Retrieval-Augmented Generation） | **外部知识注入**（external knowledge injection） | 模型不知道的，从外部知识库"查"来 |
| **微调**（Fine-tuning / SFT，Supervised Fine-tuning） | **模型能力/风格定制**（capability & style customization） | 改参数，把行为"烙"进模型 |
| **Workflow**（工作流） | **确定性编排**（deterministic orchestration） | 流程写死，每步干什么人说了算 |
| **Agent**（智能体） | **自主决策循环**（autonomous decision loop） | 模型自己决定下一步：观察→思考→行动 |

**更本质的切分**：Prompt 和微调解决"模型侧"问题（**会不会**），RAG 解决"知识侧"问题（**知不知道**），Workflow 和 Agent 解决"流程侧"问题（**怎么干**）。想清楚问题落在哪个维度，答案就出来了一半。

### 2. 底层原理（为什么各有边界）

- **Prompt 的边界**：受限于模型的先验知识（knowledge cutoff，知识截止时间）和上下文窗口（context window）。参数不变，"不会就是不会"——模型训练时没见过的事实，提示词写得再好也是编（即幻觉，hallucination）。所以它只适用于"能力在、知识在"的场景。
- **RAG 的原理**：把知识从"参数内"搬到"参数外"（external memory）。生成前先检索（retrieval）再生成（generation），检索质量决定上限——切分策略（chunking）、召回率（recall）、重排（rerank）都会影响最终答案。代价是多了一条检索链路，有额外的时延和系统复杂度。
- **微调的原理**：修改权重，把某类行为"特训"进模型。适合"模型没有这个能力或不愿意这么做"的场景（强制输出 JSON、特定产品语气、医学/法律等专业术语）。**注意：微调不能可靠地注入新事实知识——那是 RAG 的职责**。且有灾难性遗忘（catastrophic forgetting）风险、数据标注成本高、迭代周期长。
- **Workflow vs Agent 的本质区别（分水岭）**：决策权在**人**还是在**模型**。Workflow 分支写死 → 可控、可测、token 消耗可预估；Agent 运行时自决 → 灵活、上限高，但可能绕圈（loop）、误调工具、token 失控，必须加护栏（guardrails：工具白名单、最大步数、超时熔断）。

### 3. 实践应用（决策树 + 权衡表 + 演进路径）

#### 3.1 选择决策树

```
任务来了
├─ 简单、一次性、模型本身就会（改写/摘要/翻译）→ 直接 Prompt
├─ 需要事实/实时/私有数据（产品文档问答、查库存的客服）→ RAG
├─ 能力不足：格式/风格/领域术语不达标（强制 JSON、医疗术语）→ 微调
└─ 多步骤、多工具：
    ├─ 流程确定、可枚举（查库存→扣款→发货固定流水线）→ Workflow
    └─ 流程不确定、需动态决策（根据用户意图决定调哪个接口）→ Agent
```

工程上可落成一个"选型决策函数"（体现工程化思维，也方便给团队做兜底规范）：

```python
def choose_technique(task):
    if task.is_simple and task.model_already_can_do(task):
        return "Prompt"                       # 简单任务，最低成本起步
    if task.needs_facts or task.needs_realtime or task.needs_private_data:
        return "RAG"                          # 知识型问题 → 外挂知识
    if task.requires_style or task.requires_format or task.requires_domain_terms:
        return "Fine-tuning"                  # 能力/风格型 → 行为定制
    if task.workflow_is_deterministic:        # 分支可枚举 → 写死编排
        return "Workflow"
    return "Agent"                            # 意图无法枚举 → 自主决策
```

#### 3.2 成本-复杂度-效果 三维度权衡表

| 方案 | 开发成本 | 维护复杂度 | 效果上限 | 可控性 | 典型代价 |
|------|---------|-----------|---------|--------|---------|
| Prompt | ★ 最低 | ★ 低（但玄学、靠调） | ★★ 受限于模型 | 高 | 几乎为零 |
| RAG | ★★ 中 | ★★★（切分/召回/更新） | ★★★★ 知识新、可溯源 | 中 | 多一跳检索时延 |
| 微调 | ★★★★ 高 | ★★★★（数据版本/回归） | ★★★★ 行为深度改变 | 高 | 标注+训练成本 |
| Workflow | ★★★ 中高 | ★★★（多节点难排查） | ★★★ 受限于人写的流程 | ★★★★★ 最高 | 多轮调用累积 |
| Agent | ★★★ 中（框架成熟） | ★★★★★ 不可控、难测 | ★★★★★ 上限最高 | ★ 最低，需护栏 | token 可能失控 |

**关键认知：没有一个方案是免费的**。能说出"成本-复杂度-效果"三角权衡，比只会背定义高一档——这正是面试官想听的工程判断力。

#### 3.3 组合使用与演进路径

工程上从来不是"二选一"，而是**叠加演进**：

**先 Prompt → 加 RAG → 复杂了切 Workflow → 再 Agent → 沉淀后固化回 Workflow/微调**

1. **先 Prompt**：MVP 最小可行产品（minimum viable product）验证价值，成本最低，跑通业务闭环；
2. **加 RAG**：发现需要私有/最新知识，外挂知识库；
3. **切 Workflow**：步骤变多（检索→筛选→生成→校验），提示词塞不下，拆成多步确定性编排；
4. **上 Agent**：分支多到写不死（用户意图无法枚举），让模型自己决策路由；
5. **固化沉淀**：Agent 跑稳定后，把高频路径固化成 Workflow、把固定行为微调进模型——**能确定下来的就不要让它自由发挥**，因为自主决策意味着贵且不可控。

**我的简历实践恰好是第 5 步的最佳注脚**：快手 **OrbitQA 星轨平台**采用 **Agent + Workflow 混合架构**——**PMO 编排（流程确定的部分用 Workflow 写死：任务拆分、分发、状态管理）与域 Agent 执行分离**，各域 Agent 基于 Spring AI 实现 **ReAct 循环**自主调用工具执行流水线。上层编排确定性保证可控可测，下层执行自主性保证灵活。同时我搭建了 **RAG 管线**（段落 500 字符 + 50 重叠切分、PgVector 余弦检索、Query 压缩重写 + 多查询扩展，**召回率提升 55%**），把测试知识注入域 Agent，最终**白盒测试提效 70%**。这就是"Workflow 兜底确定性 + Agent 释放灵活性 + RAG 补知识"的组合打法。

#### 3.4 各手段的典型失败场景与边界

- **Prompt**：幻觉——让模型答训练数据之外的事实；提示词无限堆砌，越长效果越差。边界：知识类问题不能只靠 Prompt。
- **RAG**：检索答非所问（召回不足）；切分把语义切断；知识库更新滞后；最隐蔽的是"检索到相似但不正确的文档，模型忠实复述错误答案"。边界：解决不了"模型不会做"的问题。
- **微调**：数据少而差，学到噪声；灾难性遗忘；为小问题训练大模型，投入产出比差。**常见误区：以为微调能注入新知识——不能，那是 RAG 的活。**
- **Workflow**：把不确定流程硬写成 if-else，分支爆炸；多步串联错误累积（error propagation——每步 95% 准确率，10 步后只剩约 60%）；维护地狱。
- **Agent**：不可控（绕圈、误调工具、token 失控）；非确定性输出导致难测试；工具权限放大带来安全风险。**边界：流程能确定就别用 Agent——确定性永远更便宜。**

### 4. 深入思考

**为什么"先简单后复杂"是工程纪律？**

- **复杂度是负债**（complexity is debt）：Agent 的维护复杂度是 Workflow 的几倍，Workflow 又高于 Prompt。上来就上 Agent，等于用最贵的方案解决可能一个 Prompt 就能解决的问题——这就是过度设计（over-engineering）。
- **效果优先于方案**：先用 Prompt 验证"模型能不能做、用户买不买单"，再优化"怎么做"。花两周微调，最后发现产品方向错了，比花两天写 Prompt 验证损失大得多。
- **演进路径每一步都有明确触发条件**：加 RAG 的触发条件是"需要知识"，切 Workflow 的触发条件是"步骤太多"，上 Agent 的触发条件是"意图枚举不完"。没有触发条件就不升级，这是纪律。

**评估先行（evaluation-first）是这一切的前提**：
没有评估，选型就是玄学。动手前先建评估集（eval set）：典型问题 + 期望答案（golden answers），量化指标——准确率、召回率、格式合规率、成本（token 数）、时延。让方案对比用数据说话。我在 OrbitQA 里正是这样做的：在统一评估集上对比切分参数与检索策略（500 字符 + 50 重叠、Query 重写 + 多查询扩展），把召回率量化提升了 55%——**没有评估集，这些优化根本无法归因**。这也是 Harness Engineering 方法论里"质量门控"（quality gate）的核心：每一步产出都要有可验证的标准。

**收尾一句话**：技术选型不是"哪个最好"，而是"哪个够"——用最简单的技术满足需求，把复杂度留给真正需要的地方；而"哪里需要复杂度"，要让评估数据来回答，而不是让架构师的想象来回答。

## 🗺️ 回答思路

### 答题逻辑框架（现场 3-4 分钟结构）

1. **开场定位（10 秒）**：先给本质概括——"这五个工具解决的问题维度不同：Prompt/微调解决'模型行不行'，RAG 解决'模型知不知道'，Workflow/Agent 解决'事情怎么干'。"一句话建立框架感。
2. **决策树主体（1.5 分钟）**：按"简单→Prompt；知识型→RAG；能力型→微调；流程确定→Workflow；流程不确定→Agent"逐条讲，每条配一个具体场景（如"客服要查实时库存→RAG"）。
3. **权衡与演进（1 分钟）**：抛出成本-复杂度-效果三维权衡 + 五步演进路径（先 Prompt→加 RAG→切 Workflow→再 Agent→固化回 Workflow/微调），展示工程成熟度。
4. **个人案例收尾（30 秒）**：OrbitQA 混合架构——PMO 编排（Workflow）+ 域 Agent 执行（ReAct）+ RAG 注入知识，证明不是纸上谈兵。
5. **升华（10 秒）**：评估先行，用数据说话。

### 重点得分点

- ✅ 说出五者**本质定义**（能力挖掘/知识注入/行为定制/确定性编排/自主循环）——区别于背概念的候选人
- ✅ 给出**决策树 + 权衡表**——结构化表达是明显的加分项
- ✅ 讲**组合与演进**而非"二选一"——体现工程思维
- ✅ 点破 **RAG 与微调的分工误区**（微调不注入知识、RAG 不改能力）——区分高手的关键点
- ✅ 结合简历项目（OrbitQA 混合架构 + RAG 管线量化数据）——体现真实落地
- ✅ 收尾落在"简单优先 + 评估先行"的方法论

### 常见误区

- ❌ 把五个工具并列比较"哪个最好"——答偏了，它们解决问题的维度不同
- ❌ 说"微调能让模型学会新知识"——错误，注入新知识是 RAG 的职责
- ❌ 分不清 Workflow 与 Agent 的本质（决策权在人 vs 在模型）——这是分水岭
- ❌ 只背定义没有例子和权衡——面试官要"什么时候用"，不是"是什么"
- ❌ 简历有 Agent/RAG 项目却不引用——浪费最大的差异化筹码
- ❌ 一上来就说"我们全用 Agent"——暴露没吃过不可控的亏

### 时间分配建议

- 🧠 联想记忆法：自用/备查为主，面试现场最多 10 秒带过或直接进入深度解答
- 📖 深度解答四层：核心概念 30s → 底层原理 40s → 实践应用（决策树+权衡表+演进+项目）1.5-2min → 深入思考 30s
- 🗺️ 回答思路：不逐条念，作为底稿自检；口答总计 **3-4 分钟**，讲不透的部分留给面试官追问——追问往往就是加分题

### 过渡话术

- 概念→选择："了解了各自的本质，我们来看怎么选——我习惯用一个决策树，先问三个问题：要不要事实？能力够不够？流程确定吗？"
- 方案→权衡："但决策树只是第一步，真正工程上还要看成本-复杂度-效果的三角权衡。"
- 理论→实践："这套选择逻辑我在快手 OrbitQA 里有完整实践——它正好是 Agent 和 Workflow 的混合架构。"
- 收尾升华："最后我想强调，所有选择的前提是评估先行——没有评估集，'哪个方案好'只能是玄学。"
