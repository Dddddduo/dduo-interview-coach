# 怎么做 Prompt/模型/索引回滚？

## 🧠 联想记忆法

**记忆锚点：「三回一基，两原一速」**

- **三回** = 三类回滚对象：**Prompt 回滚**（改动最频繁，靠版本管理+配置化下发）、**模型回滚**（靠模型路由+别名 alias，粒度最粗）、**索引回滚**（靠快照 snapshot+双索引切换，最容易被忽略）。
- **一基** = 一套基础设施：配置中心（动态开关）、不可变版本化、灰度（金丝雀）、监控告警触发自动回滚——没有这四件套，回滚就是空谈。
- **两原** = 两个设计原则：向前兼容（forward compatibility）、幂等（idempotency）。
- **一速** = 一个速度目标：分钟级回滚。

**生活化联想——把 LLM 应用当餐厅：**
- **Prompt 是菜谱**：天天改（今天多放点盐、明天换个摆盘），改坏了撕掉换昨天那张就行 → 配置切换，秒级回滚。
- **模型是主厨**：换个大厨（换模型）口味可能全崩，所以门口挂牌"今日主厨 = stable 档"（别名机制），挂牌即切换。
- **索引是食材仓库**：进货批次（索引快照）要留底，新批次食材出问题，直接把"后厨取材范围"切回上一批次 → 数据版本回滚。

一句话记住核心：**回滚的本质不是"重新发布旧的东西"，而是"把版本指针（version pointer）拨回已知良好状态"**——指针切换，瞬时生效。

## 📖 深度解答

## 1. 核心概念

**回滚（Rollback）**：把线上正在运行的配置、代码或数据，快速恢复到上一个已知良好状态（last known good state）的能力。

**为什么 LLM 应用必须做回滚？** 与传统软件不同，LLM 应用的每一次改动都是"软改动"（soft change）：Prompt 里一句话的调整、模型从 A 换到 B、温度（temperature）从 0.3 调到 0.7、索引里新增一批文档——任何一项都可能让线上效果变差。原因在于 LLM 输出的**非确定性（non-determinism）**：输出空间巨大，单测和回归用例根本兜不住所有行为变化，很多问题只在线上流量里才会暴露（格式漂移、幻觉增多、安全违规率上升）。所以回滚不是可选项，而是 LLM 工程的**底线能力（engineering floor）**——"改坏了能不能一键回来"决定了你敢不敢快速迭代。

**三类回滚对象的粒度与时机：**

**a) Prompt 回滚**——改动最频繁的资产。一个生产 Prompt 一天可能改多次（调措辞、加 few-shot 示例、改 system prompt）。粒度最小：不涉及重部署，只是配置值的切换。做法是**版本管理 + 灰度开关 + 配置化下发**：代码里不内嵌 prompt 字符串，而是通过 `prompt_id + version` 从配置中心拉取；线上回答质量下降、格式漂移（format drift）、安全违规率上升时，把版本指针切回上一版。可以按用户哈希灰度 5% 流量，观察后再全量。

**b) 模型回滚**——粒度是"模型路由配置"（model routing configuration）的变更。生产代码不写死模型名，而是引用**别名（alias）**（如 `stable` / `beta`），别名由配置中心动态指向具体模型版本（如 `claude-sonnet-4-20250514`）；回滚 = 一行配置把 alias 从 v2 指回 v1，全量实例即时生效。发布新模型时走**A/B 分流**：新旧模型按流量比例并行，或新模型先跑影子模式（shadow mode）只记录不下发。**自动回滚触发条件**：错误率（error rate）超阈值且持续 N 分钟、P99 延迟（latency）超标、质量指标（自动评测集通过率、人工评估分）下滑超阈值——任一触发，自动把 alias 切回旧模型并告警。

**c) 索引回滚**——向量库/知识库的数据版本回退。知识库数据入库后，脏数据、对抗性注入内容（prompt injection 样本混入）、格式不一致都会拉低检索质量（recall@k 下降）。做法：**快照（snapshot）**——每次构建索引固化一份不可变快照并保留 N 份；**双索引切换（dual index / blue-green index）**——新索引构建完成后先在影子流量下验证，再原子切换查询指针；每个知识库带**版本号 + 发布时间戳（published_at）**，检索时限定版本。因为索引重建耗时分钟~小时级，而"切回旧快照"是秒级——这正是保留旧快照的意义。

## 2. 底层原理

**为什么回滚能"回到过去"？** 核心是"一切皆版本，版本不可变"（everything is versioned, versions are immutable）：

1. **不可变快照 + 指针切换**：每次发布前，把 prompt 文本、模型配置、索引元数据固化成一个不可变的版本对象；线上运行时通过版本指针引用它，而不是直接覆盖内容。**"指针切换"优于"内容覆盖"的根本原因**：覆盖式更新没有"上一版"可言，想回滚也无从谈起。版本对象只能新建、不能修改，删掉旧版本就失去了回滚能力。

2. **配置中心的最终一致下发**：动态配置通过发布/订阅（pub/sub）或长轮询（long polling）下发到所有实例，支持按实例维度、按百分比维度定向生效——这为灰度与定向回滚提供了传输通道。

3. **模型别名（alias）的间接层**：代码 → 别名 → 具体版本，中间多了一层"间接引用"（indirection），切换就变成纯配置操作，与发版解耦。这是软件工程里"不要依赖具体实现，要依赖抽象"在 LLM 工程中的体现。

4. **索引的快照隔离（snapshot isolation）**：HNSW 这类向量索引构建后本质不可变（不支持原地更新/删除），所以生产上采用双索引：新索引构建+验证后，查询别名（index alias）原子切换；旧索引保留几天供回滚。注意：**索引回滚不是"回滚构建过程"，而是"回滚查询指针"**。

5. **自动回滚的闭环**：监控指标（错误率/延迟/质量）→ 告警（alert）→ 阈值（threshold）判定 → 自动切换版本指针 → 通知值班（on-call）。回滚动作本身只有"改指针"一行，复杂全在平时建设的监控与阈值体系里。

**为什么是"先回滚再排查"而不是"边修边上线"？** 因为代价不对等：修复 LLM 问题需要复现、归因（LLM 问题非确定性、难复现），可能耗时数小时；而回滚回到的是"已知良好状态"，只需确认指标恢复，分钟级。线上每多挂一分钟都在损失用户与信任——所以**生产铁律：先回滚止血（rollback first），再离线定位根因（debug later）**。

## 3. 实践应用

**基础设施四件套（缺一不可）：**
1. **配置中心（Config Center）**：动态开关、灰度比例、版本指针的载体；
2. **版本化与不可变快照**：prompt / model / index 全部带版本号，快照只增不改；
3. **灰度发布（金丝雀 Canary）**：先放 1%→5%→50%→100%，每个阶段观察指标；
4. **监控告警 + 自动回滚**：阈值触发自动切指针，值班人机协作。

**代码/配置示例（伪代码）：**

```json
// 配置中心中的版本指针（只存指针，不存内容）
{
  "prompt": {
    "summary_main": {
      "version": "p20260701_003",
      "status": "canary_5%",              // 灰度阶段
      "fallback_version": "p20260601_002"
    }
  },
  "model": {
    "stable_alias": { "model_id": "claude-sonnet-4-20250514", "params": { "temperature": 0.3 } },
    "beta_alias":   { "model_id": "claude-sonnet-4-5",         "params": { "temperature": 0.5 } }
  },
  "index": {
    "kb_main": {
      "snapshot_id": "idx-20260730-1542",
      "published_at": "2026-07-30T15:42:00Z"   // 知识库版本时间戳
    }
  }
}
```

```python
# 运行时：只读指针，从快照库加载不可变内容
class PromptRegistry:
    def get(self, key):
        ptr = config_center.get(f"prompt.{key}")
        return snapshot_store.load(ptr.version)   # 不可变快照，内容永不被覆盖

# 自动回滚看门狗（watchdog）
def auto_rollback_watchdog():
    while True:
        for key, cfg in get_canary_items():
            if metrics.error_rate(key) > cfg.error_threshold \
               and metrics.error_rate(key).sustained(cfg.duration_min):
                config_center.set(key, {"version": cfg.fallback_version,
                                        "status": "rolled_back"})   # 切指针 = 回滚
                alert.oncall(f"[AUTO-ROLLBACK] {key} -> {cfg.fallback_version}")
                audit.log(key, prev=cfg.version, cur=cfg.fallback_version)
        time.sleep(10)
```

**设计原则：**
1. **向前兼容（forward compatibility）**：新版本数据结构不能破坏旧版本解析器——prompt 模板变量、索引文档 schema 都要保持旧代码可读，否则"代码回滚到旧版"会读不了"新版数据"，产生反向依赖问题（rollback 后反而崩）。
2. **幂等（idempotency）**：回滚操作可重复执行且结果一致；回滚后可再前进（roll-forward）无副作用。避免"回滚脚本只能跑一次，重试就炸"。
3. **回滚速度目标：分钟级**：从发现到全量切回，理想小于 5 分钟。所以回滚路径要定期演练（game day / 故障演练），不能只在事故当天"临场发明"。
4. **可观测性带版本标签**：日志、指标、链路（trace）里都带 prompt / model / index 版本号——先知道"线上跑的是哪套组合"，才能决策回滚哪个。这是很多人忽略但极加分的一点。

## 4. 深入思考

**1）回滚 vs 修复的取舍。** 回滚是"外科手术式恢复"——回到已知良好态，解决的是**快速止血**；修复是"根治"——解决**不再复发**。取舍依据：回滚成本低、修复时间长 → 先回滚；若问题轻微可容忍、且回滚本身有代价（如索引回滚会让新入库数据不可见），则可边观察边修。正确姿势是：**回滚止血 → 带着快照与日志离线做根因分析（root cause analysis）→ 补回归用例 → 带着测试再发布**。回滚不是逃避修复，而是给修复争取时间。

**2）为什么"先回滚再排查"是生产铁律？** 因为事故的每分钟线上成本远大于排查的收益；LLM 问题尤其如此——非确定性让"现场"难以保留，但指标会持续恶化。回滚先把服务带回可用态，把用户损失锁死在一个窗口内，再从容排查。这也是 SRE 的经典理念：**可用性优先于诊断完整性**。

**3）多组件联动的回滚顺序：先回滚上游还是下游？** 答：**先回滚上游（调用链的源头、数据与配置的提供方）**。因为下游的输出依赖上游的输入——如果同时改了 prompt 和模型，先切回旧 prompt（瞬时生效），观察指标；若仍异常，再切模型 alias。反例：先回滚下游模型而 prompt 仍是新版，"新 prompt + 旧模型"可能照样坏。经验法则：**配置类（prompt/参数）瞬时生效、先切；数据类（索引）耗时、次切；若属于一次联动发布，则整体打成一个部署单元（deployment unit），一并回滚**，避免"切一半"的混合状态。

1. **开场定调（15 秒）**：一句话点出"LLM 应用的改动都是软改动，回滚是工程底线"，然后亮出框架："三类回滚对象 + 一套基础设施 + 两个原则"。

## 重点得分点（面试官想听到的关键词）
- **"不可变快照 + 版本指针切换"** 而非"覆盖式更新"——这是回滚能成立的根本原理，讲出来立刻拉开差距；
- **模型别名（alias）机制**：代码引用抽象而非具体模型 ID；
- **自动回滚触发条件**：错误率/延迟/质量指标超阈值+持续时长；
- **索引快照保留 + 双索引（蓝绿）切换 + 知识库版本号与时间戳**；
- **分钟级回滚目标、幂等、向前兼容**；
- **"先回滚再排查"铁律**、多组件联动**先上游后下游**；
- **可观测性带版本标签**（日志/指标/trace 打版本号）——多数候选人想不到的加分项。

## 常见误区（避免踩坑）
- ❌ 把回滚等同于"重新部署旧代码"——忽略 prompt/模型/索引是**运行时配置与数据**，回滚靠指针切换而非发版；
- ❌ 模型名写死（hardcode）在代码里，无法动态切换——必须用 alias；
- ❌ 只有全量回滚意识，没有灰度/金丝雀分层；
- ❌ 索引只保留最新一份，回滚=重建（耗时小时级），不懂保留快照；
- ❌ 只讲机制不讲闭环——不提监控、阈值、自动触发，回滚就只是"手动应急方案"；
- ❌ 回滚脚本非幂等、无审计，事故现场手忙脚乱。
