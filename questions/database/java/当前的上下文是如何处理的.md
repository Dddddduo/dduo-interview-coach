# 当前的上下文是如何处理的？

# 当前的上下文是如何处理的？

## 🧠 联想记忆法

把"上下文处理"想成**米其林后厨的一条流水线**：模型是食客，窗口是盘子，盘子永远有限、菜却源源不断，所以每道菜都要过五关——"理筛组压更"（谐音"里筛猪鸭羹"：后厨里筛食材、炖鸭羹的既视感）：

- **理**（理解）：先看客人到底点的什么——query 改写、意图识别；
- **筛**（筛选）：备料，从冰箱（向量库/记忆库）挑最新鲜的食材——检索与记忆召回；
- **组**（组装）：摆盘，顺序讲究，最重要的放盘头盘尾；
- **压**（压缩）：把浓汤熬成高汤浓缩汁——历史摘要、证据裁剪；
- **更**（更新）：撤掉剩菜换新盘——多轮增量、缓存更新。

组成六要素再配一句口诀：**"系统打底，证据上身，历史为辅，问题为主，工具记账，状态兜底"**。最后记一个研究结论当"锚点"：**Lost in the Middle（迷失在中间）**——模型像吃三明治的人，记得住上下两片面包（开头和结尾），最容易忘掉中间夹层。答题时只要记住"三明治效应"，上下文顺序编排的策略就不会漏。

## 📖 深度解答

### 1. 核心概念：什么是"当前上下文"

"当前的上下文"（Current Context）不是"对话历史"的同义词，而是**模型在本次推理时实际拼进输入的全部 Token 集合**——它决定了模型"看得到什么"，也就决定了回答质量的天花板。在 RAG/Agent 架构里，它通常由六部分组成：

1. **系统提示（System Prompt）**：角色、任务边界、输出格式、安全约束。全流程最稳定，也是后面讲 prompt caching（提示缓存）时的"固定前缀"。
2. **检索证据（Retrieved Evidence）**：从向量库/搜索引擎召回的相关片段，通常是"文档块 + 元数据 + 引用"。
3. **对话历史（Conversation History）**：此前多轮的用户问题与模型回答。
4. **用户当前问题（Current Query）**：本次真正要回答的内容，优先级最高。
5. **工具调用记录（Tool Call Records）**：Agent 场景特有，包括工具名、入参、返回结果、耗时与成功/失败状态。
6. **Agent 中间状态（Intermediate State）**：当前计划（Plan）、已完成的步骤、备忘（Scratchpad）、短期记忆等。

RAG 与 Agent 的关键差异在于：RAG 的上下文更像"**一次性组装**"——每轮重新拼一桌菜；Agent 的上下文是"**持续更新的状态机**"——内容在多步工具调用之间反复进出。而两者的核心矛盾相同：**窗口有限、信息无限**。所以"上下文处理"本质上是一个**预算约束下的信息编排问题**，也就是上下文工程（Context Engineering）。

### 2. 底层原理：上下文是怎么被"处理"的

完整流水线是五步：**理解 → 筛选 → 组装 → 压缩 → 更新**。

**(1) 理解（Understand）：query 改写与意图识别。** 用户问题常常不完整："那第二个方案呢？"——"那"指代什么？直接检索大概率召回失败。所以第一步做意图分类（Intent Classification）与查询改写（Query Rewriting）：消解指代（Coreference Resolution）、补全省略、口语转书面。我在 OrbitQA 里做的 **Query 压缩重写**就是它的高阶版：**把多轮历史中的必要信息"压缩"进当前问题本身**，让问题自包含（Self-contained）。这样既解决指代，又让后续每轮检索不再依赖旧历史——这是很多系统忽略的关键一环。

**(2) 筛选（Filter）：检索与记忆。** 先用**多查询扩展（Multi-Query Expansion）**：一个模糊问题发散成多个精确问题"撒网"，提升召回率（Recall）；再用混合检索（Hybrid Retrieval，向量 + BM25）和重排（Rerank）精炼。OrbitQA 的实践是"**先压缩重写、再多查询扩展**"：压缩管"准"，扩展管"全"，分工明确。记忆层面则是从记忆库（Memory Store）按相关性召回历史片段，而不是把全部历史搬进窗口。

**(3) 组装（Assemble）：结构、顺序、预算。** 顺序编排有两件事必须遵守：一是**把最核心、最稳定的内容放开头和结尾**——研究（Liu et al., 2023，Lost in the Middle）表明 Transformer 对上下文中间段的注意力显著下降（三明治效应），同时模型有近因偏差（Recency Bias），更倾向参考靠后的内容，所以系统提示放最前、当前问题尽量靠后、证据紧邻问题；二是**证据按重排后的相关性从高到低排列**。结构上给每类内容加明确分隔符与标签（如 `<evidence>` 块），帮模型区分"可参考材料"和"既定事实"。

**(4) 压缩（Compress）：历史摘要与证据裁剪。** 历史做**摘要滚动（Summary Rolling）**：旧轮次浓缩成一段摘要、新轮次保留原文；证据做**裁剪（Pruning）**：只保留与问题相关度 Top-K 的块，必要时做**上下文压缩（Contextual Compression）**——用一个小模型把大段落提炼成只含关键信息的短段落。

**(5) 更新（Update）：多轮增量与缓存。** 新对话产生后增量更新摘要、淘汰过期证据，并把稳定前缀写入缓存供复用，而不是每轮全量重建。

### 3. 实践应用：多轮对话与 Agent 场景

**多轮对话的四种主流策略：**

- **滑动窗口（Sliding Window）**：只保留最近 N 轮原文。简单、零信息损失，但窗口外全丢，早期上下文反复"被遗忘"。
- **摘要滚动（Summary Rolling）**：摘要 + 近 N 轮原文一起进上下文，是信息保留与成本之间的经典折中（LangChain 的 ConversationSummaryBufferMemory 就是这个思路）。
- **Query 压缩重写（Query Compression）**：把历史压缩进当前问题（OrbitQA 的做法），历史本身可以不进上下文，检索依然精准——这是"治本"的思路。
- **按需取史（Selective History Retrieval）**：不预先决定留多少，把历史也做成可检索的库，按当前问题实时召回相关旧轮次，再用摘要兜底。

**Agent 场景：工具调用记录怎么保留？** 原则是"**宁缺毋滥、只留有用的**"：

- **结果截断（Result Truncation）**：工具返回长 JSON/长文本时，只保留前若干字符 + 截断标记，或提取关键字段；
- **状态摘要（Tool Result Summarization）**：把"检索到 300 条、取 Top5"这类原始输出压成"检索完成，命中主题 X 的 5 条，前 3 条为……"的结构化摘要——保留**状态**而非原始数据；
- **保留策略**：只留最近 K 次调用的（工具名、参数摘要、结果摘要、状态）四元组，完整中间数据写进外部存储而不是塞进上下文。

**记忆注入（Memory Injection）**是 Agent 场景的另一大块，正好联动第 27 题：分层记忆（如 MemGPT 的 Core Memory / Working Context / External Storage）——长期事实住"核心记忆"，当前任务住"工作上下文"，旧细节沉淀到"外部存储"按需分页取回，与操作系统内存分页是同一个思想。

**预算分配与 Token 记账（联动第 26 题）：** 把窗口看成总预算，先给输出（Max Tokens）和工具结果预留空间，再给证据、历史、系统提示分配额，逐项记账，超限时按优先级从低到高砍。我的经验基准大致是：系统提示 10% / 证据 40% / 历史 20% / 当前问题 + 输出 30%，再按场景微调。

**工程化落地：**

- **Prompt Caching（提示缓存）**：Anthropic/OpenAI 都支持前缀缓存，稳定前缀的 KV Cache 被复用，成本和首 Token 延迟大幅下降。要点是**前缀必须稳定**——把每轮都变的证据放在缓存断点（Cache Breakpoint）之后；
- **流水线化（Pipeline）**：改写 → 检索 → 重排 → 压缩 → 组装做成独立阶段，可并行（多查询扩展天然可并发检索）、可观测（每步记录延迟与 Token 数）、可灰度；
- **超长处理与截断优先级**：我的经验顺序是——**先砍历史**（对当前答案影响最小，且有摘要兜底）→ **再砍证据**（优先砍低相关性块，保住与当前问题直接相关的）→ **最后动系统提示**（动了会改变行为基座，还可能让缓存全部失效）。

**三个常见坑，答题必提：**

- **上下文膨胀（Context Bloat）**：每轮只加不删，窗口被历史垃圾占满 → 对策是预算记账 + 更新阶段做增量淘汰；
- **重复注入（Duplicate Injection）**：同一证据或同一段指令被多轮重复塞入，既浪费预算又稀释注意力 → 对策是去重 + 用缓存前缀复用稳定内容；
- **中间位置信息丢失（Lost in the Middle）**：最关键的证据被排到中间位置 → 对策是顺序编排，最相关证据放开头或紧邻问题。

### 4. 深入思考

**其一，压缩的本质是信息损失，必须有可追溯性。** 摘要滚动会累积失真（Summarization Drift）——摘要的摘要越来越不像原文。工程上要给每条摘要保留源 ID 和引用，让模型或用户能"回到原文"，并定期用原始历史刷新摘要。

**其二，缓存与压缩是一对矛盾。** 缓存鼓励前缀长期不变，压缩鼓励上下文动态变化。解法是：**稳定靠缓存、动态靠预算**——把系统提示、工具定义等稳定内容放前缀并设缓存断点，把每轮变化的证据和历史放断点之后。

**其三，统一视角：上下文处理就是"内存管理"。** 读（检索）、写（记忆）、整理（Compaction，压缩）、淘汰（Eviction）四件事，与操作系统的虚拟内存/缓存置换同构——MemGPT 正是把这个类比做成了系统。有了这个视角，遇到任何新框架（长上下文模型、无限上下文插件）都能快速归类。

**其四，评估与未来。** 上下文策略不能靠感觉，要离线评测：忠实度（Faithfulness）、引用率（Citation Rate）、每千问的 Token 成本，做 A/B。未来长上下文模型会变便宜，但"注意力稀释"和"成本放大"依然存在——所以上下文工程不是过渡技巧，而是长期能力；更进一步的方向是"让模型自己决定读什么"（Agentic Context Management），而不是我们静态替它排版。

## 🗺️ 回答思路

### 答题逻辑框架（总—分—总）

1. **一句话定义**（15 秒）："我理解的当前上下文，是模型本次推理实际看到的全部输入，包含系统提示、证据、历史、当前问题、工具记录和中间状态六部分；上下文处理就是在一个固定预算里决定『放什么、放多少、怎么排』。"
2. **拆组成**（60 秒）：六要素逐个点一遍，点出 RAG 与 Agent 的差异（一次性组装 vs 持续状态机）。
3. **讲流程**（2-3 分钟，核心）：理解 → 筛选 → 组装 → 压缩 → 更新，每步给"动作 + 为什么 + 例子"，组装一步务必提到 Lost in the Middle 与近因偏差。
4. **场景展开**（2 分钟）：多轮对话四种策略对比；Agent 的工具记录保留（截断 + 摘要）与记忆注入（联动第 27 题）。
5. **工程化 + 坑**（1-2 分钟）：预算记账、prompt caching、截断优先级，收在三个坑上。
6. **收尾**（30 秒）：总结一句 + 抛出可追问点："如果时间允许，我可以展开讲讲缓存断点或历史摘要的评估方案。"

### 重点得分点

- **概念升维**：把"上下文"定义成"模型实际看到的输入"而非"对话历史"，立刻与多数候选人拉开差距；
- **流程完整性**：五步流水线一个不落，体现系统性思维；
- **理论锚点**：Lost in the Middle、近因偏差、Summarization Drift 这些研究结论是加分项；
- **工程细节**：截断优先级"先历史、再证据、不动系统提示"、缓存断点、预算比例——面试官最想听"你真的做过"；
- **简历联动**：OrbitQA 的 query 压缩重写 + 多查询扩展，讲清"压缩管准、扩展管全"的分工与"先压缩再扩展"的顺序理由；
- **体系联动**：主动提"这和记忆（第 27 题）、Token 记账（第 26 题）是一体的"，展示知识图谱。

### 常见误区

- 只答"窗口多大、怎么截断"，忽略理解和筛选——最常见的一问到底；
- 说"超长就砍历史"但不解释为什么先砍历史（摘要兜底 + 对当前答案影响最小）；
- 把工具调用结果和检索证据混为一谈——前者是"已发生事实"，后者是"待参考材料"，保留策略完全不同；
- 不知道缓存与压缩的冲突，把每轮变化的内容混进前缀导致缓存全部失效；
- 编造项目细节——只讲 OrbitQA 真实做过的 query 压缩重写和多查询扩展，不现场发明框架与数据。

### 时间分配建议

- **3 分钟快速版**：定义 + 五步流程各一句 + 一个项目例子 + 收尾；
- **5 分钟标准版**：定义 → 五步展开（每步 30-40 秒）→ 多轮策略与 Agent 各 60 秒 → 坑总结；
- **10 分钟深度版**：按完整框架，把工程化、评估、深入思考全展开，留 2-3 个点给面试官追问（缓存、压缩、记忆）。

### 过渡话术

- 开场："我先给个定义，再讲一条从输入到输出的处理流水线，这样比较完整。"
- 组成 → 流程："刚才说的是『有哪些菜』，接下来讲『后厨怎么处理』——核心是五步：理解、筛选、组装、压缩、更新。"
- 多轮 → Agent："上面是聊天场景，Agent 场景多了一个关键角色——工具调用记录，它和证据的保留策略完全不同。"
- 提到记忆："这正好能联动第 27 题的记忆机制，我在这里只讲和上下文相关的部分，分层细节可以展开聊。"
- 收尾："一句话总结：上下文处理就是预算约束下的信息编排——先理解，再筛选，按重要性组装，超了就压缩，最后增量更新。"
