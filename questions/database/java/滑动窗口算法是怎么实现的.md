# 滑动窗口算法是怎么实现的？

# 滑动窗口算法是怎么实现的？

## 🧠 联想记忆法

**记忆口诀**：*"边界两连发，窗口滑着补——Z 删旧、队出队、桶挪界"*

**记忆原理**：整道题的记忆锚点只有一个场景——**0:59 与 1:00 相邻两个窗口各打满额度，真实一个窗口周期内放行 2 倍流量**。这个"双倍流量"画面一旦记住，你自然能讲出"为什么要滑动窗口"。后半句三个动作对应三种实现，且本质上是同一个动作的三种版本——**"怎么把过期元素移出统计区间"**：
- **Z 删旧**：ZSET（有序集合）用 `ZREMRANGEBYSCORE` 删掉窗口外的时间戳；
- **队出队**：时间戳队列 `poll()` 弹出过期队首；
- **桶挪界**：分桶窗口只重置"进入窗口"的边界桶，历史桶环形复用。

记住"删旧"这一个动作，三种实现就全部串起来了。

**关联知识**：你早已熟悉的 **TCP 滑动窗口**（发送窗口随 ACK 向右滑动，确认过的数据不再参与统计）——网络层和限流层用的是同一个思想：*统计区间不是固定的，而是跟随当前时间流动*。另一个类比是地铁闸机："过去 60 秒进了多少人"，而不是"这一分钟进了多少人"——前者永远在滑，后者到点清零，这就是全部区别。

## 📖 深度解答

## 1. 核心概念（是什么）

**滑动窗口（Sliding Window）限流**：统计区间的时间边界不固定，而是随"当前时刻"不断向前滑动——任何时候被统计的都是 `[now - windowSize, now]` 这个**恰好一个窗口长度的真实时间区间**。它要解决的核心问题是固定窗口（Fixed Window）算法的**临界突变问题（Boundary Burst Problem）**。

**固定窗口为什么有缺陷**：固定窗口把时间轴切成与钟表对齐的固定周期，每个周期一个独立计数器。假设限流 **100 QPS**、窗口为 1 秒：

- 窗口 A = `[0:59:00, 1:00:00)`，窗口 B = `[1:00:00, 1:01:00)`；
- 攻击者（或真实的流量尖峰）在 `0:59:59.5 ~ 1:00:00` 这 0.5 秒内打满 100 个请求，填满窗口 A 的额度；
- `1:00:00` 一过，窗口 B 计数器**清零重置**，于是 `1:00:00 ~ 1:00:00.5` 又可以打进 100 个请求；
- 结果：在 `[0:59:59.5, 1:00:00.5]` 这个**恰好 1 秒（一个窗口周期）的真实区间**内，系统放行了 **200 个请求——是单窗口额度（100）的 2 倍**。限流在窗口边界形同虚设，下游被打爆的往往是这一瞬间。

这个"0:59 与 1:00 相邻两窗口打满额度"的场景，就是整个话题的引子，也是面试官最想听你讲清楚的第一件事。

**滑动窗口的解决思路**：把"窗口 A 结束 → 窗口 B 清零"这个**瞬间重置**，改成"窗口边界**连续滑动**"——窗口起点从 0:59:00 滑到 0:59:59.5、1:00:00……任何长度为 1 秒的真实区间内，计数都恒定地被压在这个窗口内，双倍流量漏洞从根上被堵住。代价是：实现从"一个计数器"变成"需要维护窗口内请求的历史信息"。

## 2. 底层原理（为什么）

滑动窗口的**设计哲学**是：*固定窗口的错误在于"计数区间与真实流量无关、只与钟表对齐"，滑动窗口则让统计区间永远等于"最近的 N 个时间单位"*。难点只有一个——**如何维护并更新窗口内的历史记录**。围绕这个难点，业界演化出三条实现路线，精度与成本依次递减：

### 路线 a：精确版——Redis ZSET（时间戳有序集合）

- 每个被限流的资源一个 key；每个请求是 ZSET 的一个 **member**（用 UUID 保证唯一），其 **score** 存当前毫秒时间戳；
- 每个请求到来时执行三步：**`ZREMRANGEBYSCORE key 0 (now - window)`** 删除窗口外元素 → **`ZCARD`** 统计窗口内请求数 → 未超限则 `ZADD` 写入并放行；
- **原子性**：这三步"检查-再写（check-then-act）"必须原子，否则并发下会超限。做法是把三步写进一段 **Lua 脚本**，由 Redis 单线程执行——脚本不结束，别的命令插不进来，天然无竞态；
- **精度**：每条请求一条记录，窗口内计数绝对精确，误差为零。

### 路线 b：近似版——滑动日志（Sliding Log，单机）

- 不依赖 Redis 时，用一个**时间戳队列**保存每次请求的到达时间；新请求到达时，先把队首所有满足 `now - head >= window` 的记录 `poll()` 弹出，队列长度即窗口内请求数；
- 单机实现可用 `ConcurrentLinkedQueue` 或环形数组。**近似的原因**有二：一是高并发下"先清再查再入队"非原子，需加锁（`synchronized`/`ReentrantLock`）或容忍短暂误差；二是队列 `size()` 是 O(n) 遍历，通常要配一个 `AtomicInteger` 计数；
- **内存**：窗口内有多少请求就存多少条记录，是"有状态的、随流量增长"的内存开销，且**多实例无法共享**——这是它只能当单机方案的原因。

### 路线 c：优化版——分桶滑动窗口（Bucket Sliding Window，Sentinel 实现）

- 把整个窗口切成 **N 个固定时长的子桶（sub-bucket）**，例如 1 秒窗口切成 10 个 100ms 的桶，每桶只记一个计数器；
- 请求到来时按 `idx = (now / bucketMs) % N` 定位当前桶，桶计数 `+1`；
- **关键优化：桶是环形数组，只"挪动边界"**——统计前检查当前桶是否已过期（`now - bucketStart >= window`），过期才重置它，其余历史桶的计数器继续复用。这样**内存恒定 = N 个桶**，与请求量完全无关；
- 统计时累加所有"桶起点落在 `now - window` 之后"的桶；对部分覆盖的边界桶还可**按时间比例折算**（Sentinel 就是这么做的），进一步压低误差；
- 这就是 **Sentinel 流控默认实现**：`LeapArray` 环形数组 + `WindowWrap` 桶对象，通过比较 `windowStart` 判断桶是否过期，过期才重置。

**三条路线的本质对比**：精确版与近似版是"**存每条请求**"（时间换内存、请求换精度），分桶版是"**存每个桶的聚合计数**"（内存恒定、精度换内存）。面试时能把这条主线讲清楚，就已经超过绝大多数候选人。

## 3. 实践应用（怎么用）

### 精确版完整可运行代码：Java + Redis + Lua

Lua 脚本（`sliding_window.lua`）：

```lua
-- KEYS[1] = 限流 key，如 ratelimit:sliding:order:1001
-- ARGV[1] = 窗口大小（毫秒），如 1000
-- ARGV[2] = 窗口内阈值 limit，如 100
-- ARGV[3] = 当前时间戳（毫秒）
-- ARGV[4] = 本次请求唯一标识（UUID）

local key    = KEYS[1]
local window = tonumber(ARGV[1])
local limit  = tonumber(ARGV[2])
local now    = tonumber(ARGV[3])
local member = ARGV[4]

-- 1) 滑动：删除窗口外（score < now - window）的全部元素
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- 2) 计数：窗口内剩余请求数
local count = redis.call('ZCARD', key)
-- 3) 判断并写入（整段脚本原子执行，天然无竞态）
if count < limit then
    redis.call('ZADD', key, now, member)
    redis.call('PEXPIRE', key, window)  -- 兜底过期，防止 key 与 member 永久残留
    return 1   -- 放行
else
    return 0   -- 拒绝
end
```

Java 调用端：

```java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import java.util.Collections;
import java.util.UUID;

public class RedisSlidingWindowLimiter {

    private static final String LUA = """
            -- 上方 Lua 脚本全文
            """;

    private final RedisTemplate<String, String> redisTemplate;
    private final DefaultRedisScript<Long> script =
            new DefaultRedisScript<>(LUA, Long.class);

    public RedisSlidingWindowLimiter(RedisTemplate<String, String> redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    /** @return true=放行, false=拒绝 */
    public boolean tryAcquire(String resource, long windowMs, int limit) {
        String key = "ratelimit:sliding:" + resource;
        Long result = redisTemplate.execute(
                script,
                Collections.singletonList(key),
                String.valueOf(windowMs),
                String.valueOf(limit),
                String.valueOf(System.currentTimeMillis()),
                UUID.randomUUID().toString());
        return result != null && result == 1L;
    }
}
```

调用示例：`limiter.tryAcquire("order:1001", 1000L, 100)` —— 表示订单接口 1001 用户 1 秒最多 100 次。Redis 集群下所有实例共用同一把限流，天然支持多实例水平扩展。

### 单机近似版：滑动日志（Java）

```java
public class SlidingLogLimiter {
    private final ConcurrentLinkedQueue<Long> queue = new ConcurrentLinkedQueue<>();
    private final AtomicInteger count = new AtomicInteger(); // 避免 queue.size() 的 O(n) 遍历
    private final int limit;
    private final long windowMs;

    public SlidingLogLimiter(int limit, long windowMs) {
        this.limit = limit;
        this.windowMs = windowMs;
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        // 1) 滑动：把窗口外的队首时间戳全部出队
        while (true) {
            Long head = queue.peek();
            if (head != null && now - head >= windowMs) {
                queue.poll();
                count.decrementAndGet();
            } else {
                break;
            }
        }
        // 2) 计数放行
        if (count.get() < limit) {
            queue.offer(now);
            count.incrementAndGet();
            return true;
        }
        return false;
    }
}
```

### 优化版：分桶滑动窗口（Sentinel 核心思想的简化版）

```java
/** 1 秒窗口切成 10 个 100ms 桶，环形数组复用，内存恒定 = 10 个桶 */
public class BucketSlidingWindowLimiter {
    private static final long WINDOW_MS = 1000;
    private static final int  BUCKETS   = 10;
    private static final long BUCKET_MS = WINDOW_MS / BUCKETS; // 100ms
    private static final long LIMIT     = 100;

    private final long[] bucketStart = new long[BUCKETS]; // 每个桶的起始时间
    private final long[] bucketCount = new long[BUCKETS]; // 每个桶的计数

    public synchronized boolean tryAcquire(long now) {
        // 1) 定位当前桶；桶已过期则只重置这个"边界桶"（核心优化）
        int idx = (int) ((now / BUCKET_MS) % BUCKETS);
        if (now - bucketStart[idx] >= WINDOW_MS) {
            bucketStart[idx] = now / BUCKET_MS * BUCKET_MS;
            bucketCount[idx] = 0;
        }
        // 2) 累加窗口内所有桶；边界桶按时间比例折算可进一步降低误差
        long total = 0;
        for (int i = 0; i < BUCKETS; i++) {
            if (bucketStart[i] > now - WINDOW_MS) {
                total += bucketCount[i];
            }
        }
        if (total < LIMIT) {
            bucketCount[idx]++;
            return true;
        }
        return false;
    }
}
```

**复杂度与内存分析**（面试必讲的一张表）：

| 实现 | 每次请求操作 | 内存 | 精度 | 适用 |
|---|---|---|---|---|
| ZSET 精确版 | `ZREMRANGEBYSCORE`(O(log n)) + `ZADD`(O(log n)) + `ZCARD`(O(1))，共 3 次 Redis 命令 | O(窗口内请求数)，每条请求一个 member | 零误差 | 分布式、对精度敏感的硬性限流 |
| 滑动日志单机 | 出队若干 + 计数 | O(窗口内请求数) | 零误差（加锁后） | 单机、无 Redis 的场景 |
| 分桶滑动窗口 | 定位桶 + 累加 N 个桶 | **O(N) 常数**，与请求量无关 | 误差 ≤ 一个桶时长（1s 窗口 10 桶 ≈ 10%） | Sentinel 等轻量、高并发场景 |

一句话记忆：**精确版用"每条请求一条记录"换零误差，分桶版用"10% 的粒度误差"换常数内存**。

## 4. 深入思考（注意事项）

**① 时间精度与误差的权衡**。这是滑动窗口最核心的工程权衡：分桶粒度越细，误差越小但桶越多——1s 窗口 10 桶误差约 10%，20 桶（50ms/桶）误差约 5%，理论上可无限逼近精确版。但存在物理下限：`bucketMs` 不能小于网络耗时与调度粒度，否则桶定位本身就不稳定。此外还有两个"时间陷阱"：一是**多实例时钟漂移（Clock Drift）**——客户端各自取 `System.currentTimeMillis()`，机器间时钟不一致会让同一限流在多台机器上表现不同，分布式精确限流应改用 Redis `TIME` 命令取服务器时间；二是**延迟清理**——滑动日志的过期元素是"惰性删除"的，清理不及时会短暂高估窗口内请求数（表现为少放行，安全方向）。

**② 与令牌桶/漏桶的选型（联动第 35 题）**。三种算法解决的痛点不同，面试官通常追问选型依据：

- **滑动窗口**：精确限制"单位时间内的请求数"，**不允许突发**，适合登录失败次数、短信发送频率、验证码这类**必须严格执行的频率上限**；
- **令牌桶（Token Bucket）**：允许一定突发（桶里攒的令牌可一次性消耗），输出速率总体平滑，适合接口兜底限流——允许秒杀开场短时爆发，又限制长期均值（Guava RateLimiter 即此模型）；
- **漏桶（Leaky Bucket）**：恒定速率输出，完全打散突发，适合保护下游资源（数据库、MQ 消费速率）。

选型四问：**能否容忍突发？需要平滑还是精确？精度要求多高？是否多实例共享？**——允许突发选令牌桶，要求平滑选漏桶，要求精确计数选滑动窗口，多实例则优先 Redis 方案。

**③ Sentinel vs Guava RateLimiter 的实现细节**。这是高频加分点：**Sentinel** 的流控默认就是分桶滑动窗口——`LeapArray` 环形数组 + `WindowWrap`，默认把 1s 窗口切成 2 个 500ms 采样桶，通过 `windowStart` 判断桶是否过期、过期才重置，内存恒定，且支持集群流控；**Guava RateLimiter** 走的是另一条路——"未来积分（nextFreeTicketMicros）"模型，本质是带预支能力的平滑令牌桶（`SmoothBursty` 支持一次性透支后续额度，`SmoothWarmingUp` 支持冷启动预热），纯 JVM 内存、零网络开销、**单机**。一句话对比：*Sentinel 是"数过去的请求"（滑动计数），Guava 是"赊未来的令牌"（积分预支）*——前者精确、可分布式，后者平滑、允许突发。

**④ 常见陷阱**：只 `ZADD` 不清理 → ZSET 无限膨胀，必须 `ZREMRANGEBYSCORE` + `PEXPIRE` 双保险；把"每 100ms 一个独立计数器"误称为滑动窗口——那只是**更细粒度的固定窗口**，边界问题依然存在（只是从 1s 缩小到 100ms）；并发下不加锁直接用 `ConcurrentLinkedQueue.size()` 计数（O(n) 且弱一致）；把客户端时间传进 Lua 导致多机时钟不一致。

## 常见误区（千万别说）

- ❌ 只背代码、讲不出"滑动"的本质——面试官一句"为什么固定窗口有漏洞"就卡住；
- ❌ 把分桶窗口说成"N 个固定窗口"——"只挪边界桶"和"N 个独立周期"的区别是精髓；
- ❌ 只提 Redis ZSET、不提单机滑动日志和分桶版——三者递进关系才是"深度"；
- ❌ 不提误差与权衡——"分桶有粒度误差、精确版有内存成本"这类 trade-off 是加分项，回避等于放弃加分；
- ❌ 把 Guava RateLimiter 说成滑动窗口实现——它是令牌桶（积分预支模型），说错直接扣分。

## 过渡话术

- 开场引子："先讲它解决什么问题——固定窗口在边界上有漏洞。假设限流 100 QPS、窗口 1 秒，0:59 的窗口在最后 0.5 秒被打满 100 个请求，1:00 一到计数器清零，前 0.5 秒又能打进 100 个——从 0:59:59.5 到 1:00:00.5 这恰好 1 秒（一个窗口周期）里放行了 200 个，正好两倍阈值。"
- 进入原理："既然问题出在'瞬间清零'，那滑动窗口的思路就是把边界改成连续滑动。实现上有三条路线，复杂度递增、成本递减……"
- 进入代码："以最常用的 Redis 精确版为例，核心就是一段 Lua 脚本——先删窗口外的，再数窗口内的，没超就写进去，三步原子完成。"
- 收尾选型："最后补充一点选型。滑动窗口的优势是精确、不允许突发；如果业务允许突发，就该考虑令牌桶，Guava RateLimiter 就是这种模型；要求恒定速率则用漏桶。三者各解决一类问题，没有银弹。"
