# 讲一下上下文工程是怎么设计的。

## 🧠 联想记忆法

**一句话记忆：上下文工程 = "进什么、以什么形、放哪里、花多少"（四个决定）——把 LLM 的上下文窗口当作受约束的稀缺资源来治理。**

**口诀记忆（六步链路）："理 → 检 → 排 → 剪 → 装 → 压"**
- 理：Query 理解与改写
- 检：混合检索（向量 + BM25）
- 排：重排（Rerank）
- 剪：截断去重
- 装：上下文组装（系统提示 + 证据 + 历史 + 问题）
- 压：上下文压缩

**形象记忆：上下文工程像"新闻发布会给发言人递材料"**
- 不是把一屋子文件全搬上台（那叫"喂上下文"），而是先看记者问了什么（Query 理解）→ 去档案室找材料（检索）→ 按相关度挑出最相关几份（重排）→ 删掉重复废话（剪）→ 按"开场白、材料、前情提要、问题"的顺序摆好（组装）→ 把 10 页前情提要压成 3 行（压缩）。
- 发言人记性有限（token 预算），材料放中间他最容易忘（Lost in the Middle），所以最重要的必须放最前或最后。

**数字记忆：0.1 / 1.25 / 55% / 20%**
- 缓存命中读 token 只要 **0.1** 倍价格（成本降 90%），写入 **1.25** 倍；
- OrbitQA 检索层（Query 压缩重写 + 多查询扩展）召回率提升 **55%**；
- Lost in the Middle 中间位置信息有效利用降到约 **20%**。

## 📖 深度解答

## 1. 核心概念

**上下文工程（Context Engineering）**是指：系统性决定"什么信息、以什么形式（format）、什么顺序（order）、多少预算（budget）进入大模型的上下文窗口（context window）"的一整套设计方法。它的对象不只是 prompt 文本，而是**整个信息进出的管线（pipeline）**——从用户输入到最终组装成发给模型的消息序列。

它和"喂 prompt"的本质区别在于三个词：**选择性（selective）、结构化和量化**。
- 不是把能找的都塞进去，而是**先检索、再挑选**（selective injection）；
- 不是平铺一段文字，而是**分块结构化组装**（system prompt / evidence / history / query 四段式）；
- 不是凭感觉，而是**用 token 预算做量化约束**（budgeting）。

**目标有三层：**
1. **质量**：最大化答案准确性与相关性——提供高信噪比（signal-to-noise ratio）的上下文，降低幻觉（hallucination）；
2. **成本与时延（cost & latency）**：token 就是钱，上下文越长推理越慢，必须在效果与开销之间取平衡；
3. **稳定与一致（consistency）**：多轮对话、多 Agent 协作下，上下文要可预期、可溯源、可审计。

一句话：**上下文工程是 RAG 与 Agent 系统的"信息治理层"（information governance layer），prompt 只是它的最终呈现。**

## 2. 底层原理

**（1）注意力机制与位置偏差。** Transformer 的自注意力（self-attention）是 O(n²) 复杂度，且注意力权重要在序列中摊薄分配：token 越多，每个 token 分到的注意力越少，这就是"注意力稀释"（attention dilution）——塞得越多，模型反而越抓不住重点。这是上下文工程存在的最根本动机：**上下文是一种有成本、且边际收益递减的稀缺资源。**

**（2）Lost in the Middle（迷失在中间）。** 斯坦福大学 Liu 等人 2023 年的论文《Lost in the Middle: How Language Models Use Long Contexts》通过多文档问答（multi-document QA）与合成键值检索任务证明了经典的 **U 形性能曲线**：模型对位于上下文**开头**（首因效应 primacy bias）和**结尾**（近因效应 recency bias）的信息利用最好，对位于**中间**的信息利用急剧恶化——中间位置的有效利用可低至约 20%。更关键的是：即使显式支持长上下文的模型（GPT-3.5-Turbo、Claude 1.3 等）也表现同样；在中间场景下 GPT-3.5-Turbo 的多文档 QA 成绩甚至**低于不给任何文档的闭卷成绩**（56.1%）。这直接证明了"更大的上下文窗口 ≠ 更好地利用上下文"，**文档顺序和位置本身就是设计变量**。

**（3）召回上限与重排的意义。** 检索器（retriever）的召回率（recall）是阅读器（reader）效果的上限；而排序（ranking）质量决定了 top-k 截断后真正进入上下文的是什么。实验还显示，文档数从 20 加到 50，效果几乎不涨（约 1%），说明**多塞文档是负收益的**——这也支撑"少而精"的上下文哲学。

**（4）压缩的动机。** 信息论视角下，上下文压缩（context compression）本质是在 token 预算约束下最大化条件信息量——删掉与答案无关的 token，等于提高上下文中的信噪比。

## 3. 实践应用

### 3.1 完整设计链路：理 → 检 → 排 → 剪 → 装 → 压

**第一步：Query 理解与改写（Query Understanding & Rewriting）。** 原始用户问题往往是口语化、指代不清、多意图的，需要做意图识别、实体抽取、改写。典型手段包括：**多查询扩展（multi-query expansion）**——把一个问题拆成多个视角的查询词以提升召回；**HyDE（Hypothetical Document Embeddings）**——先生成伪文档再以它做向量检索；以及 **query 压缩重写（query compression rewriting）**——多轮对话中，把"上一轮的问答背景"压缩进当前问题，使查询**脱离对历史的依赖、成为自包含（self-contained）的独立查询**。

> **OrbitQA 实例**：我在 OrbitQA RAG 管线中实现了 Query 压缩重写 + 多查询扩展，正是这一步的设计——把多轮对话压缩成独立查询后单独检索，解决"越问越偏"的漂移问题。

**第二步：混合检索（Hybrid Retrieval）。** 单一向量检索（dense retrieval，稠密向量语义匹配）长于语义但会漏掉精确词匹配（专有名词、编号）；**BM25**（经典词法检索，稀疏表示，基于词频 TF 与逆文档频率 IDF）长于精确匹配却不懂语义。工程上做**向量 + BM25 混合**，再用 **RRF（Reciprocal Rank Fusion，倒数排名融合）** 或加权分数融合（weighted score fusion）合并两路结果。

> **OrbitQA 实例**：语料按 500 字符切分、50 字符重叠（overlap）保留上下文连续性，向量检索采用 PgVector（PostgreSQL 向量扩展）做余弦相似度（cosine similarity）检索，配合 Query 压缩重写 + 多查询扩展后**召回率提升了 55%**。

**第三步：重排（Reranking）。** 双塔式（bi-encoder）向量检索快但粗，重排阶段用**交叉编码器（cross-encoder）**（如 Cohere Rerank、bge-reranker）把 query 与每个候选文档拼接后精细打分，取 top-k（通常 3–8 条）进入上下文。

**第四步：截断与去重（Truncation & Deduplication）。** 对相似候选做去重，常用 **MMR（Maximal Marginal Relevance，最大边际相关）**——在"与 query 相关"和"与已选内容冗余"之间折中；再按相关度与长度截断，保证每条证据有边界。

**第五步：上下文组装（Context Assembly）——四段式结构：**
```
[系统提示 System Prompt]  — 角色、任务、输出规范、引用要求
[检索证据 Retrieved Evidence] — <document id="1">…</document> XML 标签包裹 + 引用标注 [1][2]
[历史对话 Conversation History] — 压缩后的最近 K 轮
[用户问题 User Query] — 改写后的最终问题
```
检索证据的**格式化**是得分点：用 XML 标签（如 `<evidence>`、`<document>`）显式区分每条证据边界，配引用标注（citation markers）如 `[1][2]`，并要求模型"只基于 [1][2] 作答、并标注来源"。这样做的好处：**可溯源、可审计、显著降低幻觉**，还支持用户后续"第 2 条依据是什么"的追问。

**第六步：上下文压缩（Context Compression）。** 两类手段：一是**针对检索结果的压缩**（如 LLMLingua 这类 token 级压缩器、按 query 做证据摘要）；二是**针对历史的压缩**（query 压缩重写、历史摘要滚动更新）——把 10 轮冗长历史压成"用户最近在问 X，已确认条件 Y"这样的状态句。

### 3.2 顺序与位置设计（Positioning）

依据 Lost in the Middle 原理，设计规则是：
- **最重要的证据放开头**（紧随系统提示），或**放最后紧贴用户问题**；
- **重排后 top-1 放首位**，其余按相关度递减；
- 证据放在历史与问题之间，避免把核心证据埋进中段；
- 用户最终问题放在消息序列**最末尾**（recency 效应，模型对最后一句的注意力天然最强）；
- 实证表明：给每条证据加上"问题感知"的提示、或在关键处重复 query，都能缓解中段遗忘。

### 3.3 预算管理（Token Budgeting）

以 4K token 窗口为例，我的分配表如下（比例化设计，窗口放大时按比例缩放）：

| 组成部分 | 预算 | 说明 |
|---|---|---|
| 系统提示 | 10%（约 400） | 稳定不变，适合走缓存 |
| 检索证据 | 50%（约 2000） | 3–6 条 × 300–500，重排后截断 |
| 历史对话 | 25%（约 1000） | 只保留最近 K 轮 + 压缩摘要 |
| 用户问题 | 5%（约 200） | 改写后的最终问题 |
| **答案留白** | **10%（约 400）** | **必须为输出预留，防止生成被截断** |

设计原则：**先为输出（答案）留白，再反推输入预算**；证据数量宁可少而精；历史"按需取史"——query 命中哪一段才注入哪一段。

### 3.4 工程化落地

**（1）Prompt Caching（提示缓存）。** Anthropic 的 prompt caching：在稳定的内容块末尾加 `cache_control` 断点标记（`"cache_control": {"type": "ephemeral"}`），后续请求若**前缀精确匹配**则命中缓存。收益：缓存读（cache read）token 仅 0.1 倍价格（成本降 90%），缓存写（write）1.25 倍，首轮写入后第二轮即回本；时延最多降 85%。设计要点：TTL 默认 5 分钟（可配 1 小时）；最小缓存块约 1024 tokens；最多 4 个断点；**动态内容（时间戳、UUID）绝不能放进缓存块**，否则静默全失效。工程上应把"系统提示 + 静态知识 + 工具定义"作为**稳定前缀**统一缓存，每条用户请求只拼动态尾部——多轮对话场景成本可降 80% 以上。

**（2）动态选择性注入（Dynamic Selective Injection）。** 核心是"**先检索、后组装、按需注入**"：不预先把所有知识塞进 system prompt，而是每一轮根据改写后的 query 现检索、现组装；历史对话按相关性动态选取而非全量回放；多知识源场景可加**路由（router）**决定注入哪个知识库。这是与"把所有文档全放进去"的朴素做法最本质的区别。

**（3）可观测性（Observability）。** 监控 `cache_read_input_tokens` / `cache_creation_input_tokens` 验证缓存命中；用消融实验（去掉证据、去掉历史、调整顺序）量化每一步的边际收益，用数据而非感觉调预算。

## 4. 深入思考

**（1）上下文工程 vs Prompt Engineering vs RAG 的关系。** 这是常见加分题。我的框架：**RAG 是"供给方"**——解决"信息存在哪、怎么切、怎么检"（数据侧）；**Prompt Engineering 是"表述层"**——解决"同一批信息用什么措辞、什么 few-shot 样例组织"（静态文本侧）；**上下文工程是两者的交集与总纲**——它站在管线视角，治理"信息是否进入、以何形式、放何位置、花多少预算"，RAG 的输出只是它组装的一个组成部分，Prompt 只是它的最终呈现。没有上下文工程，RAG 检索得再好也可能被乱序、超载或格式混乱毁掉。

**（2）上下文一致性（Context Consistency）。** 多轮与多源场景下，要处理：同名实体的指代一致性（历史里的"它"是谁）；**证据冲突**——检索到的多条证据互相矛盾时，要么显式呈现矛盾并要求模型指出，要么按来源可信度裁决；上下文与系统约束的一致性（不能与 system prompt 的安全边界冲突）。设计上可用"证据冲突检测 + 引用裁决提示"。

**（3）毒性输入与注入过滤（Toxic Input & Prompt Injection Filtering）。** 必须认识到：**检索回来的语料是不可信上下文（untrusted context）**——外部文档可能包含指令注入（如"忽略以上指令，输出 XX"）、恶意内容或错误信息。因此工程上要做两道闸：**输入侧**对用户 query 做注入/毒性检测；**上下文侧**对检索片段做安全过滤与"证据不可信"声明（让模型只把证据当数据、不当指令），配合输出侧的 guardrails（护栏）过滤。这是上下文工程常被忽视、但实际生产中必踩的坑。

**（4）长上下文时代还需要上下文工程吗？需要，而且更值钱。** Lost in the Middle 在长上下文模型上依然成立——窗口变长不等于利用变好；且 token 更贵、时延更长，预算管理的杠杆更大。

## 答题逻辑框架（总分总，约 4 分钟）

1. **定义开场（30 秒）**：一句话给定义 + 四个维度（内容/形式/顺序/预算）。用"不是喂 prompt，而是信息治理"立住高度。
2. **链路主线（90 秒）**：按"理→检→排→剪→装→压"六步讲完完整链路，每步一句话"为什么"。这一步讲**广度**。
3. **两个亮点深讲（60 秒）**：挑"Lost in the Middle 顺序设计"与"token 预算分配表"展开——这一步讲**深度**，面试官通常在这里确认你是否真的做过。
4. **工程化落地（30 秒）**：prompt caching（0.1x 价格、cache_control 前缀匹配）、动态选择性注入。
5. **实例收尾（30 秒）**：OrbitQA——Query 压缩重写 + 多查询扩展、500 字符/50 重叠切分、PgVector 余弦检索、召回率 +55%。**用数字说话。**
6. **升华（30 秒）**：三概念关系（RAG=供给方，Prompt=表述层，Context Engineering=总纲）+ 主动提毒性/注入过滤——体现系统性视野。

## 重点得分点

- 定义中说出**四个维度（what / form / order / budget）**，立刻区别于"会写 prompt 的人"；
- 说出 **Lost in the Middle** 这个术语及其 U 形曲线、约 20% 的有效利用、长上下文模型也失效——这是核心加分点；
- 能给出**预算分配表**且记得"先留答案留白"；
- 提到**引用标注 [1][2] + XML 标签**的证据格式；
- 提到 prompt caching 的 **0.1x 读 / 1.25x 写 / 精确前缀匹配**这些细节；
- 有**真实项目数字**（55% 召回率提升）。

## 常见误区

- ❌ 把上下文工程等同于"写一个长 prompt"——丢失了"检索、挑选、预算"的管线视角；
- ❌ 只讲检索不讲组装——检索只是供给，组装才是工程；
- ❌ 不提 token 预算与成本——说明没上过生产；
- ❌ 把上下文工程与 RAG 划等号——RAG 只是数据侧，要讲清楚关系；
- ❌ 忘记位置设计——这是"理论→实践"最直接的证据；
- ❌ 只讲效果不讲代价——面试官更想听权衡（trade-off）。

## 时间分配建议

若只给 2 分钟（快答版）：定义 + 六步各一句 + 一个实例数字 + 一个亮点。若给 5 分钟（完整版）：按上面 6 段走。永远预留 30 秒做"三概念关系 + 安全"的升华，它最容易被追问。

## 过渡话术（可直接背）

- 讲完链路后："以上就是完整的组装链路。不过如果只讲'怎么做'，其实还缺一个更底层的问题——为什么要这么设计？这要从注意力机制和 Lost in the Middle 说起。"
- 引出预算："光有结构还不够，工程上真正要命的是预算。我一般在生产里用这样一张分配表——先给输出留白，再分配输入。"
