# 大模型应用上线前你最关心哪些工程指标？

## 🧠 联想记忆法（必须最前）

**口诀：质、效、本，稳、安、体——六维把关，门禁+监控串成闭环。**

用"一次用户提问的完整旅程"串起六类指标:

- 用户发出问题 → 系统要**快**(性能:TTFT 首 token 延迟、P95 尾延迟)
- 系统要答得**对**(质量:准确率、忠实度、badcase 密度)
- 系统要**贵得起**(成本:单次调用成本、token 消耗结构)
- 服务要**不挂**(稳定性:可用性、错误率、上游 API 故障率)
- 内容要**不出事**(安全:注入拦截率、敏感信息泄漏)
- 用户要**愿意用**(体验:采纳率、追问率、流失率)

英文侧记三组:"**首尾吞**"= TTFT + 尾延迟(P95/P99) + 吞吐(QPS);"**一可用二错误三超时**"= 稳定性三件套;"**上游四二九**"= 依赖 API 的 429 限流/5xx 故障是常见事故源。

再记一句答题主骨架:**"质量是上线第一关,性能是体感,成本是盈亏,稳定是底线,安全是红线,体验是终局"**——这句话本身就是回答的提纲。

## 📖 深度解答

### 1. 核心概念:一套"六维指标 + 门禁 + 监控"的度量体系

上线前最关心的不是某一个指标,而是一整套**可量化、可门禁、可观测**的体系。我把它分成六类:

**a) 质量指标 (Quality)**——上线第一关,答不对一切归零:
- **离线评测集准确率 (offline eval accuracy)**:固定评测集(如 500-1000 条带标注问题)上的正确率;
- **忠实度 (faithfulness)**:RAG(Retrieval-Augmented Generation,检索增强生成)场景下,生成内容与检索引用是否一致,是**幻觉 (hallucination)** 的代理指标;
- **拒答率 (refusal rate)**:超出能力范围的问题是否诚实拒绝,而不是硬编;
- **badcase 密度 (badcase density)**:每百条回答中错误/无关/有害用例占比,比单点准确率更贴近真实质量。

**b) 性能指标 (Performance)**:
- **TTFT (Time To First Token,首 token 延迟)**:用户看到第一个字的等待时间,决定"打字感";
- **端到端延迟 (end-to-end latency) 的 P50/P95/P99**:P50 是常态体验,P95/P99 是长尾体验;
- **吞吐 QPS (Queries Per Second) 与并发上限 (max concurrency)**:撑住多大流量而不劣化。

**c) 成本指标 (Cost)**:
- **单次调用成本 (cost per call)**:按 token 计费的单次平均成本;
- **token 消耗结构**:输入输出配比、prompt 缓存 (prompt caching) 命中率;
- **成本/质量比**:单位成本换来的质量分,防止"为 1% 质量多花 3 倍钱"。

**d) 稳定性指标 (Stability)**:可用性 (availability)、错误率 (error rate)、超时率 (timeout rate)、限流触发率 (rate limit trigger rate)、**依赖的 LLM API 故障率 (upstream failure rate)**。

**e) 安全指标 (Security)**:注入攻击拦截率 (prompt injection interception rate)、敏感信息泄漏检出率、内容安全审核命中率 (content moderation hit rate)。

**f) 体验指标 (Experience)**:用户满意度 (CSAT)、采纳率 (adoption rate,用户是否复制/点赞/采纳回答)、追问率 (follow-up rate)、流失率 (churn rate)。

### 2. 底层原理:为什么是这六类、为什么这么拆

- **生成式+流式 (streaming) 输出**决定了延迟必须拆成 TTFT 和首字之后的输出速度 (TPOT, time per output token)。排队、上游 API 抖动、上下文过长都会拉长尾延迟,而尾延迟正是用户喊"卡"的来源——所以只看平均值是自欺欺人,必须看 P95/P99。
- **非确定性 (non-deterministic)**:LLM 采样 (sampling) 使同一问题多次回答不同,单条用例无法评估,必须"评测集 + 统计口径 + badcase 人工回归"。忠实度之所以关键,是因为幻觉是"语言上自信、事实上错误",普通准确率测不出来。
- **按量计费 (usage-based pricing)**:输出 token 通常比输入贵数倍,重试、注入检索片段、上下文堆叠都直接抬价,所以 token 消耗结构决定成本曲线,必须看成本/质量比这个复合指标。
- **依赖链传导**:自建服务 → LLM API 供应商,上游一次 429/5xx 故障会逐级放大,所以稳定性指标必须覆盖上游故障率,并配套重试 (retry)、熔断 (circuit breaker)、降级 (degradation) 三层防御。
- **指令跟随 (instruction following) 的安全悖论**:模型越听话越易被注入攻击操纵,内容安全必须"输入侧拦截 + 输出侧审核"双向守护,故安全单列一维。
- **体验是结果指标**:前五类都是过程指标,体验才是最终裁判;但它依赖真实用户流量,天然属于上线后阶段——这正好引出第 4 层的取舍逻辑。

### 3. 实践应用:门禁、灰度、监控、压测、伸缩熔断

**设定上线门禁 (release gate)**:把指标翻译成 **SLO (Service Level Objective,服务目标)** 与 **SLA (Service Level Agreement,服务协议)**——SLO 是内部承诺,SLA 是对外契约(含赔偿条款),门禁引用 SLO。举例:质量上"离线准确率 ≥ 90%、忠实度 ≥ 85%、badcase 密度 ≤ 2% 且 P0 级为 0";性能上"TTFT P95 ≤ 2s、端到端 P95 ≤ 5s";稳定上"可用性 ≥ 99.9%、错误率 ≤ 0.5%、超时率 ≤ 1%";成本上"单次调用成本 ≤ 阈值"。任一项不达标即**阻断上线**。

**灰度放量 (canary release)**:5% → 20% → 50% → 100% 逐档放量,每档停留观察 1-2 小时以上,盯六类指标与 badcase 密度,否决项亮红灯立即回滚 (rollback),期间保留旧流量做对照组。

**A/B 实验**:同一流量对比模型版本、提示词 (prompt) 策略、检索 TopK,以体验与业务指标为准做显著性检验,样本覆盖至少一周流量周期。

**监控体系**:
- **全链路可观测 (observability)**:用 OpenTelemetry 打通 trace,**贯穿"query → 检索 (embedding + retrieval) → prompt 组装 → LLM 调用 → 后处理"每一段**,每段埋耗时、token 数、重试次数,按 request_id 串联日志与指标——出问题一键定位是检索慢还是模型慢;
- **告警分级**:P0(可用性掉线、敏感信息泄漏)即时电话/IM 告警;P1(错误率、P95 超阈值)5 分钟内响应;P2(成本环比激增、性能劣化趋势)日级跟进;
- **成本看板**:按业务线/功能/模型维度拆日成本,设预算与环比告警,异常涨点(如某 prompt 把日志全量塞进上下文)当日暴露。

**工程实践**:
- **压测方法**:真实流量回放 (traffic replay) 或 k6/Locust 构造混合负载(长问答+短问答+高并发),压出延迟/错误率拐点以测定并发上限,并特意模拟上游 429/5xx 验证熔断是否生效;
- **弹性伸缩 (elastic scaling)**:自建推理层(如 vLLM)按请求队列长度做 HPA (Horizontal Pod Autoscaling,水平伸缩);依赖第三方 API 时做连接池与排队控制;
- **熔断降级**:上游错误率超阈值(如 30%)或持续超时 → 熔断,降级到"缓存命中回答/小模型/预设话术",可用性优先——这就是**第 55 题"限流、熔断、降级三件套"**在 LLM 场景的落地。

### 4. 深入思考:否决项 vs 可后置优化

**上线否决项 (veto items)**——四类红线,不达标坚决不上线:
- **P95 延迟超 SLA**:尾延迟是体感灾难,上线后口碑难以挽回;
- **幻觉率/忠实度超标**:直接摧毁信任,可能带来事实性法务风险;
- **成本失控**:算不过账的功能注定被下线;
- **敏感信息泄漏、可用性低于目标**:合规红线与事故底线。

**可上线后优化**:体验类指标(采纳率、追问率)必须靠真实用户统计,天然后置;长尾 badcase 打磨、提示词精调、模型路由 (model routing,简单问题走小模型省钱)、缓存策略、检索调参,在灰度期逐步迭代,形成"上线 → 监控 → 迭代"闭环。

**更深一层**:警惕指标间的**联动与冲突**——提质量常拉高成本,压成本可能伤质量,所以要盯"成本/质量比";还要警惕**古德哈特定律 (Goodhart's law)**:指标一旦成为考核目标就失去意义——拒答率压得过低会逼模型硬编,所以质量评测要设"拒答率上限 + 准确率下限"双向约束。

## 🗺️ 回答思路

**答题逻辑框架(总分总)**:开场一句话给框架——"我把上线前指标分成六类:质量、性能、成本、稳定、安全、体验;再用门禁 + 灰度 + 监控把它们串成闭环"。中间按"六类速览 → 门禁放量 → 监控压测 → 否决项收尾"展开,结尾回到主骨架句收束。

**重点得分点**:
1. **框架完整**:六类全覆盖,比只答"延迟和 QPS"高一个段位;
2. **有具体数值**:能报出 SLO 例子(如 P95 ≤ 5s、可用性 99.9%),证明真做过;
3. **有工程细节**:trace 贯穿检索-生成、灰度比例、真实流量回放压测;
4. **有取舍判断**:分清否决项与可后置优化,体现工程判断力;
5. **有闭环**:门禁 → 灰度 → A/B → 监控 → 迭代,不是罗列指标而是呈现体系。

**常见误区**:
- 只答性能指标,漏掉质量与成本(面试官必追问"答错了怎么办""钱谁出");
- 拿离线准确率当唯一质量指标,漏了忠实度、拒答率、badcase 密度;
- 只报平均延迟,不分 P50/P95/P99;
- 说不清 SLO 与 SLA 区别(内部目标 vs 对外契约);
- 没有回滚预案;完全不谈成本,显得缺乏商业 sense。

**时间分配建议**(按 3-5 分钟作答):0.5 分钟框架总述 → 2 分钟六类指标速览(每类一句话定义 + 挑 1-2 个关键指标展开)→ 1 分钟门禁 + 灰度 + A/B → 1 分钟监控与压测/熔断降级 → 0.5 分钟"否决项 vs 可后置优化"收尾。

**过渡话术**:
- 「指标分层的价值在于:不同角色关心不同指标,而我要保证每一层都有数字兜底。」
- 「质量是上线第一关——答得不对,速度再快、成本再低也没有意义,所以我先看评测集准确率和忠实度。」
- 「指标不是上线那天才看的,我把它拆成两个清单:上线前必须达标的否决项,和上线后用数据持续迭代的优化项。」
