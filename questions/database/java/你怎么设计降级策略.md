# 你怎么设计降级策略？

## 🧠 联想记忆法

**一句话本质**：降级（degradation）= 系统部分失效时"保核心、砍次要"，是可用性设计（availability design）的一环——**不是消灭故障，而是管理故障的影响面**。

**一个生活场景锚定**：把降级想成"停电应急"——主电源 → 备用发电机 → UPS 电池 → 蜡烛。主模型挂了换备用模型，备用挂了换小模型，小模型也挂就用模板答案（蜡烛虽弱，屋里不会全黑）。这个链条和"模型层降级链"一一对应，面试时能顺口讲出画面感。

**两套口诀串联全局**：
- 降级四层："**模、检、功、容**"——模型层、检索层、功能层、容量层，从上往下数，顺序即降级优先级。
- 触发三开关："**检、人、水**"——故障检测（超时/错误率/熔断器）、人工开关（可灰度可回滚）、资源水位（成本/配额告警）。

**一条递进链**：超时（timeout）→ 重试（retry）→ 熔断（circuit breaker）→ 降级。像层层收网：先给一次机会，再保护下游，最后换替代方案。把这四个词按顺序背下来，深入思考环节的升华就有了。

## 📖 深度解答

## 1. 核心概念

降级（degradation）是指在系统部分组件失效、资源紧张或外部依赖不可用时，**主动牺牲非核心功能或部分体验，保证核心功能仍可用的设计手段**。它属于可用性设计的一部分：可用性公式 `可用性 = MTBF / (MTBF + MTTR)`，降级做的不是提高 MTBF（平均无故障时间），而是**把"故障期间的完全不可用"变成"降级可用"**，从用户视角缩小故障窗口的体感。

在 LLM 工程里，降级是刚需而非锦上添花，原因有三：
- **强外部依赖**：大模型能力来自第三方 API（OpenAI、Anthropic 等），你无法控制对方的故障、限流、内容审核拒绝，单点依赖风险天然高；
- **高时延高成本**：模型调用动辄数秒、成本按 token 计费，瞬时流量洪峰下极易触发配额（quota）与成本告警；
- **Agent 架构复杂**：检索、工具调用、多轮记忆任一环节故障，都可能让整体对话不可用。

所以 LLM 应用上线前，**降级链（fallback chain）设计是架构评审的必考题**。

## 2. 底层原理

降级的本质是把"不确定性封装为确定性"：**把对第三方的强依赖，改造成一条带优先级的候选序列**。核心决策模型是三要素：

**降级决策 = 触发信号 × 降级动作 × 恢复路径**

**触发信号（三开关）**：
- 故障检测：超时（timeout）、错误率（error rate）超过阈值、熔断器（circuit breaker）处于打开（open）状态——这是自动化触发；
- 人工开关：通过配置中心/特性开关（feature flag）人工下发，支持灰度（gray release）与秒级回滚（rollback），用于主动降级或兜底自动检测失灵的情况；
- 资源水位：成本、配额（quota）、并发水位告警触发，属于"被动牺牲体验换稳定性"。

**降级动作**：按层级选择替代方案（详见实践应用）。

**恢复路径**：健康检查（health check）+ 自动恢复（automatic recovery），故障解除后分级回迁，而非一次性全部恢复。

**两个底层设计思想**：
- **业务分级**：核心链路（如支付、鉴权）绝不降级甚至要物理隔离，非核心链路（如摘要、推荐）直接砍掉——降级的粒度先按业务分，再按功能分；
- **降级点粒度**：按功能维度（feature dimension）降级，而非全局一刀切——"搜索挂了只降检索层，对话功能照常"，避免雪崩式全站降级。

## 3. 实践应用

### 降级四层（"模检功容"）

**a) 模型层降级（Model Tier）**：主模型（旗舰大模型）→ 备用模型（备选供应商）→ 小模型（轻量/本地模型）→ 规则引擎（rule engine）/模板答案（template answer）。注意降级到小模型时要同步调整提示词（prompt）、温度（temperature）等参数，小模型对复杂指令理解弱。

**b) 检索层降级（Retrieval Tier）**：向量库（vector DB）故障 → 关键词检索（keyword search，如 BM25）→ 缓存结果（cached results）→ 无检索直接生成（generation-only，依赖模型内部知识）。RAG 场景下检索挂了不代表生成必须停。

**c) 功能层降级（Function Tier）**：Agent 自主决策 → 半自动（每一步人工确认）→ 人工兜底（human-in-the-loop）；多轮对话（multi-turn）→ 单轮（single-turn，砍掉记忆）；联网检索 → 离线知识库。

**d) 容量层降级（Capacity Tier）**：限流（rate limiting）→ 排队（queueing）→ 拒绝并提示稍后再试（reject with friendly retry hint）。这是面对流量洪峰的最后防线。

### 设计四原则（"度观复雅"）

1. **降级点粒度**：按功能维度而非全局；
2. **降级可观测（observability）**：降级日志（degradation log）、指标（metric）、响应标识（如响应头 `X-Degraded: tier-3`），让线上排查一秒钟定位"当前哪一级在兜底"；
3. **降级可恢复**：健康检查 + 自动恢复，配合熔断器的半开（half-open）状态试探下游；
4. **优雅降级（graceful degradation）**：返回旧缓存（stale cache）或友好提示文案，绝不裸抛 500。

### 具体案例：LLM API 故障时的多级降级链（代码骨架）

以 Python 为例，一个带触发、链路、可观测、恢复的降级路由器：

```python
class LLMFallbackRouter:
    """多级降级链：主模型 → 备用模型 → 小模型 → 模板兜底"""
    def __init__(self):
        self.tiers = [
            Tier("claude-main",  timeout=3.0),   # 主模型
            Tier("gpt-backup",   timeout=5.0),   # 备用模型
            Tier("local-7b",     timeout=8.0),   # 本地小模型
        ]
        self.breaker = CircuitBreaker(failure_threshold=0.5, open_seconds=30)
        self.manual_switch = FeatureFlag("degradation.manual", gray_ratio=0.1)

    def generate(self, query, user_id):
        # 触发信号1：人工开关（可灰度、可回滚），命中直接走兜底
        if self.manual_switch.on(user_id):
            return self.fallback(query, level="manual")

        for tier in self.tiers:
            # 触发信号2：熔断器状态 + 配额水位
            if self.breaker.is_open(tier) or not quota_ok(tier):
                continue
            try:
                return tier.call(query, timeout=tier.timeout)
            except TimeoutError as e:
                self.breaker.record_failure(tier)          # 超时计数，为熔断积累数据
                log_degradation(user_id, level=tier.level, reason="timeout")
                continue                                   # 进入下一级
        return self.fallback(query, level="template")      # 全链路失败

    def fallback(self, query, level):
        # 优雅降级：先查旧缓存，再无则模板答案，绝不裸报错
        resp = cache.get_or_template(query, "当前 AI 服务繁忙，已为您提供基础回答")
        resp.headers["X-Degraded"] = level                  # 降级标识，可观测
        return resp

    def health_recover(self):   # 定时任务：探活成功后自动恢复主链路
        for tier in self.tiers:
            tier.probe() and self.breaker.close(tier)
```

要点：超时→记录→下一级；熔断器过滤掉持续故障的供应商，避免每次请求都白等；`X-Degraded` 标识让监控和排查有抓手；探活成功后逐级回迁，完成"可恢复"闭环。

## 4. 深入思考

**降级与熔断/限流/重试的关系——一条递进链**：超时（timeout）→ 重试（retry）→ 熔断（circuit breaker）→ 降级（degradation）。重试解决瞬时抖动（注意重试需有退避策略 backoff，否则是雪崩放大器）；熔断解决持续故障——它负责"保护下游别再被打"；降级解决"能力缺失时的替代方案"。而限流是"入口处控制流量"，与降级互补：限流挡住超量请求，降级处理能力不足。面试时主动画出这条递进链，是明显的加分点。

**降级体验的兜底文案**：三要素——**明确告知 + 安抚 + 给出路**。"AI 服务繁忙，已切换为基础模式，回答可能简化，请稍后重试体验完整功能"，远好过"系统错误"四个字。且线上文案要区分用户侧（友好）与运维侧（带 `X-Degraded` 标识）。

**业务分级**：核心链路绝不降级（支付、登录等要的是隔离而非降级），非核心链路直接砍。判断标准是"降级收益 vs 体验损失"——砍一个推荐栏几乎无感，砍掉订单确认就是事故。

**两个更深的点**：一是降级策略本身需要演练，通过故障注入（fault injection）/混沌工程（chaos engineering）验证链路真的能兜住；二是 LLM 场景的特殊性——降级不只是"换模型"，提示词、参数、工具集、上下文长度都要随层级联动调整，否则小模型配长系统提示词反而更慢更差。

## 答题逻辑框架（总分总，5 步走）

1. **一句话定义**：降级是可用性设计的一部分，核心是"保核心、砍次要"（30 秒定调）；
2. **四层展开**："模检功容"——模型层、检索层、功能层、容量层，每层一句话说清链尾（60–90 秒，占大头）；
3. **触发与原则**：三开关（检人水）+ 四原则（度观复雅），收拢回设计理念；
4. **代码案例**：给出降级链骨架，突出"触发信号 × 降级动作 × 恢复路径"；
5. **升华**：递进链（超时→重试→熔断→降级）+ 业务分级，体现全局视野。

## 重点得分点

- **分层意识**（模型/检索/功能/容量四层）——大多数人只说"换备用模型"，分层的回答直接拉开差距；
- **可观测 + 可恢复**——面试官最怕听到只降级不恢复的"裸降级"，`X-Degraded` 标识和健康检查是亮点；
- **代码骨架落地**——能写出含熔断、降级标识、优雅兜底的骨架，证明是真做过而非背概念；
- **业务分级与递进链**——把降级放进熔断/限流/重试的体系里讲，体现架构全局观。

## 常见误区

- 把降级和熔断混为一谈——熔断是"保护"，降级是"替代"，先说清关系再展开；
- 只谈模型层、忽略检索/功能/容量层——RAG 和 Agent 场景下这些更常被考；
- 降级没有恢复路径——只降不升等于慢性死亡，自动恢复必须提；
- 全局一刀切降级——必须强调按功能维度/业务分级；
- 兜底直接报错——优雅降级（旧缓存/友好文案）是体验底线。
