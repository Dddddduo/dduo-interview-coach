# 滑动窗口和令牌桶相比有什么区别？

# 滑动窗口和令牌桶相比有什么区别？

## 🧠 联想记忆法

**一句话定性**：滑动窗口是「计数型」限流——数窗口里过了几个请求；令牌桶是「速率型」限流——看桶里还剩几张令牌。

**生活比喻**（两个画面感最强的例子）：
- 滑动窗口 = 餐厅的客流统计：老板规定「任意 10 分钟内最多接待 10 桌」，服务员每进来一桌就在本子上记一笔，同时划掉 10 分钟前的旧记录。它管的是**时段总量**，超了一律请出去。
- 令牌桶 = 自动售货机的代币机：机器每 1 分钟匀速吐 1 枚代币，最多攒 5 枚。客人来买东西必须投币，没币就排队等。它管的是**持续速率**，但攒下来的币允许你一次性花掉——这就是突发。

**关键词钩子**：「计数 vs 速率」「严格拒绝 vs 允许突发」「时间戳列表 vs 两个字段」「窗口硬上限 vs rate×t+burst」。

**口诀**：窗口数个数，桶里攒速率；窗口是闸门，桶是蓄水池。

## 📖 深度解答

## 1. 核心概念

**滑动窗口（Sliding Window）**：一种计数型（counting-based）限流算法。维护一个固定长度的时间窗口（如 1 秒），窗口内累计请求数不得超过上限 N。窗口随时间推移持续滑动：新请求到达时，先把落在窗口之外的旧记录剔除，再判断窗口内计数是否已满。它是对**固定窗口（Fixed Window）**的改进——固定窗口在窗口边界处存在"双倍突刺"漏洞（比如 0.9 秒和 1.1 秒各打满 100 个请求，2 秒内实际通过了 200 个），滑动窗口通过持续平移消除了这个盲区。

**令牌桶（Token Bucket）**：一种速率型（rate-based）限流算法。以恒定速率 r 向桶中补充令牌（token），桶容量（bucket capacity）为 b；请求到达时必须消耗一个令牌才能放行，无令牌则拒绝或阻塞。长期来看平均速率不超过 r，但**允许瞬时突发（burst）最多 b 个请求**——前提是之前攒下了足够的令牌。

**一句话概括本质区别**：滑动窗口限制的是「任一窗口内的总量」（硬上限），令牌桶限制的是「长期平均速率 + 突发上限」（软速率）。

## 2. 底层原理

**滑动窗口的实现**：核心数据结构是一个时间戳队列/循环数组。每次请求到达：① 剔除所有 `now - 时间戳 ≥ 窗口长度` 的旧记录；② 若队列长度已达 N 则拒绝；③ 否则加入当前时间戳。精确版滑动窗口需要存储窗口内**每一个**请求的时间戳，内存随 QPS 线性增长；工程上常用**滑动窗口计数器（Sliding Window Counter）**变体——把窗口切成若干小格子（如 1s 切成 10 个 100ms），用「上一格子的部分占比 + 当前格子计数」估算总量，牺牲一点精度换取 O(1) 内存，Sentinel 即采用此方案。

**令牌桶的实现**：只需要**两个字段**——`lastRefillTime`（上次补充时间）和 `availableTokens`（当前令牌数）。请求到达时按 `(now - lastRefillTime) × rate` 补令牌（封顶为桶容量 b），再扣减 1。整个计算是 O(1) 的纯数学运算，无任何存储结构。

**⚡ 关键洞察（数学差异，全场最值钱的一句）**：两者对"时间窗内最大放行量"的约束完全不同——
- 滑动窗口：**任意窗口内请求数严格 ≤ N**，这是硬上限（hard cap）。
- 令牌桶：**任意时长为 t 的窗口内，最多放行 rate × t + bucketSize 个请求**。例如 rate=100/s、burst=50，那么 1 秒窗口内最多可放行 100×1+50 = **150** 个（桶里攒满 50 个再以 100/s 消费）。
- 结论：令牌桶在**短窗口内可能超过 rate**，滑动窗口则**永不超 N**。这正是"硬限制"与"软速率"的数学本质，答出来即与普通背概念的候选人拉开差距。

## 3. 实践应用

**滑动窗口适用场景**：需要"绝对不超限"的硬约束——接口级 QPS 硬限制、网关单 IP 限流防刷/反爬（统计维度是次数而非速率）、对用户可感知的 SLO 承诺。典型代表：**Sentinel**（默认滑动窗口计数，统计 QPS、并发等指标并限流）、网关层按维度（IP/用户）限频。

**令牌桶适用场景**：下游保护 + 允许突发——数据库/第三方 API 有吞吐上限但能容忍瞬时尖峰；秒杀开场、缓存击穿恢复期的流量突刺；需要**动态调整速率**（按用户等级动态调 rate）。典型代表：**Guava RateLimiter**（SmoothBursty/SmoothWarmingUp 平滑变体）、Spring Cloud Gateway 的 RequestRateLimiter、Amazon API Gateway 的默认限流。

**选型决策**：追求「绝不超限、统计精确」→ 滑动窗口；追求「资源利用率最大化、允许突发、速率可调」→ 令牌桶。实际生产常**组合使用**：令牌桶削峰 + 滑动窗口封顶。

## 4. 深入思考

**代码级对比**（两个核心实现并排）：

```java
// 滑动窗口：时间戳队列
class SlidingWindow {
    private final Deque<Long> timestamps = new ArrayDeque<>();
    private final int limit;              // N 个请求/窗口
    private final long windowMillis;
    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        while (!timestamps.isEmpty()
                && now - timestamps.peekFirst() >= windowMillis)
            timestamps.pollFirst();       // 剔除窗口外旧记录
        if (timestamps.size() >= limit) return false; // 严格拒绝
        timestamps.addLast(now);
        return true;
    }
}

// 令牌桶：仅两个字段
class TokenBucket {
    private final double rate;            // rate 个令牌/秒
    private final double capacity;        // 桶容量 burst
    private double tokens;
    private long lastRefillNanos;
    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity,
                tokens + (now - lastRefillNanos) / 1e9 * rate);
        lastRefillNanos = now;
        if (tokens < 1) return false;
        tokens -= 1;
        return true;
    }
}
```

并排看更清晰：滑动窗口多一个**存储结构**，令牌桶只有**两个数值字段**；滑动窗口的拒绝是即时的、绝对的，令牌桶的拒绝只发生在"令牌耗尽"时。

**分布式实现差异**（单机到分布式的放大效应）：滑动窗口在分布式下需要全局时间戳集合 → 用 Redis **ZSET**（score 为时间戳）存储，每次请求一次 `ZADD` + `ZREMRANGEBYSCORE` + `ZCARD`，内存随 QPS × 窗口时长线性增长，高 QPS 下内存成本很高；令牌桶在分布式下依然只有两个字段（`last_refill_time`、`tokens`），用 **Lua 脚本**原子完成"补充+扣减"，O(1) 内存。此外分布式滑动窗口还依赖节点时钟一致或 Redis 时间戳，令牌桶无此问题。这也是生产中**分布式限流（如 Redis+Lua 方案）普遍偏向令牌桶**的原因。

**Sentinel 与 Guava 的选型逻辑**：Sentinel 选滑动窗口，因为它的定位是"指标统计 + 限流一体"，需要按任意时间粒度精确统计 QPS/并发数并拒绝超限请求，滑动窗口天然的"窗口内严格 ≤ N"契合其保护微服务的硬约束目标；Guava 选令牌桶（平滑变体），因为它的定位是"平滑速率整形"，要利用突发能力、输出更平滑的流量。**两者目标函数不同：一个要精确总量，一个要平滑速率。**

**加分扩展——漏桶（Leaky Bucket）**：漏桶恒定速率出水、无突发、纯粹整形，可看作"零突发的特殊令牌桶"。三角对比一句话：滑动窗口管总量、令牌桶管速率+突发、漏桶管匀速整形。

## 常见误区
- ❌ 说"滑动窗口比令牌桶更精确"——两者约束语境不同（总量 vs 速率），不可直接比精确度。
- ❌ 混淆固定窗口与滑动窗口——固定窗口才有边界突刺问题，滑动窗口正是其改进。
- ❌ 说"令牌桶允许无限突发"——突发上限 = 桶容量 b。
- ❌ 把 Guava RateLimiter 当成标准令牌桶——它是平滑变体（SmoothBursty/SmoothWarmingUp）。
- ❌ 只聊单机——分布式下滑动窗口 ZSET 内存成本呈数量级差异，这是面试官最爱追问的延伸点。
- ❌ 只背定义不给场景——面试官考察的是**决策能力**，必须落到选型。
