# 两阶段缓存是什么？

## 🧠 联想记忆法

**记忆口诀**：**「先近、后远、再到源——两级缓存挡在 DB 前」**；进阶版：**「两查两写两坑」**（两查：L1→L2 两级查询；两写：DB 与缓存的双写一致性；两坑：双写不一致 + 缓存击穿）。

**记忆原理**：把整个问题压缩成一条**访问路径**——读请求先打进程内本地缓存（Local Cache，第一级 L1），未命中再打分布式缓存（Distributed Cache，第二级 L2，如 Redis），两级都未命中才回源数据库（Database，DB）。「近 → 远 → 源」三个字钉住三级存储的物理距离，面试时顺着这条路径讲，天然就是完整答案的主线，不会漏层。

**关联知识**（知识锚点）：你已经熟悉计算机组成原理里的**存储金字塔**（Memory Hierarchy）——CPU 的 L1/L2 缓存（约 1ns）、主存（约 100ns）、磁盘（约 10ms），每往下一层，延迟涨几个数量级，所以用快的一层挡慢的一层。**两阶段缓存就是把这个金字塔思想搬到业务系统**：Caffeine 相当于 CPU 的 L1 寄存器级，Redis 相当于内存，MySQL 相当于磁盘。另一个生活锚点：奶茶店配方**门店冰箱（本地缓存）+ 中央仓库（Redis）+ 供应商（DB）**——冰箱有货直接做，没货去仓库取，仓库也没有才向供应商要货并补货。

## 📖 深度解答

## 1. 核心概念（是什么）

**两阶段缓存（Two-Stage / Two-Level Cache）**指一种两级缓存架构：**第一级是进程内本地缓存**（如 Caffeine、Guava），**第二级是集中式分布式缓存**（最典型的是 Redis），数据源是数据库。它在工程上还有一种等价表述——**「检查缓存 → 未命中则查询源」的两阶段读取流程**（Cache-Aside 模式，旁路缓存）：先查缓存（阶段一），命中直接返回；未命中查数据库并回填（阶段二）。这两种表述一个是「架构视角」，一个是「流程视角」，面试时最好都点出来，证明你不是背定义。

三个角色各司其职：

| 层级 | 代表组件 | 延迟量级 | 容量 | 特点 |
|---|---|---|---|---|
| L1 本地缓存 | Caffeine / Guava | ~100ns | 几 MB~几十 MB/实例 | 最快，但有 N 份副本，一致性最弱 |
| L2 分布式缓存 | Redis（集群） | ~1-3ms（含网络 RTT） | 全局一份，可无限扩 | 跨进程共享，多实例一致 |
| 数据源 | MySQL | ~5-20ms | 全量 | 最慢，数据是唯一真相 |

它解决的问题本质只有一个：**用「近距离存储」的容量，去换「远距离访问」的延迟**，把读请求按局部性原则分流，让 90% 以上的请求永远碰不到数据库。

## 2. 底层原理（为什么）

**（1）延迟数量级差距（Latency Gap）是物理前提。** 内网一次网络往返（Round-Trip Time, RTT）约 0.5~2ms，而进程内内存访问约 100ns——**两者相差 3~4 个数量级**。如果热点数据能落在本地进程内存里，单次请求从 1ms+ 压到亚微秒级；而 Redis 再快，也要经过网络协议栈、序列化、IO 多路复用。加上 DB 查询是 5~20ms，也就是说：**L1 命中 ≈ 100ns，L2 命中 ≈ 1-3ms，DB 查询 ≈ 10ms+，每一级差约 10~100 倍**。这就是「多一级缓存，多一个数量级的收益」。

**（2）热点数据（Hot Data）的二八定律。** 绝大多数业务遵循 80/20 法则：约 10%~20% 的 Key（如热门藏品、爆款商品、大 V 主页）承担了 80%~90% 的访问量。把这份「高频小集合」复制到每台机器的本地内存，可以让绝大多数请求完全免去网络开销——**用容量换延迟，是分布式系统里最划算的买卖**。

**（3）给 Redis 减压（Offload）。** Redis 虽然是内存数据库，但仍是独立进程：高 QPS 下 CPU、网卡、连接数都会成为瓶颈，而且它一旦抖动会影响全局所有业务（故障面大）。L1 命中率做到 80%~90% 后，打到 Redis 的 QPS 直接降一个量级，Redis 压力小了，连接池、主从复制、持久化的压力全都跟着降。同时，**Redis 挂掉时本地缓存还能兜住大部分读流量**，这是两级架构天然带来的容错（Fault Tolerance）红利——故障从「不可用」降级为「部分延迟」。

**（4）读路径完整走查（读流程的两阶段）。** ① 请求进入，先查 L1（Caffeine）：命中 → 直接返回，流程结束；② L1 未命中，查 L2（Redis）：命中 → 回填 L1 → 返回；③ L2 也未命中，查数据库：命中 → 先回填 L2（供所有实例共享），再回填 L1（供本实例后续复用）→ 返回。每一层都扮演「下一层的缓存」，整个设计哲学就是**时间局部性（Temporal Locality）**——刚被读过/写过的数据很快还会被再次访问。

## 3. 实践应用（怎么用）

**（1）技术选型与配置。** L1 首选 **Caffeine**（比 Guava 更强的淘汰算法 **W-TinyLFU**：结合 LRU 的近期性与 LFU 的频率性，用 Count-Min Sketch 做频率估计 + 频率老化窗口，能抵抗「一次性大批量扫描」把热点挤出去的攻击），L2 用 Redis 集群。容量上 L1 必须设上限，否则堆内存会被拖垮：

```java
// L1：Caffeine 本地缓存 —— 容量小、TTL 短
Cache<String, String> l1 = Caffeine.newBuilder()
        .maximumSize(10_000)                    // 单实例上限 1 万条
        .expireAfterWrite(Duration.ofSeconds(30)) // 本地 TTL 30s，短一点降低脏数据窗口
        .recordStats()                           // 统计命中率，用于监控调优
        .build();

// 两级读取（阶段一：L1；阶段二：L2 → DB 并双回填）
public String get(String key) {
    String v = l1.getIfPresent(key);            // ① 查本地
    if (v != null) return v;
    v = redis.get(key);                          // ② 查 Redis
    if (v != null) { l1.put(key, v); return v; } // 命中 → 回填 L1
    v = db.query(key);                           // ③ 回源 DB
    redis.set(key, v, 10, TimeUnit.MINUTES);     // 回填 L2（TTL 长）
    l1.put(key, v);                              // 回填 L1（TTL 短）
    return v;
}
```

**（2）写路径与两级一致性（Cache Consistency）——这是本考点最容易扣分也最值分的地方。** 核心策略是 **Cache Aside（旁路缓存）**：**先更新数据库，再删除缓存**（删除而非更新缓存，因为并发下两个线程各自更新缓存会把旧值覆盖成「脏值」，而删除是懒加载，下次读取自然重建）。写流程天然也是「两阶段」：**阶段一写 DB，阶段二删/失效缓存**。

两级缓存的一致性难在：L1 有 N 个进程副本，光删 Redis 不够，还得让所有实例把自己的本地缓存也删掉。三种手段：

- **广播失效（Broadcast Invalidation）**：写操作完成后通过 **Redis Pub/Sub** 发一条失效消息，所有实例订阅后删除本地对应 Key（注意：Pub/Sub 不保证送达，丢了消息要靠 TTL 兜底）；
- **可靠 MQ 广播**：用 RocketMQ 的广播模式（Broadcast Mode）下发失效事件，可靠性更高、可重试；
- **TTL 兜底（Backstop）**：把 L1 的过期时间设短（30s~5min），即使广播丢了，最坏也只是短暂读到旧值——**用「最终一致性（Eventual Consistency）」换取性能，是可接受的工程权衡**。

**（3）双写不一致（Double-Write Inconsistency）与延迟双删。** 根因是 DB 和缓存是两个独立存储，无法原子提交；典型竞态：写线程 A 更新 DB 期间，读线程 B 回填了旧值进缓存，导致缓存里长期是脏数据。经典解法是**延迟双删（Delayed Double Delete）**：先删缓存 → 更新 DB → 休眠几百毫秒（等并发读回填完成）→ **再删一次缓存**；更稳的做法是给数据带版本号，缓存写入时校验版本，旧版本直接丢弃。

**（4）与简历呼应——真实案例。** 我在数字藏品电商平台（省级实验室项目）中就实现了这套架构：技术栈是 `Spring Cloud Alibaba + Redis + Caffeine`，**用 Redis 和 Caffeine 构建多级缓存机制，优化数据读取速度、减少数据库压力**。当时针对**热点藏品**（抢购场景下的详情、库存信息）引入缓存，接口 RT 从 **700ms 降到 50ms**（提效 14 倍），Redis 压力大幅下降；库存类热点数据配合 **Lua + Redis 原子扣减**和 InventoryHint 热点拆分。落地过程中我重点处理了两点：一是 L1 容量与淘汰策略的调优（Caffeine 的 W-TinyLFU 保证秒杀时被批量请求挤不掉真正的热点），二是写库存这类强一致数据**不放进本地缓存**，只在 Redis 层用分布式锁（Redisson）保护——**不是所有数据都适合两级缓存，一致性要求 > 延迟收益时就要分层取舍**。

**（5）其他一致性策略对比**：**Write Through（直写）**——写 DB 的同时同步写缓存，读不会 miss 但写延迟翻倍；**Write Back / Write Behind（写回）**——只写缓存，异步批量刷 DB，吞吐高但宕机会丢数据；**Read Through**——缓存组件自己负责回源。两级缓存下常见组合：L1 用「TTL 刷新 + 广播失效」，L2 用 Cache Aside 或 Read Through。

## 4. 深入思考（注意事项）

**（1）缓存三兄弟在两阶段架构下的「变体形态」**——这是把八股答出深度的关键：

- **缓存击穿（Cache Breakdown）**：热点 Key 的 L1 和 L2 **同时过期**，一瞬间所有请求直接打到 DB。两阶段下击穿的伤害被放大：N 个实例的 L1 各自重建，等于 N 倍的回源。对策：**互斥重建（Single-Flight）**——单实例内用 `ConcurrentHashMap.computeIfAbsent` 或同步块保证只有一个线程回源，跨实例用 **Redisson 分布式锁**（加锁后要**双重检查**，防止第一个线程已重建完）；或者**逻辑过期 + 后台异步刷新**（永不过期，值带逻辑过期时间，读到过期值返回旧值并异步重建）。
- **缓存穿透（Cache Penetration）**：查询一个**根本不存在的 Key**，两级缓存永远 miss，全部穿透到 DB。对策：**布隆过滤器（Bloom Filter）前置**到 L1 之前，不存在的 Key 直接被滤掉；或把「空值」也写进 L1、L2（TTL 设短，如 5 分钟），防止恶意流量反复打 DB。
- **缓存雪崩（Cache Avalanche）**：L2 整体宕机或大量 Key 同时过期。两阶段的形态变化是：**L2 挂掉后，各实例 L1 的 TTL 仍在各自流逝，到期后每台机器各自回源 DB，形成「错峰雪崩」**。对策：过期时间加随机抖动（Jitter）错峰；L1 永不过期 + 后台刷新；配合 Sentinel 限流降级——简历里我在数字藏品项目就用 Nginx + Sentinel 做过服务限流，可以和这里打通讲。

**（2）「两阶段提交（Two-Phase Commit, 2PC）」在缓存重建中的应用**——这层联想是加分项，恰好呼应题目里的「两阶段」：

- **重建锁协议本身就是 2PC 的两段式**：缓存击穿时的互斥重建，可以建模为 **Prepare（阶段一）**：抢分布式锁、二次检查缓存是否已被他人重建；**Commit（阶段二）**：回源 DB → 写入 L2 → 写入 L1 → 释放锁。类似 2PC 的 prepare/commit，先确认「我能不能写、值是否已变化」，再原子完成「写缓存」这一步。
- **DB 与缓存双写的一致性问题，可以用「事务消息」做 2PC 化落地**：RocketMQ 事务消息的机制正是 2PC 思想的工程实现——先发送**半消息（Half Message）**（相当于 prepare），本地执行 DB 事务（提交 = commit），提交成功后确认消息发出，消费者收到消息去删除/更新缓存；DB 事务失败则回滚消息，缓存就不会被错误更新。这样「更新 DB」和「失效缓存」从无序双写变成了**可保证顺序、可补偿的两阶段**。
- **版本号 + 原子指针切换（Copy-on-Write 式提交）**：重建缓存分两步提交——先写新值（带全局递增版本号），再原子地把「当前版本指针」切换到新值。读者永远读到「旧版本的完整数据」或「新版本的完整数据」，看不到中间态，这其实就是 2PC 里「prepare 可见性隔离 + commit 原子生效」的思想。
- 但要指出边界：**纯 2PC 在缓存场景不可直接用**——协调者（Coordinator）单点、同步阻塞、参与者宕机会阻塞全局，所以工程上几乎都是「异步 MQ + TTL 兜底」的最终一致性，2PC 思想只用于「重建」这个窄场景。能说出「为什么不能全用 2PC」，面试官就知道你真懂分布式事务。

**（3）边界与陷阱**：本地缓存天然有**副本延迟（Replica Lag）**，强一致场景（如库存扣减、支付金额）绝不放 L1；L1 过大会挤压堆内存引发频繁 GC；L1 命中率要接入监控（Caffeine `recordStats()`），低于 60% 说明配置不当（容量太小 / TTL 太短 / Key 设计不合理）。

## 🗺️ 回答思路

**答题逻辑框架（总分总，5 步走）**：
1. **一句话定义**（30 秒）：两阶段缓存 = 本地缓存 + 分布式缓存的二级架构，配合「先查缓存、未命中查源」的两阶段读取流程；
2. **为什么需要**（1 分钟）：延迟数量级差距（100ns vs 1ms vs 10ms）+ 热点二八定律 + 给 Redis 减压、顺带容错；
3. **怎么实现**（1.5~2 分钟）：选型（Caffeine W-TinyLFU + Redis）→ 读路径两查一回填 → 写路径 Cache Aside「先更 DB 再删缓存」→ 两级一致性（广播失效 + TTL 兜底 + 延迟双删）；
4. **简历案例**（1 分钟）：数字藏品项目 Caffeine + Redis 多级缓存，热点藏品 RT 700ms→50ms；
5. **主动拔高**（1 分钟）：击穿/穿透/雪崩在两阶段下的形态 + 2PC 思想在缓存重建中的应用。

**重点得分点**（面试官在听的）：① 能报出**三个数量级的延迟对比**；② 主动说出「**删除缓存而不是更新缓存**」及原因；③ 点出**本地缓存有 N 份副本、必须广播失效**这个两阶段独有的难点；④ 简历量化数据准确（700ms→50ms）；⑤ 结尾抛 2PC 与缓存重建的联想——这属于「超纲但正确」的亮点。

**常见误区**：只说「本地缓存 + Redis」七个字，不展开读/写两条链路；把「击穿、穿透、雪崩」三兄弟讲混（击穿=热点过期，穿透=查不存在，雪崩=大量同时失效）；说「先更新缓存再更新 DB」或「更新缓存」——正确姿势是「先 DB 后删缓存」；忘了提一致性（只讲性能不讲一致性 = 只答对一半）；编造简历里没有的多级缓存项目（我的经验是数字藏品项目，必须锚定它）。

**时间分配建议**：整体控制在 **3~4 分钟**——定义 30s，原理 1min，实现 1.5min，案例 40s，深入思考 30~40s（作为「如果面试官追问」的储备，主动讲 1-2 个即可，别贪多）。

**过渡话术**：
- 定义 → 原理：**「刚才说的是它是什么，接下来讲为什么需要它——核心是三个数量级的延迟差距。」**
- 原理 → 实现：**「理解了这个差距，落地时的关键就变成两件事：读路径怎么分层，写路径怎么保证两级一致。」**
- 实现 → 案例：**「这套方案我在数字藏品项目里真实落地过——Redis + Caffeine 多级缓存，热点藏品接口 RT 从 700ms 降到 50ms。」**
- 收尾（把话头递给面试官）：**「最后我想补充一点两阶段架构的延伸思考——缓存击穿时用 2PC 思想做互斥重建……如果面试官想深入，我可以展开讲讲双写一致性的细节。」**
